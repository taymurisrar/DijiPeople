PostgreSQL via **Prisma 7.8** with the `@prisma/adapter-pg` driver adapter.

Working rules for changing it: [`../../services/api/prisma/AGENTS.md`](../../services/api/prisma/AGENTS.md).

## Conventions

```prisma
model Thing {
  id          String   @id @default(uuid())
  tenantId    String
  code        String
  status      ThingStatus @default(ACTIVE)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
  createdById String?
  updatedById String?

  tenant Tenant @relation(fields: [tenantId], references: [id], onDelete: Cascade)

  @@unique([tenantId, code])
  @@index([tenantId])
  @@index([tenantId, status])
}
```

- `PascalCase` models, `camelCase` fields, `SCREAMING_SNAKE_CASE` enum members.
- **No `@@map` / `@map`** — Prisma names are the physical table and column names.
- Primary keys are `String @id @default(uuid())`. `ErrorLog` uses `cuid()`;
  there are no integer keys.
- `createdAt` / `updatedAt` on primary entities; `createdById` / `updatedById`
  where an actor matters.
- Money is `Decimal` with explicit precision. Coordinates appear as both
  `Decimal @db.Decimal(10, 7)` and `Float` in different models — follow the
  neighbouring field rather than "fixing" it as a drive-by.
- `Json` is used for snapshots, policy payloads, settings values and metadata.
  It is not queryable — nothing you must filter or join on belongs there.
- Long explanatory comments on non-obvious fields are house style (see
  `AttendanceEntry.workedMinutes`). Keep them.

## Tenant-owned models

- `tenantId String` + `tenant Tenant @relation(..., onDelete: Cascade)`.
- `@@index([tenantId])` minimum, plus `@@index([tenantId, <column>])` for every
  list filter and sort.
- **Uniqueness must include `tenantId`.** `@@unique([tenantId, employeeCode])`,
  never a bare unique on a business key.
- Platform-owned models (`Platform*`, `Plan`, `Lead`, `Partner`,
  `CustomerAccount`, `PlatformAuditLog`, …) deliberately have no `tenantId`.

`tenantId` appears ~1,493 times across the schema. That is a naming convention;
**it is not enforcement** — see [`tenancy.md`](tenancy.md).

## Soft delete

`isDeleted` exists on a small number of models (`Employee` among them). It is
**not** universal. Check before assuming, and when it exists, filter it in every
read path including counts and uniqueness checks.

## Migrations

```
services/api/prisma/migrations/
  20260814140000_attendance_operational/
  20260814120000_attendance_engine/
  20260814090000_gateway_runtime_phase2/
  ...
  migration_lock.toml
```

Timestamped `YYYYMMDDHHMMSS_snake_case_description`, generated by
`prisma migrate dev`, applied in production by `prisma migrate deploy` as part
of `npm run release:api`.

Hard rules (full detail in the prisma `AGENTS.md`):

- Never edit or delete an applied migration. Fix forward.
- Never `migrate reset`, `db push` or `db execute` against a shared database.
- **Schema and migrations are single-writer** — one task, one owner, at a time.
- Regenerate the client (`npm run prisma:generate`) before typechecking anything
  that imports `@prisma/client`.
- Destructive changes stage as expand → backfill → contract, with an idempotent
  backfill script (see `backfill-attendance.ts`,
  `backfill-default-views.ts`).
- Enum members can be added; **removing or renaming one breaks stored rows** and
  every exhaustive `switch` in the API and both frontends.

## Prisma client and scoping middleware

`common/prisma/prisma.service.ts` extends `PrismaClient` with the `pg` adapter
and attempts to register a `$use` middleware that applies **business-unit**
scoping (not tenant scoping) for a fixed model list, and writes a
`BUSINESS_UNIT_ACCESS_DENIED` audit row when an id-targeted query is filtered to
nothing.

> **It does not run.** `@prisma/client@7.8.0` no longer exposes `$use`; the
> constructor checks `typeof this.$use === 'function'`, logs a debug line and
> returns. Verified: `PrismaClient.prototype.$use === undefined`.
>
> Row scoping that actually takes effect is the explicit
> `buildScopedAccessWhere()` calls in services. See [`rbac.md`](rbac.md).

| Script | Command | Production |
|---|---|---|
| `seed-config.ts` | `npm run seed:config` | **Yes** — every release |
| `verify-seed-config.ts` | `npm run seed:verify` | Yes |
| `seed-admin.ts` | `npm run seed:admin` | Yes |
| `seed-platform-workflows.ts` | `npm run seed:platform-workflows` | Yes |
| `seed-demo.ts` / `seed-demo-reset.ts` | `npm run seed:demo` / `:reset` | **No** |
| `seed-payroll-flow.ts` | `npm run seed:payroll-flow` | No |

`npm run release:api` = `migrate deploy` → `seed:config` → `seed:verify` →
`seed:admin`.

All seeds must be idempotent. New permission keys, roles, system views, catalog
entries or required configuration rows **must** be added to `seed-config.ts` and
asserted in `verify-seed-config.ts`, or a fresh deployment comes up missing
them. Demo rows carry `isDemoData` / `demoBatchId` so the reset script can find
them.

Detail: [`../seed-architecture.md`](../seed-architecture.md).

## Known risks

1. One 11,800-line schema file is the worst merge-conflict surface in the
   repository.
2. The long migration chain is checked from empty by the required
   `database-migration` CI job. Upgrade-from-previous-schema and environment
   drift are still not automated; `npm run prisma:migrate:status` remains the
   local/manual status check.
3. Multiple worktrees typically share one `DATABASE_URL`; two agents running
   `migrate dev` will corrupt each other's migration state.
4. The Prisma-level scoping middleware reads as active defence and is not.
5. Tenant isolation depends entirely on query-site discipline; the schema
   provides the column, not the guarantee.
