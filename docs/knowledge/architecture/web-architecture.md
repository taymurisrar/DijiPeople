## CURRENT

The tenant product. Next.js App Router, React 19, Tailwind v4, port **3001**.
**1,100 TypeScript files, 253 pages, 416 route handlers, ~145,000 lines** —
roughly seven times `apps/landing`.

Two route groups only: `(authenticated)` (231 pages) and `(public)` (4).
`activate-account/`, `dashboard/`, `partner/`, `t/`, `workspace/` and `api/` are
plain segments, not groups. **`workspace/` is missing from every instruction
file** and matters — it serves the workspace-state pages the proxy rewrites to.

209 files carry `'use client'`; **zero carry `'use server'`.** There are no
server actions — every mutation goes through `app/api/**`.

## How a screen is actually built

**Not by registration.** `apps/web/AGENTS.md` used to say a new module is
registered in `module-registry.ts` and `command-registry.ts`; those registries
have **zero call sites** and are inert
([[BUG-0044-the-documented-new-module-workflow-for-apps-web-cannot-be-fo]],
fixed; the code decision is [[ITEM-0036]]).

A module is a **`StandardModuleRuntimeSpec` object** imported directly by the
route file and converted per render:

```
page.tsx (server)
  → apiRequestJson("/projects")            lib/server-api.ts
  → buildStandardRouteRuntime({spec, sessionUser})
  → <StandardModuleListPage records runtime spec/>   (client)
      → ModuleListPage → ModuleDataTable
```

**105 specs exist, from three sources** — 11 in `standard-module-specs.ts`, 12 in
`payroll-foundation-runtime-specs.ts`, and **82 generated by
`settings-adapter-registry.ts`**, which is the one *live* registry in the app and
self-validates at module load. That file is absent from the runtime documentation
despite holding four fifths of the specs.

**61 of 253 pages (24%) are runtime-driven.** `employees` is bespoke by design
(3,850 lines of dedicated adapters); `attendance` (9 of 11 bespoke) and
`timesheets` (4 of 5) are the areas that drifted furthest from the runtime, and
no file records why.

Two coupling facts worth knowing before extending it: `moduleKey` string
equality selects command handlers and derives the API path (`"/api" + routeBase`
when `apiPath` is absent), and the "generic" data adapter already carries **nine
hardcoded module branches** — per-module behaviour accreting into the shared file
for want of a registration point.

## The data path

`lib/server-api.ts` (762 lines) is the only sanctioned caller: cookies,
`Authorization: Bearer`, `X-DijiPeople-App`, a 30 s timeout, refresh-on-401 with
a **single** retry, and `ApiRequestError` normalisation.

**Nothing is cached, by construction.** Zero `revalidate`, zero
`unstable_cache`, zero `revalidateTag`. `server-api` defaults every fetch to
`cache: "no-store"` and calls `await cookies()`, which opts every enclosing
render into dynamic rendering. Freshness is guaranteed; there is **no
cache-invalidation surface at all**, which is why the settings-save staleness in
[[BUG-0046-tenant-theme-mode-and-runtime-settings-saves-do-not-take-eff]] is a
provider problem rather than a cache one.

The 416 route handlers are mostly thin — 357 use `proxyApiJsonResponse`. The
exceptions are recorded:
[[BUG-0039-employee-payslip-and-bank-account-proxies-return-the-callers]] (two
handlers substitute the caller's own data on a 403) and
[[BUG-0041-web-route-proxies-make-authorization-and-business-decisions]]
(one authorization decision, several business-logic sites). **125 of 416 flatten
the upstream status to 500** — [[ITEM-0035]].

## Tenant isolation — the part that is done well

Two mechanisms, and the authoritative one is solid.

`proxy.ts` (611 lines) resolves the workspace **before anything renders**, and
**fails closed**: an unresolvable hostname serves a workspace-state page unless
`resolvePlatformEnvironment(process.env) === DEVELOPMENT` — gated on
`PLATFORM_ENVIRONMENT`, deliberately not on `NODE_ENV`. Hostname parsing uses
exact suffix matching plus single-label arithmetic, so
`victim.dijipeople.com.attacker.com` resolves to nothing. The six workspace
headers are **deleted before being set**, so a browser cannot forge them, and
`assertSessionMatchesWorkspace` compares the hostname's tenant to the session's
before any tenant data is fetched.

**Zero route handlers accept a `tenantId` from the client** — verified across all
416. The proxy performs no signature verification and no role logic; it decodes
the JWT only for expiry and session id. That is the correct division.

The one soft spot: `proxy.ts:164` trusts `x-forwarded-host` ahead of `Host` with
no allowlist, and whether the edge strips it cannot be determined from this
repository. Recorded in the QA run rather than as a bug, because exploitability
depends on hosting configuration that is not committed anywhere.

Separately, `lib/tenant-resolution.ts` is a *hint* layer that does read a cookie
and `?tenant=`; both are slug-validated and reach only login/logout URL
construction, never data access. Logout does not clear the tenant cookie, which
produces a cross-tenant login bounce on a shared browser.

## Testing — the shape of the gap

`jest.config.js` is `testEnvironment: "node"`, `testMatch: **/*.spec.ts`
(**`.spec.tsx` is not matched**), with an inline tsconfig that ignores
`apps/web/tsconfig.json`. jsdom and testing-library are not installed.

**17 specs** cover pure logic — resolvers, catalogs, validators — and two are
genuinely load-bearing: `workspace-routing.spec.ts` pins the suffix-confusion
cases, and `settings-runtime.spec.ts` asserts every settings route resolves to a
file that exists on disk.

What cannot be tested at all under this config: every page, every client
component, `proxy.ts`'s decision flow, `lib/server-api.ts`, and all 416 route
handlers. **And `apps/web` has zero browser coverage** — the Playwright suite
never opens port 3001 ([[ITEM-0034]]). So the largest application has no
mechanism that can test its largest surfaces.

CI covers it through six required jobs (`lint`, `typecheck`, `test-web`,
`build`, `test-runtime`, and indirectly `test-api`, whose wiring invariants read
four `apps/web` files across the workspace boundary — renaming them breaks an
API test).

## Environment and deployment

`next.config.ts` calls `validateDeploymentEnv` at module scope, so a missing
variable fails the **build**. For `web` the minimum is
`NEXT_PUBLIC_API_BASE_URL` plus one of the four web-URL keys, both non-loopback.
Note CI never sets `APP_ENV`/`VERCEL`/`RENDER`, so **the production branch of
that validation never runs in CI** — a missing URL passes CI and fails on Vercel.

**21 variables are read but unregistered in `turbo.json` globalEnv**
([[BUG-0042-apps-web-reads-21-environment-variables-unregistered-in-turb]]),
including three `NEXT_PUBLIC_*` flags inlined at build time. Four registered
variables are read nowhere.

Deploys to **Vercel as `diji-people-web`** — evidenced by GitHub PR check names,
not by anything in this repository. There is no `vercel.json`; `render.yaml`
defines only the API. Unlike `apps/landing`, `apps/web` **does** have a `release`
script (an alias for `build`).

`next.config.ts` also carries **55 settings redirects** that expand to 110 rules,
remapping the flat legacy `/settings/<thing>` namespace onto the current
hierarchy. None is asserted by any test.
