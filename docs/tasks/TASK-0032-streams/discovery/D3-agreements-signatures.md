**Authorization deviates from the documented house pattern.** Instead of the two-decorator `PermissionsGuard`/`RequirePermission` system described in root `AGENTS.md`/`services/api/AGENTS.md`, every write path calls a private `assertPlatform(user)` (`contracts.service.ts:5080`) — requires `user.platform?.id` **and** `userHasPlatformPermission(user, 'contracts.read')` — or `assertWrite(user)` (5087) which additionally requires `contracts.manage`. This means:
- **Tenant admins have no access to this module at all** — it is exclusively a platform-staff (DijiPeople internal) surface for managing commercial agreements, not a tenant-product feature. (Answers scenario 26 below: N/A by design, not a gap.)
- `listPlaceholderDefinitions` (`GET /contracts/placeholder-definitions`, 1089) only calls `assertPlatform`, i.e. **read** access is enough to see the full registry (including `CONFIDENTIAL`-classified example values like tax IDs) — there is a `securityClassification` field on each `ContractPlaceholderDefinition` but nothing in `listPlaceholderDefinitions` or `renderContractPlaceholders`/the admin UI actually filters or redacts by it. It exists as metadata only.
- Partners get a **separate, read-only, correctly tenant/partner-scoped** view: `partner-experience.service.ts:1041 listPartnerContracts` / `:1071 getPartnerContract`, both `where: { partnerId: actor.partnerId }` after `assertPartnerActor(actor)`. Partners cannot create, edit, send, or manage agreements — only read their own.
- External signers (partner or customer contact) never authenticate at all; they use the emailed public link (`/public/signatures/:token`), rate-limited only.

**Lifecycle / immutability**: `assertAgreementEditable(status)` (4922) throws on `SENT, VIEWED, SIGNATURE_IN_PROGRESS, PARTIALLY_SIGNED, FULLY_SIGNED, FULLY_EXECUTED, ACTIVE, SUPERSEDED, TERMINATED, ARCHIVED` — i.e. everything from `SENT` onward, called before every party/field/content mutation (1871, 2812, 2847, 2901, 2922). This is the fix for **BUG-0011** (`docs/bugs/BUG-0011-signed-agreement-editable-defeating-the-lead-conversion-gate.md`) — the old code kept its own drifted copy of the blocked-status list and let a `FULLY_EXECUTED` agreement's `relatedLeadId` be edited, silently moving the lead-conversion gate. `governing-agreement.ts` is the single shared definition of "governing agreement executed" (`GOVERNING_CUSTOMER_AGREEMENT_TYPES` + `EXECUTED_CONTRACT_STATUSES` = `FULLY_EXECUTED, ACTIVE, EXPIRING, EXPIRED, ARCHIVED`).

**Versioning / regeneration**: A new `ContractVersion` row is created at `sendForSignature` (3260) with **fully resolved** `contentHtml` (all non-signature placeholders substituted from a frozen `placeholderSnapshot`, hashed as `contentSha256`/`placeholderSnapshotSha256`) — this is the version that gets signed and is never mutated again. Editing before sending mutates the current draft version in place (`saveVersion`/`update`, gated by `assertAgreementEditable`). Regenerating a PDF (`generateDocument`, 4250) always reads `contract.versions[0]` ordered by `version desc` — i.e. **the latest version**, not necessarily the signed one, though in practice once `FULLY_EXECUTED` no new version can be created (immutability gate) so they coincide.

**Auditability — BUG-3231 (DEFERRED, MEDIUM, `docs/bugs/BUG-3231-*.md`)**: `rg "AuditService|auditService|audit\.log"` inside `modules/contracts` (excluding specs) returns **zero matches** across 31 mutating endpoints. Contract signing, amendment, void, and termination are invisible to `AuditService`/`/api/audit-logs`. The module keeps its own parallel, non-queryable trail instead: `ContractTimeline` rows (e.g. `contracts.service.ts:3955` `DOCUMENT_SIGNED`) and an ad-hoc `auditTrail` array assembled at 3990 from `SignatureEvent` rows for the evidence bundle JSON — neither passes through `redactAuditSnapshot`, neither is queryable from the standard audit surface, and both are deleted along with the contract (no `AuditLog` row survives deletion). Architect disposition: `DEFER`, contracts prioritized as legal-exposure but not yet fixed.

## 3. Placeholders

**Registry**: `CONTRACT_PLACEHOLDER_REGISTRY` (`contracts.service.ts:285`), a flat array of `ContractPlaceholderDefinition` built by a `placeholder()` factory (230). Each entry: `key`, `label`, `description`, `dataType` (`TEXT|EMAIL|PHONE|ADDRESS|CURRENCY|CURRENCY_CODE|PERCENTAGE|DATE|DATE_TIME|BOOLEAN|INTEGER|DECIMAL|URL|TABLE|REPEATING_COLLECTION|SIGNATURE|INITIALS|USER|PARTNER|CUSTOMER`), `required`, `fallbackBehavior` (`ERROR|LEAVE_TOKEN|EMPTY`), `securityClassification` (`PUBLIC|INTERNAL|CONFIDENTIAL` — metadata only, unenforced, see §2), `allowedContractTypes` (present but appears empty/unused in every registry entry read — no per-contract-type filtering was found applied against it in `listPlaceholderDefinitions` or the template editor).
- Default: `required: true`, `fallbackBehavior: 'ERROR'` unless the key starts with `signature.` (then `required: false`, `fallbackBehavior: 'LEAVE_TOKEN'`).
- `optional` helper (262) sets `required: false, fallbackBehavior: 'EMPTY'` for terms the platform may not hold (e.g. `partner.contact.phone`... many `customer.*`/`platform.*` fields).
- `DEPRECATED_PLACEHOLDER_ALIASES` (208) + `deprecated()` (272): legacy keys (`customer.name`, `customer.contactName`, etc.) still resolve, backfilled from the canonical key at render time via `applyDeprecatedPlaceholderAliases`, but are not offered when authoring new templates.
- Namespaces seen: `platform.*`, `partner.*`, `customer.*`, `contract.*`, `counterparty.*`, `lead.*` (implied), `tenant.*`, `commercial.*`, `implementation.*`, `hosting.*`, `sla.*`, `signature.*` — grouped for the UI by `placeholderGroup()`/`PLACEHOLDER_GROUP_ORDER` (5979): Platform, Partner, Lead, Customer, Commercial, Contract, Service order, Tenant, Implementation, Integration, Hosting, SLA, Signatures, Other.

**Template-editor endpoint**: `GET /contracts/placeholder-definitions` → `ContractsService.listPlaceholderDefinitions` (1089), consumed by `apps/admin/app/_components/documents/contract-template-editor.tsx:201`. It returns each registry item plus `group` and `exampleHtml` — the example run through the **real renderer** (`renderContractPlaceholders`), not a raw string substitution. A code comment there documents a prior bug: the preview used to show raw `exampleValue` (`["Employees","Attendance","Payroll"]`, `99.5`) instead of the rendered form (a bulleted list, `99.5%`) — fixed by rendering the example through the same function used for real documents.

**Resolution / unresolvable placeholders** (`renderContractPlaceholders`, 5495; `extractContractPlaceholders`, 5539; `validateContractPlaceholderValues`, 5561):
- A `{{key}}` token with no value and `fallbackBehavior !== 'EMPTY'` is **left as the literal token in the HTML** (`match` is returned) — never `"undefined"` or `"[object Object]"`. This is deliberate: `renderContractPlaceholders`'s inline comment says the unresolved token exists so "the signature gate can refuse it."
- A key not in the registry at all gets a synthesized definition via `inferPlaceholderType()` (5641, heuristic on the key name) with default `required: true, fallbackBehavior: 'ERROR'` unless it starts with `signature.`.
- `sendForSignature` (3146) calls `assertValidContractPlaceholderValues(definitions, snapshot, true)` **before** resolving — throws `BadRequestException` listing every unmet required placeholder by label, and separately rejects if any **non-signature, non-initials** placeholder remains unresolved in the rendered HTML (3180-3188) — a required-placeholder-missing send is fully blocked (scenario 18 below).
- `validateContractPlaceholderValues` also type-checks each populated value (numeric for `INTEGER/DECIMAL/CURRENCY/PERCENTAGE`, 3-letter code for `CURRENCY_CODE`, JSON/list for `TABLE`/`REPEATING_COLLECTION`, email regex, URL parse, date parse, boolean set) and collects human-readable errors rather than throwing on the first one.
- `formatPlaceholderValue` (5412) applies `formattingRule`/`dataType`-driven formatting (percentage `%`, currency-code-prefixed amount, `1 October 2026`-style dates, thousands separators) — documented as a **fix** for a prior defect where 19 declared `formattingRule`s were silently ignored and a service order printed `"99.5."` instead of `"99.5%"`.
- **Known prior defect, BUG-1541** (referenced in `source-fills-template.spec.ts`): a Tenant Provisioning template created *from a customer* resolved only 8/39 placeholders (every `tenant.*`/`implementation.*`/`hosting.*`/`commercial.*` stayed as raw unresolved tokens) because `customerSource()` never emits those namespaces. Fixed by `assertSourceCanFillTemplate` (1592), called from `createFromSource` (1538) — it refuses the *pairing* of template+source at creation time (before any HTML is generated) rather than letting the document render half-empty. It only checks **required** placeholders and excludes namespaces the source is never responsible for (`contract.*`, `platform.*`, `counterparty.*`, `sla.*`, `signature.*`).

## 4. Document generation

- **Renderer**: `pdfkit` (`import PDFDocument from 'pdfkit'`, line 21) for PDF; a DOCX path also exists (`createDocx`, referenced at 4379) — both take `(title, html, plainText)`. HTML is parsed (via `htmlparser2`/`domhandler` — `DomUtils`, `parseDocument` imports seen around 6214-6289) and walked to build the PDF content; not a headless-browser (no Puppeteer/Playwright) render.
- **Storage**: `common/storage/storage.service.ts` (`StorageService`) — `saveFile`/`readFileBuffer`, scoped by `contractStorageScope(tenantId)` (a contract's storage scope follows the tenant it's *with*, documented at 5093, not the platform staff handling it) and `domain: 'contracts'`, `segments: [contractId]`.
- **Frozen vs. live**: The **content** is frozen at `sendForSignature` time into a new immutable `ContractVersion` (all non-signature placeholders pre-resolved into `contentHtml`, hash-anchored via `contentSha256`). `signature.*` tokens are deliberately **not** resolved into that stored HTML — "the stored version HTML is never rewritten: evidence hashes anchor to its content, so the signature is applied at render time instead" (code comment, 3827). Re-running `generateDocument(..., immutable=true)` after full execution re-reads `SignatureEvidence` rows and does a **regex substitution of `{{signature.*}}` tokens only**, injecting `<img>` signature images (base64 data URI read back from storage) or "Electronic signature pending" placeholders — every other field in the document is whatever was frozen at send time, so a later change to the partner/customer/lead source record does **not** alter a reopened signed document (scenario 30 below: SUPPORTED for content; the signature appendix/audit certificate is recomputed each time from `SignatureEvidence`/`SignatureEvent`/`ContractTimeline`, which is fine since those are themselves immutable once written).
- Each `generate/:format` call, immutable or not, creates a **new** `ContractDocument` row (never overwrites) — `kind: 'SIGNED_COPY'` + `source: 'SIGNATURE'` when `immutable`, `isImmutable: true`; otherwise `GENERATED_PDF`/`GENERATED_PREVIEW` + `source: 'EDITOR'`, `isImmutable: false`. So repeated "Generate" clicks on a draft pile up `ContractDocument` rows; only the signature-completion-triggered generation is marked immutable. `sha256` of the **rendered PDF bytes** is stored on `ContractDocument.sha256` (separate from `ContractVersion.contentSha256`, which hashes the HTML).
- `openDocument` (4436) — `assertPlatform` only; resolves tenant scope by walking to the parent `Contract` because `ContractDocument` carries no `tenantId` of its own (documented as file `FILE-15`, explicitly called out as "no tenant-crossing bug today because only platform staff reach this, but a future non-platform caller would not inherit a scope").

## 5. Signatures

- **Capture UI**: `apps/landing/app/sign/[token]/signing-experience.tsx` — the only signature-capture surface in the repo (not in admin, not in the tenant `apps/web`). Public, token-only (`GET/POST /api/signatures/:token...` → proxied to `/public/signatures/:token` in the API).
  - **Typed**: a text input for the legal name plus a purely cosmetic "Classic / Script / Formal" font-style `<select>` (`typedStyle` state) — **the style is never sent to the API** (only `typedName` is posted); the signed document always renders the typed name as plain bold text (`renderSignatureValue`/the injected `<strong>` in `generateDocument`), so the style picker has no effect on the final document. Server-side minimum length check: `typedName.trim().length >= 2` (3724).
  - **Drawn**: an HTML5 `<canvas>` (touch/pointer events, no third-party lib), exported via `canvas.toDataURL('image/png')`.
  - **Uploaded**: PNG/JPEG file input, client-validated to ≤2MB and one of the two mime types before base64-encoding as a data URL.
  - All three post the same `signatureDataUrl` (drawn/uploaded) or `typedName` (typed) to `POST /public/signatures/:token/sign` with `consentAccepted`, `consentText` (echoed back from the session payload), and the browser's IANA timezone.
- **Server-side persistence** (`completeSignature`, 3678): decodes the data URL (`decodeSignatureDataUrl`), detects PNG vs JPEG by magic byte, saves the image via `StorageService.saveFile` (scoped to the contract's tenant), and writes one `SignatureEvidence` row per signer with: `method`, `typedName`, `signatureStorageKey`/`Provider`, `signatureSha256`, `consentText`+`consentVersion`+`consentAcceptedAt`, `ipAddress`, `userAgent`, `sessionId` (from `x-request-id`), `timezone`, `signerEmail`/`signerRole`/`partyId`, `agreementVersion`, `authenticationMethod: 'SECURE_TOKEN'`, `verificationStatus: 'TOKEN_VERIFIED'`, `requestTokenId` (sha256 of the raw token, truncated — never the raw token itself), `documentSha256` (the `ContractVersion.contentSha256` being signed), and the hash chain fields.
- **Hash chain**: `eventHash = sha256(JSON.stringify({ documentSha256, recipientId, signatureHash, consentText, signedAt, eventSequence, previousEventHash }))` (3760) — each signer's evidence links to the previous signer's `eventHash` in signing order (queried via `signingOrder: { lt: recipient.signingOrder }`, 3748-3756), so the whole `SignatureEvidence` chain for a request is tamper-evident. A **separate**, similarly hash-chained `SignatureEvent` log records lifecycle events (`SENT`, `VIEWED`, `SIGNED`, `DECLINED`, etc.) per signature request — same `eventHash`/`previousEventHash` pattern (5018-5035, `signatureEventTx`).
- **Rendering into the final document**: signatures ARE rendered into the document, not left as "signed electronically" text — `generateDocument` (§4) substitutes `{{signature.*}}` tokens with an actual `<img>` of the drawn/uploaded signature (or bold typed name text) plus a metadata line (`method · timestamp · Verified · SHA-256 <prefix>…`). A companion **evidence bundle** (`*-evidence.json`, saved to storage, 3988-4041) captures the full signer list, consent text/version, hash chain, and IP/UA for compliance/legal retention, independent of the human-readable PDF.
- **Idempotent re-sign**: if `recipient.status === SIGNED` already, `completeSignature` short-circuits with `{ success: true, completed: ..., message: 'Signature was already recorded.' }` (3703) rather than erroring or double-writing.
- **Sequential enforcement**: `earlierIncomplete` check (3713) blocks a later-order recipient from signing before an earlier required one has, unless `signingMode === 'PARALLEL'`.
- Downstream side effects on the final signature (`isFinal`, 3772): `ContractVersion.status → SIGNED` + `lockedAt`; `Contract.status → FULLY_EXECUTED`; `CustomerOnboarding.contractSigned = true` if linked; for `PARTNER_AGREEMENT`/`MASTER_PARTNER_AGREEMENT`, `Partner.status → AGREEMENT_EXECUTED`, a `PartnerTimeline` row, and auto-creation of a default `PartnerReferralLink` if none exists yet.

| # | Scenario | Verdict | Evidence |
|---|---|---|---|
| 1 | Partner, no customer | SUPPORTED | `CreateContractDto.partnerId` optional/independent; `validateCounterparty` only requires `partnerId` for `PARTNER_AGREEMENT`/`MASTER_PARTNER_AGREEMENT` (4879); nothing requires a customer link. |
| 2 | Partner, no lead | SUPPORTED | Same DTO — `relatedLeadId` fully independent of `partnerId`. |

| 7 | Before lead conversion | SUPPORTED | `leadAgreementScope`/`executedGoverningAgreementWhere` (`governing-agreement.ts`) is exactly the mechanism that gates lead conversion on an executed agreement — pre-conversion, a `CUSTOMER_AGREEMENT` can exist against `relatedLeadId` alone (no `customerAccountId` yet). |
| 8 | After lead conversion | SUPPORTED, known past defect fixed | `customerAgreementScope` matches via direct FK **or** `ContractRelatedRecord` — the mechanism for keeping the lead-era agreement visible from the resulting customer.
