## What this release changed in production

| | Before | After |
|---|---|---|
| Saving a plan price | Silently deactivated siblings across billing models and markets | Supersedes only the true slot occupant |
| Editing a price with a stale Stripe id | `500 SYSTEM_UNEXPECTED_ERROR` | Saves; row marked unsynced with a readable reason |
| `invoice.paid` webhook | Rejected — a customer could pay and get no workspace | Resolves from either Stripe API shape |
| A failed-webhook notification | "Provider webhook failed / Stripe webhook processed" | Names the reason and the path to fix and replay |
| Home page plan cards | A price with no indication what it buys | The same capability ladder as `/plans` |
| `/plans` estimate | "QAR 80 · below this plan's minimum" | "10 seats (this plan's minimum, not your 1) × QAR 8 each" |

## The deploy repaired the price data, as predicted

The nine Starter prices destroyed by [[BUG-1133]] on 2026-08-24 are active again,
and no manual step was needed.

| | Before the release | After |
|---|---|---|
| `starter` | **3** | **12** |
| `growth` | 12 | 12 |
| `enterprise` | 12 | 12 |
| `enterprise-plus` | 0 (intended — the "ask us" tier) | 0 |
| **Total active prices** | **27** | **36** |

`preDeployCommand` ran `seed:config` → `bootstrapCommercialDefaults`, whose
`findActiveForSlot` filters on the full five-column key and creates a price where
a catalogue slot has no active occupant. TASK-0019 recorded this expectation
*before* the merge rather than explaining it afterwards, which is the difference
between a prediction and a rationalisation.

The fix that stops the loss shipped in the same deploy that repaired it, so the
repair could not re-arm the trap.

**One false alarm, recorded because dismissing it silently would be the wrong
habit.** Three consecutive probes returned `000` in ~0.2s, including
`/api/health`, which had answered normally minutes earlier. The cause was local:
`curl: (43) A libcurl function was given a bad argument`. Re-running the same
requests through Node's `https` returned `200` for both. The service was never
affected — but "the tool broke" is a conclusion that has to be demonstrated, not
assumed, when the alternative reading is "production just went down".

## What this release does not do

**It does not make the platform live.** `STRIPE_MODE` remains `test`, so no real
payment can be collected — [[BUG-0903]], and an owner decision rather than a
deployment step. [[BUG-0898]] is likewise unchanged: 2 of 36 prices carry a
synced Stripe price, both on `starter`, both `TEST`.

This release fixed the machinery of the payment path. Opening it for business is
a separate, deliberate act.
