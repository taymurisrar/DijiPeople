## What shipped

### A business refusal reads as a refusal, not as a crash

`BUG-2822` · `REG-392` · `QA-RUNTIME-040`

Pressing Approve on your own approval raised the platform's fatal-error dialog —
red `ERROR ACCESS_DENIED`, a reference id, a timestamp and a **Download log**
button — for a rule the product deliberately enforces and had just enforced
correctly. Attendance already had this split, written after the same complaint
about a refused check-in; it was per-module, so every module added since
inherited the fatal dialog. `classifyCommandFailure` now sits in the shared
runtime, and business refusals go to a toast carrying the server's own sentence.

The line is drawn on HTTP status (400/403/409/422), not on a list of error codes
— a code list in the frontend is a second copy of the API's catalog and fails in
the dangerous direction, dressing a real defect as a calm toast. 401 and 404 stay
with the dialog.

### The advisory sweep

`ITEM-0122` — 40 undocumented advisories → 0.

The first assessment was wrong and the correction is the useful part: it looked
like twenty packages needing major bumps including a prisma downgrade, but that
was npm's package-level count, inflated by `apps/admin` pinning fifteen tiptap
packages at an exact `3.29.2`. `isSemVerMajor` was false for all of them; the
real fix was a **minor** bump to 3.31.3, clearing 34 of the 40 alone. The rest
went to `npm audit fix --omit=dev` — `@xmldom/xmldom` 0.8.13→0.8.15 (high),
`fast-uri` (high), `sanitize-html`, `qs`, `brace-expansion`, `js-yaml`,
`nodemailer`. `--force` was never run.

## The decision this release required

`ITEM-0123` — **multer ≤ 2.2.0, three high DoS advisories, accepted.**

Three high advisories against `multer` were published *between* this branch's
green CI run and the release PR's run on the same SHA, sixteen minutes apart.
multer is the multipart parser behind every authenticated upload, so the path is
live. **No reachability claim is made to the contrary.**

It was dispositioned rather than fixed, and the fact that decided it is not the
obvious one:

> **multer 2.2.0 was already in production.** It is in `main`'s lockfile at
> `fe1cd3dd`, and had been serving traffic for as long as
> `@nestjs/platform-express` has pinned it.

So the choice was never "ship a vulnerability or don't" — it is live either way.
The choice was whether to *also* withhold the 37 advisories this release fixes,
two of them high, in order to avoid writing down a risk that already existed.
Shipping improves the net posture.

The fix is unavailable rather than merely inconvenient. Checked on the day:
`11.2.3` (newest of the 11.x line this product is on) and `12.0.1` (latest
overall) both pin exactly `2.2.0`. npm's offered fix is `@nestjs/core@7.5.5`, a
downgrade from v11. Forcing a root override requires a from-scratch resolve,
which was attempted and measured: it produced multer 2.3.0 **and a CRITICAL
`tar` advisory, four further highs, and 294 unrelated version changes**. Reverted.

**Removal trigger**, recorded in the disposition itself:

```bash
npm view @nestjs/platform-express@latest dependencies.multer
```

Anything above `2.2.0` and all three entries come out.

**The gate itself was not changed.** Pinning an advisory snapshot, or moving the
feed-dependent check out of the required set, are real options and each trades
away some of a security control's bite — not a trade to make as a side effect of
clearing it. Recorded in `ITEM-0122` and as the bug pattern
`gate-that-depends-on-the-outside-world`.

## Follow-ups

1. **`ITEM-0123`** — remove the multer disposition the moment upstream ships the
   bump. One command checks it.

   object-level rules, so Approve can be enabled for an action the module
   refuses. The toast in this release makes that refusal read correctly, which
   reduces the sting without closing the gap.
