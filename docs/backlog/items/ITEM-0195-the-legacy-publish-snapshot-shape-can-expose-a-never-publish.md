# ITEM-0195 — The legacy publish snapshot shape can expose a never-published custom module at runtime

## Summary

The tenant runtime treats a custom module as available when it appears in the
tenant's latest published snapshot ([[BUG-3494]], REG-491). It reads two snapshot
shapes. The Publish Center shape lists only published components. The legacy
`publish()` shape lists every table present at publish time, including tables
never published through a package. If a tenant's latest snapshot was written by
the legacy path, a module nobody published could appear in the sidebar and
accept records.

## Why It Matters

REG-491 exists so a draft module's records are not reachable. Through the legacy
shape that guarantee depends on which publish path wrote the snapshot. The
Publish Center is believed to be the path in use, which is why this is low
priority, but that belief is an inference, not a check.

## Evidence

- `services/api/src/modules/data/published-custom-modules.ts` reads both
  `effectiveMetadata.modules/fields/forms/views` (Publish Center) and
  `tables/columns/forms/views` (legacy).
- `docs/tasks/TASK-0031-streams/WP-02-report.md`, "Residual risks and open
  items": "INFERENCE: the Publish Center is the path in use."

## Proposed Approach

First measure: count production tenants whose latest snapshot has the legacy
shape (read-only query). If none, stop reading the legacy shape for runtime
availability, or retire the legacy `publish()` path. If some, restrict the
legacy shape to tables with a published component layer. No ExecPlan needed
unless the legacy path is retired.

## Acceptance Criteria

- The production count of legacy-shaped latest snapshots is recorded here.
- A module with no published component layer is never runtime-available,
  whichever path wrote the latest snapshot, and a spec in
  `published-custom-modules.spec.ts` proves it.
