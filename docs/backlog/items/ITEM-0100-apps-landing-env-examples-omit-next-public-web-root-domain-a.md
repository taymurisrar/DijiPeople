# ITEM-0100 — apps/landing env examples omit NEXT_PUBLIC_WEB_ROOT_DOMAIN and no parity test guards them

## Summary

`apps/landing/.env.local.example` and `apps/landing/.env.example` contain no
`NEXT_PUBLIC_WEB_ROOT_DOMAIN` (or any of the other names
`getPlatformDomainConfig` accepts for it). A developer who sets the landing app
up by copying the example file — the documented way — gets an empty
`tenantBaseDomain`, and the subscribe wizard's workspace-address step renders a
bare `.` where the domain suffix belongs.

The parity test that exists to prevent exactly this only covers `apps/web`.

## Why It Matters

The broken suffix is on step 2 of checkout, so the first thing a developer sees
when exercising the purchase flow locally is a field that looks defective. It
is not — it is unconfigured — but nothing says so, and the cost is the time
spent proving it is not a real bug. This QA run spent that time.

More generally, the env-example parity test is a good mechanism that is applied
to one of four Next apps. The gap is likelier to widen than to close on its own.

## Evidence

`apps/landing/.env.local.example`, in full — nine variables, none of them the
root domain:

```
NODE_ENV=development
NEXT_PUBLIC_APP_NAME=DijiPeople
NEXT_PUBLIC_APP_ORIGIN=http://localhost:3001
NEXT_PUBLIC_LANDING_APP_URL=http://localhost:3000
NEXT_PUBLIC_WEB_APP_URL=http://localhost:3001
NEXT_PUBLIC_ADMIN_APP_URL=http://localhost:3002
NEXT_PUBLIC_API_BASE_URL=http://localhost:4000/api
API_BASE_URL=http://localhost:4000/api
API_ORIGIN=http://localhost:4000
```

The consumer, [`apps/landing/lib/env.ts`](../../../apps/landing/lib/env.ts):

```ts
tenantBaseDomain: getPlatformDomainConfig(process.env).tenantBaseDomain,
```

and its render at
[`apps/landing/app/subscribe/onboarding-steps.tsx:335`](../../../apps/landing/app/subscribe/onboarding-steps.tsx#L335):

```tsx
{slug}.{tenantBaseDomain} is available.
```

With the example file as given, step 2 of `/subscribe` shows the input suffixed
with `.` and the message `qa-e2e-test-company. is available.`

The guard that does not reach here —
[`packages/config/env-examples.test.js`](../../../packages/config/env-examples.test.js):

```js
const WEB = join(REPO_ROOT, "apps", "web");
const examplePath = join(WEB, ".env.example");
const localExamplePath = join(WEB, ".env.local.example");
```

It asserts `fromExample.tenantBaseDomain === fromLocal.tenantBaseDomain` and
that it derives from `NEXT_PUBLIC_WEB_ROOT_DOMAIN` — for `apps/web` only. Its
own header comment records that this test exists because the two web example
files once disagreed about that very domain.

## Proposed Approach

Add `NEXT_PUBLIC_WEB_ROOT_DOMAIN` to both landing example files, then widen the
parity test to iterate over the apps that have example pairs rather than naming
`apps/web`. Widening it will likely surface the same gap in `apps/admin`, which
should be fixed in the same change rather than deferred.

No ExecPlan needed — example files and a test, no runtime behaviour and no
schema.

## Acceptance Criteria

- Copying `apps/landing/.env.local.example` to `.env.local` and starting the app
  renders a real domain suffix on `/subscribe` step 2.
- `packages/config/env-examples.test.js` covers every app with an example pair,
  and fails if one of them omits a variable the other defines.
- The test names the app in its failure message, so a future gap says which one.
