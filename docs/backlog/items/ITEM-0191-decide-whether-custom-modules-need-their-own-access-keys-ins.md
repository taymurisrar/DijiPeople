# ITEM-0191 — Decide whether custom modules need their own access keys instead of the shared custom-records privilege

## Summary

Every published custom module is authorised through one shared entity,
`custom-records`, in both permission systems. A role that may read custom
records may read every custom module in the tenant; there is no way to grant
"QA Assets" to one team and "Vehicles" to another. The Architect accepted the
shared privilege for TASK-0031. Whether tenants need per-module access is a
product decision.

## Why It Matters

Tenants build custom modules for different departments. If some modules hold
sensitive data, a single privilege over all of them either over-exposes records
or forces administrators to withhold custom modules entirely. Per-module keys
change the permission model, seeds and the role editor, so the choice should be
made before tenants depend on the shared behaviour.

## Evidence

- `services/api/src/modules/data/custom-module-runtime.controller.ts` and
  `services/api/src/modules/data/data.controller.ts` declare `custom-records` in
  both permission systems.
- `services/api/src/modules/auth/auth-access.service.ts` derives the legacy
  `custom-records.*` keys from matrix privileges.
- `docs/tasks/TASK-0031-streams/WP-02-report.md`, "Permission model".

## Proposed Approach

Owner to choose:

1. Keep the shared `custom-records` privilege (current behaviour; row-level
   scope still applies).
2. Add a per-module privilege derived from the module key, with the shared
   privilege as the default grant.

Option 2 needs an ADR and an ExecPlan (permission registration, matrix, seeds,
role editor).

## Acceptance Criteria

- The owner's choice is recorded as an ADR.
- If option 2 is chosen, a follow-up item carries the implementation.
