# ITEM-0116 — 53 bug fixes are regression-covered but have never been QA-retested

## Summary

**53 of the 281 bug records sit at `Status: FIXED`.** Every one of them has a
`RegressionId`, a populated `Resolution` and a `ResolvedAt` date. None has been
re-executed by a QA run against a running application.

That is why the backlog reports ~79 open records while only 3 are `OPEN`: `FIXED`
buckets as open by design, because a fix nobody retested is not finished. The
count is honest — but the debt behind it has never been named as a single piece
of work, so it accumulates silently and no one schedules it.

## Why this is not just a status flip

Moving these to `VERIFIED` without running anything would be **fabricating
verification**, which is worse than the current state: it converts a known gap
into a false assurance. The records themselves say so plainly. Sampled retest
sections read:

- "Not retested against production. Covered by unit tests over the real helper."
- "Awaiting retest, which must run with `entitlementEnforcement` set to ON."
- "The URL half is verified. The owner rebuilt and reinstalled the agent…"
- "Retested by unit coverage, not in a browser."

So the distinction being drawn is real: **unit and regression cover is not the
same as re-executing the scenario.** Several explicitly cannot be retested
without something external — a live Stripe, a production duplicate check, a
feature flag switched on.

## What was already corrected

Three records — [[BUG-1950]], [[BUG-1951]], [[BUG-1986]] — carried
"Not retested — not yet fixed" in QA Retest while their own `Status`,
`ResolvedAt` and `Resolution` all said the fix had landed. That sentence was left
over from before the fix and contradicted the record it sat in. Corrected
2026-08-30 to state what is true: fixed, regression-covered, not retested. Their
statuses were **not** changed.

## Proposed Resolution

Not one campaign. The 53 split into three populations that need different things:

1. **Retestable now, no external dependency.** The majority. A QA run against the
   demo tenant with `npm run qa:select` on the affected modules closes these.
2. **Blocked on an external or a flag** — the live-Stripe cases, the production
   duplicate check for [[BUG-0084]], the entitlement flag for [[BUG-1952]]. These
   need the dependency recorded on the record and should arguably move to
   `BLOCKED` rather than sitting in `FIXED`.
3. **Genuinely covered by a regression and not worth a browser pass.** Where the
   record says so explicitly, the honest move is a decision that the regression
   *is* the verification — recorded as such, not left ambiguous.

Sorting them into those three is the first step and is cheap; running (1) is the
bulk of the work.

## Acceptance Criteria

- Every `FIXED` record is either retested and `VERIFIED`, moved to `BLOCKED` with
  its dependency named, or carries an explicit decision that its regression is
  the verification.
- No record's `QA Retest` section contradicts its own `Status` or `Resolution`.
- The open count reflects work genuinely outstanding rather than unretested work.
