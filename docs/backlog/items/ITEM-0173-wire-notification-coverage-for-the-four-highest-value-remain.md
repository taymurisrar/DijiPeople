# ITEM-0173 — Wire notification coverage for the four highest-value remaining silent modules

## Summary

ITEM-0170 ranked eleven silent tenant modules by customer-visible expectation
and found `support-cases` was actually a latent bug (a real trigger with a
missing catalog entry, fixed directly — see BUG-3200-adjacent
`EXECPLAN-0038`), not new wiring. The four modules ranked above the
"can follow or decline" tier still have zero notification wiring — no catalog
entry and no trigger — and were not implemented in the SESSION-0103 pass that
created this item, purely for lack of remaining session time, not because
they are low value. This item exists so the next pass on notification
coverage starts from a ranked, evidenced list instead of re-surveying.

## Why It Matters

Each of these is a workflow this product's own domain vocabulary implies
should notify somebody, and currently notifies nobody:

- **Document/policy acknowledgement due** — an employee who has not
  acknowledged a required policy is invisible until someone manually checks.
- **Contract renewal or expiry** — a contract lapsing with no warning is a
  commercial risk, not just a UX gap.
- **Recruitment stage change** — a candidate advancing with no signal to the
  hiring manager stalls a hiring pipeline silently.
- **Business trip approved** — the traveller and their manager learn the
  outcome only by checking back.

## Evidence

Confirmed by grepping each module for any reference to the notifications
service, orchestrator or catalog and finding none, at commit `f5f43805`:

- `services/api/src/modules/documents/` — no `notificationsService` /
  `emailService` reference.
- `services/api/src/modules/contracts/` — none.
- `services/api/src/modules/recruitment/` — none.
- `services/api/src/modules/business-trips/` — none.

`EXECPLAN-0038` covers the ranking methodology and the one candidate that
was fixed instead (`SUPPORT_CASE_UPDATE`, a broken existing trigger, not new
wiring).

## Proposed Approach

Needs its own ExecPlan under `PLANS.md` per module (or one covering all four,
sequenced), because each is a genuine cross-module change: a new catalog
entry, a new `NotificationTemplate`/`EmailTemplate`, a real trigger call site
inside that module's own service at the state transition in question, and —
per `ADR-0009` — a decision for each on whether it needs a `NotificationRule`
row (in-app) as well as an email template. Reuse the existing path
(`NotificationsService.emit()` or `EmailService.sendTemplateEmail()` per
ADR-0009's guidance in `services/api/AGENTS.md`), never a direct mailer call.

## Acceptance Criteria

- Each of the four events has a catalog entry, a real trigger, a written
  (non-generated) description, and a template.
- No new event bypasses the notifications module.
- A test asserting the trigger actually fires (not only that the catalog
  entry exists) — closing the same "declared but unwired" shape ITEM-0169
  found in the existing catalog.

## Dependencies

Blocked by nothing technical; sequenced after `ITEM-0170`/`ADR-0009` because
the model-ownership decision (which of `NotificationRule` /
`NotificationPreference` gates each new event) needs to be applied
consistently.
