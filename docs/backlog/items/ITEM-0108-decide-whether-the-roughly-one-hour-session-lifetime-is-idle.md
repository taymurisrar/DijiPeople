# ITEM-0108 — Decide whether the roughly one-hour session lifetime is idle or absolute

## Summary

Both the tenant workspace and the platform admin console returned the signed-in
user to the login screen roughly 60 minutes after sign-in, during a session that
was making requests throughout. That may be exactly the intended timeout. It is
recorded as a decision rather than a defect because the run did not establish
whether the limit is idle-based or absolute, and the answer changes whether the
behaviour is acceptable.

## Why It Matters

If the limit is **idle-based**, an hour is short for an HR product but defensible,
and the only question is the value.

If it is **absolute**, a user is signed out mid-task regardless of activity — and
during this run it did interrupt an in-progress form. On a product where people
fill in long forms (an employee record, a payroll run, a leave policy), an
absolute one-hour cap means losing unsaved work on a predictable schedule, with
no warning. That is a product decision nobody has visibly made, and it is
cheaper to make it deliberately than to receive it as a support ticket.

Either way, the current behaviour gives no warning before it happens and no
recovery of the form state after it.

## Evidence

Observed 2026-08-29 against production, on both surfaces, in a session that was
issuing requests continuously:

- Tenant workspace: redirected to the login screen with `?reason=session-expired`.
- Platform admin console: the same, with the API returning
  `"Session is no longer active."`
- Elapsed time from sign-in: approximately 60 minutes on both.

The measurement is approximate — the run was not instrumented for it — and
whether the clock is idle or absolute was not determined, because the session was
never idle long enough to distinguish the two.

No configuration value was located. Where the lifetime is set in
`services/api/src/modules/auth` and whether it is tenant-configurable are both
unestablished.

## Proposed Approach

1. Read the actual configuration: the access token lifetime, the refresh
   behaviour, the session row's expiry semantics, and whether any of them is
   tenant-configurable.
2. State which of idle or absolute is in force. If it is absolute, decide whether
   that is intended for an HR product.
3. Decide the value, and whether it should differ between the tenant workspace
   and the platform admin console — the second holds cross-tenant access and has
   a stronger argument for a short cap.
4. Independently of the value, consider warning before expiry and preserving form
   state across a re-authentication. Those are what make any timeout tolerable,
   and they are worth more than the number.

## Acceptance Criteria

- The session lifetime and its semantics (idle versus absolute) are documented.
- A deliberate value is recorded for each surface, with the reasoning.
- If the current behaviour is kept, the decision says so explicitly rather than
  leaving it as an accident of configuration.
