# ITEM-0178 — Recruitment job opening edit page is bespoke while its detail page already uses the shared record shell

## Summary

`recruitment/jobs/[jobId]/page.tsx` (the job opening detail view) already
renders through `StandardModuleRecordPage`. Its sibling edit route,
`recruitment/jobs/[jobId]/edit/page.tsx`, is fully bespoke — a hand-rolled
header section and a standalone `JobOpeningForm` component, with no
reference to the shared shell at all. One module, two different layout
systems depending on which mode you're in.

## Why It Matters

A user editing a job opening sees a different action bar, a different
header, and a different tab structure (none) than the one they were just
reading. It is the same class of inconsistency ITEM-0167 named for detail
pages, just on the edit side, which that record's evidence pass and this
session's conformance check did not enumerate — edit-mode routes were
explicitly out of scope for both. Left alone, it is exactly the kind of
drift `docs/architecture/record-page-layout-contract.md` exists to catch
before it spreads to other modules' edit routes too.

## Evidence

- `apps/web/app/(authenticated)/recruitment/jobs/[jobId]/page.tsx:2` —
  imports and renders `StandardModuleRecordPage`.
- `apps/web/app/(authenticated)/recruitment/jobs/[jobId]/edit/page.tsx` —
  no import of `ModuleRecordPage`, `StandardModuleRecordPage`, or
  `EmployeeRuntimeFormWrapper`; renders a bespoke header section and
  `JobOpeningForm` (`../../../_components/job-opening-form`) directly.
- Found while writing
  `apps/web/app/(authenticated)/_components/record-page-shell.conformance.spec.ts`
  for [[ITEM-0167]] / `EXECPLAN-0044`, which scopes out `/edit/` routes
  entirely (see that check's own comment) — so this inconsistency exists
  outside what that check enforces today.

## Proposed Approach

Likely no ExecPlan: this is a single-module, single-page layout swap with
no permission or data-shape change, similar in size to ITEM-0165/ITEM-0166.
Should be assessed alongside whether `ModuleRecordPage` in `edit` mode can
host `JobOpeningForm`'s fields as form sections directly, or whether the
edit-mode-vs-detail-mode conformance question is better answered by
extending `EXECPLAN-0044`'s conformance check to cover `/edit/` routes
tenant-wide first (which would likely surface more than just this one page)
before fixing any single instance. State a direction once that scoping
question is answered, rather than assuming this document already knows it.

## Acceptance Criteria

- `recruitment/jobs/[jobId]/edit` renders through the same shell as
  `recruitment/jobs/[jobId]`, or a stated structural reason is recorded for
  why it should not.
- Every field and validation rule `JobOpeningForm` currently enforces is
  preserved.
