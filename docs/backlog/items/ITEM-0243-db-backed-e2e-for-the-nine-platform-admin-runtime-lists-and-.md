# ITEM-0243 — DB-backed e2e for the nine platform-admin runtime lists and removal of the in-memory fallback path (BUG-3175 follow-up)

## Summary

BUG-3175 moved paging, search and sort of nine platform-admin runtime lists into Prisma queries, but the only automated proof is a mocked spec that asserts the Prisma arguments, not SQL results. This item adds a DB-backed e2e for the nine lists (tenants, subscriptions, plans, invoices, payments, partner-inquiries, partner-onboarding, commissions, contract-templates) and then removes the in-memory fallback path once the e2e shows every filter the admin UI sends is expressible in SQL.

## Why It Matters

Until it exists, a wrong `where` or `orderBy` that the mocks cannot see (a column rename, a relation path, a case-insensitive search that misses) ships silently. The retained fallback also keeps the full-table read alive for any request carrying an unsupported filter.

## Evidence

`services/api/src/modules/platform-runtime/runtime-db-query.ts` and `runtime-db-query.spec.ts`; BUG-3175; QA-PLATFORM-072; commit 2088ec4f.

## Proposed Approach

Add an e2e under `services/api/test/` against the ephemeral Postgres recipe: seed a few rows per module, assert page, total, search, sort and each supported filter against real results. Then log which filters hit the fallback (numeric, date equality, invalid enum) and either express them in SQL or reject them, and stop using the in-memory pagination for these lists. No ExecPlan needed unless the fallback removal changes the API contract. Consider a trigram index only if ILIKE over the listed columns measures slow.

## Acceptance Criteria

- An e2e runs all nine lists against a real database and passes in CI.
- Search, sort and every supported filter are asserted on returned rows, not on call arguments.
- The fallback path is removed or each remaining use is documented with a reason.
