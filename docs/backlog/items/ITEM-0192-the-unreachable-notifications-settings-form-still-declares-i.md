# ITEM-0192 — The unreachable notifications settings form still declares In-app, Browser Push and Digest switches

## Summary

The settings-runtime page configuration still declares a notifications form with
"Enable in-app notifications", "Enable browser notifications" and "Enable digest
notifications" switches. No screen reaches that form, and none of the three
settings has a consumer on the server. ITEM-0180 replaced the page that showed
Browser Push and Digests as active; this declaration is what is left.

## Why It Matters

Dead configuration with live-sounding labels is how the Browser Push and Digests
tiles came back last time. If anything wires the form up again, administrators
see switches that do nothing.

## Evidence

- `apps/web/app/(authenticated)/settings/_lib/settings-page-config.ts` —
  `notificationSettingsSections`, lines 1966-2000 at `88f33c6e`.
- `services/api/src/modules/tenant-settings/tenant-settings-resolver.service.ts`
  — `inAppEnabled`, `browserPushEnabled` and `digestEnabled` are returned but
  read by nothing else; only `emailEnabled` has a consumer.
- `docs/tasks/TASK-0031-streams/WP-05-report.md`, "Residual risks and findings
  for the orchestrator".

## Proposed Approach

Remove the three unconsumed switches (or the whole unreachable section) from
`settings-page-config.ts`, keeping the "Send email" setting the events page
uses. Leave the stored settings keys alone unless a separate decision retires
them. No ExecPlan needed.

## Acceptance Criteria

- `settings-page-config.ts` declares no In-app, Browser Push or Digest switch.
- The notification events page's "Send email" switch still reads and writes
  `notifications.emailEnabled`.
- Web tests and typecheck pass.

## Dependencies

None.
