# ITEM-0177 — The recruitment draft form's Reporting manager lookup still filters one page in the browser

## Summary

[[BUG-3376]] found that a runtime lookup loaded one unpaged server page and
filtered it in the browser, so every record past the server's default page size
was unselectable and typing a missing colleague's name produced "No matching
records found" — which reads as "this person does not exist". That is fixed for
every lookup rendered by the metadata runtime.

One lookup is not rendered by it. The **Reporting manager** field on the
recruitment draft form is a bespoke page that takes a plain array as a server
component prop and filters it client-side. It has the same defect, untouched.


## Why It Matters

The defect is silent, and that is the whole of its severity. Nothing errors,
nothing logs, and the control confidently reports that a person does not exist.
A recruiter assigning a reporting manager to a draft either picks the wrong
person from the twenty they can see, or concludes the manager has not been
created yet and makes a duplicate.

It is worse here than in the general case it was found in, because a reporting
manager is by definition a senior person, and seniority does not correlate with
being in the first page of an unsorted employee query. The people most likely to
be chosen for this field are the ones least likely to be reachable.

It also now stands alone as the one place the lookup contract is not honoured.
A contract with one documented exception is a contract; a contract with one
undocumented exception is a suggestion.


## Evidence

- `apps/web/app/(authenticated)/recruitment/_components/employee-draft-form.tsx`
  — the "Reporting manager" `LookupField`, given a plain array from a server
  component prop and filtered in the browser.
- [[BUG-3376]]'s Resolution names this file as a known remaining gap and
  explains why closing it was not required to close that bug: the record's own
  reproduction, Project to Project Manager, does not route through it.
- [[ITEM-0172]] wired the fix into the metadata runtime's single call site. This
  form is not one of its call sites, so that item did not reach it either.
- `docs/architecture/lookup-control-contract.md` records this as the one place
  the contract is not yet fully conformed to.


## Proposed Approach

No ExecPlan needed. The contract, the server-side search path, the page-size
convention, the selection pinning and the truncation affordance all exist and
are in use; this is conforming one bespoke form to them.

Either pass the search through to the same adapter path the runtime uses, or —
better, if the form has no other reason to be bespoke — render this field
through the metadata runtime so it inherits the behaviour rather than copying
it. Look at why the form is bespoke before choosing; a page that is bespoke for
a reason unrelated to its lookups should keep its shape and just adopt the
search path.

Whichever is chosen, remove the exception from
`docs/architecture/lookup-control-contract.md` when it lands, so the contract
stops carrying a permanent asterisk.


## Acceptance Criteria

- On a tenant with more than one server page of employees, typing the exact name
  of an employee outside the first page into **Reporting manager** finds and
  selects them.
- The request issued while typing carries the search term.
- A truncated result set says so in the control.
- Opening a draft whose reporting manager lies outside the first page still
  shows that person's name, not a raw id.
- `lookup-control-contract.md` no longer lists an unconformed surface, or lists
  a different one with its own reason.
