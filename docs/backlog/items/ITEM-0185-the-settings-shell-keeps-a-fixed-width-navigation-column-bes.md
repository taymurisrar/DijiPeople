# ITEM-0185 — The settings shell keeps a fixed-width navigation column beside the content at phone width

## Summary

Every tenant settings page renders inside a shared layout whose settings
navigation is a fixed 260px column in a row beside the page content. The row
never stacks and the navigation never collapses on a small screen. At 400px the
content is squeezed beside the navigation, or pushed below it and scrolls
sideways. The walkthrough saw notification settings content start about 900px
down the page (finding N10).

## Why It Matters

Settings are where an administrator acts on the demo's findings. Fixing each
settings page's own layout (as ITEM-0180 did for the events page) cannot help
while the shell around it does not fit a phone, so every settings page stays
unusable at phone width.

## Evidence

- `apps/web/app/components/settings/settings-layout.tsx` — lines 26-31 at
  `88f33c6e`: a `flex` row with a `shrink-0` aside and no small-screen stacking.
- `apps/web/app/(authenticated)/settings/_components/settings-shell.tsx` — lines
  63-67 at `88f33c6e`: the aside is `w-[260px]` (collapsed `w-[56px]`).
- `docs/tasks/TASK-0031-streams/WP-05-report.md`, "Residual risks and findings
  for the orchestrator".
- Walkthrough finding N10 (ITEM-0180 Evidence).

## Proposed Approach

Make the shared settings layout responsive once: below the tablet breakpoint,
stack the navigation above the content as a compact control or collapse it
behind a menu, and let the content column take the full width. Use the runtime
shells' existing breakpoints. No page-level workaround, and no explanatory
text. No ExecPlan needed.

## Acceptance Criteria

- At 400px, every settings page's document width equals the viewport width.
- At 400px, the page content starts within the first viewport height.
- At 820px and 1440px the navigation behaves as it does today.
- Navigation remains keyboard-operable and named at every width.
