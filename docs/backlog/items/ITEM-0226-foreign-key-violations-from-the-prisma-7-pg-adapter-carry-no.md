# ITEM-0226 — Foreign-key violations from the Prisma 7 pg adapter carry no P2003 code and surface as generic errors

## Summary

With Prisma 7 and `@prisma/adapter-pg`, a real foreign-key violation arrives as
a `DriverAdapterError` whose `code` is `undefined`. It is not a
`PrismaClientKnownRequestError` with code `P2003`. `HttpExceptionFilter` maps
only the latter to `DATABASE_CONSTRAINT_FAILED`. Every other delete or update
that hits a foreign key therefore returns a generic `SYSTEM_UNEXPECTED_ERROR`
500, which tells the operator nothing.

## Why It Matters

- A blocked delete looks like a server crash.
- Monitoring records the failure as an unexpected error rather than a
  constraint refusal.
- This is the likely source of the old "500 Unexpected error" on partner
  delete.

## Evidence

- TASK-0037 WP-07 confirmed this against a real database on 2026-10-07: a
  foreign-key violation came back with `code: undefined`.
- The partner path now detects it by message in `isForeignKeyViolation`
  (`services/api/src/common/deletion/record-dependencies.ts`).
- The global filter only maps the Prisma-coded error
  (`http-exception.filter.ts`, around line 279).

## Proposed Approach

Move the detection into `HttpExceptionFilter`: classify a `DriverAdapterError`
with a foreign-key message (Postgres SQLSTATE 23503 when present) as
`DATABASE_CONSTRAINT_FAILED` 409. Add a DB-backed spec. No ExecPlan is needed.

## Acceptance Criteria

- A foreign-key violation from any module returns 409
  `DATABASE_CONSTRAINT_FAILED`, not 500.
- A spec reproduces this against a real database.
