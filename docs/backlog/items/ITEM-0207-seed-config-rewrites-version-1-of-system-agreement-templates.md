# ITEM-0207 — seed:config rewrites version 1 of system agreement templates in place instead of publishing a new version

## Summary

`seed:config` refreshes version 1 of each system agreement template in place.
TASK-0032 changed those templates (signature blocks, platform signature line
markers), so the next `seed:config` against production — which the pre-deploy command
currently runs — rewrites v1 rather than publishing v2.

## Why It Matters

Agreements already created from v1 keep their own frozen versions, so no
signed document changes. But the template's history no longer shows what v1
said when earlier agreements were drafted from it, and a reviewer comparing an
old draft to "v1" sees different text.

## Evidence

TASK-0032 WP-11 report, UNRESOLVED
(`docs/tasks/TASK-0032-streams/t0032-wp-11-report.md`); BUG-3582.

## Proposed Approach

Owner decision: keep in-place refresh for system templates (simple, current
behaviour), or have `seed:config` publish a new version when the seeded content
differs from the latest version.

## Acceptance Criteria

The decision is recorded as an ADR and `seed:config` follows it.

## Dependencies

None.

## Related Items

[[BUG-3582]], [[TASK-0032]], [[contracts-and-agreements]]

## Resolution

Owner decision 2026-09-26: publish new versions (ADR-0023). Implemented on
`agent/item-0207-template-versions`: `seed:config` never rewrites an existing
template version. `planSystemContractTemplateWrite` creates version 1 when a
template has none, writes nothing when the latest version already carries the
seeded text, publishes the next version (unpublishing the previous one, as an
operator edit does) when the latest is the seed's own and differs, and keeps an
operator-authored latest version in place. Covered by
`services/api/src/modules/contracts/seed-config-template-versions.spec.ts`, which
fails if the operator-version rule is removed. Production's version 1 already
matches the seeded text, so the first deploy writes nothing.
