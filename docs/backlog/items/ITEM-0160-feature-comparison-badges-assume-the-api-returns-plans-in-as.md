# ITEM-0160 — Feature comparison badges assume the API returns plans in ascending tier order

## Summary

`FeatureComparison` decides between "Available in higher plan" and "Not included"
by looking at the plans that come **after** the current one in the array it was
handed:

```tsx
const availableLater =
  !isIncluded &&
  plans.slice(planIndex + 1).some((laterPlan) => ...);
```

Nothing establishes that later in the array means higher in price. The ordering
comes from `getPublicPlans`, which sorts by `sortOrder` then `name` — an
administrative field, not a commercial one. Today it happens to be ascending, so
every badge reads correctly. Change a plan's `sortOrder`, add a fourth plan in
the wrong slot, or rename one such that the name tiebreak decides, and cells
silently invert: a feature that is included in a cheaper plan would be labelled
"Available in higher plan" in a more expensive one.

Two smaller couplings in the same function:

- `featuresByKey` keeps the **first** plan's copy of a feature's label,
  description and category. If two plans describe the same feature key
  differently, whichever plan sorts first wins, including for the category the
  row is filed under.
- The API returns a `featureCategories` array giving the canonical category order,
  and the component ignores it, re-deriving grouping from the first-seen feature's
  `categoryLabel`. Two sources for one ordering.

## Why It Matters

A silent inversion in a price comparison is the worst kind: it renders cleanly,
nothing throws, and the first person to notice is a customer who bought the wrong
plan. The cost of the fix is small and the cost of finding it in the wild is not.

## Evidence

`apps/web/app/(authenticated)/settings/billing/_components/billing-settings-client.tsx:676-687`
for the ordering assumption, lines 609-616 for `featuresByKey`, and lines 618-625
for the grouping reduce.

Plan ordering, `services/api/src/modules/billing/services/billing.service.ts:124`:

```ts
orderBy: [{ sortOrder: 'asc' }, { name: 'asc' }],
```

The unused canonical ordering, same file, lines 265-280 — `featureCategories`,
already sorted by `categoryOrder`.

## Proposed Approach

No ExecPlan needed.

1. Order the comparison columns by something commercial — the plan's monthly base
   price in the selected currency — or have the API state the tier rank
   explicitly rather than leaving it implied by array position.
2. Take the feature label, description and category from the platform
   `featureCatalog` the API already returns, not from the first plan that
   mentions the key.
3. Group by the returned `featureCategories` order.

## Acceptance Criteria

- Reordering `Plan.sortOrder` does not change which cells read "Available in
  higher plan".
- A feature's row is filed under the catalog's category regardless of which plan
  includes it.
