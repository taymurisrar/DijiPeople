# ITEM-0188 — Custom-module screens ignore the module's published action bar

## Summary

[[BUG-3494]]'s expected behaviour, per ADR-0016, is that a published custom
module's action bar defines the commands on its screens. The runtime shipped in
TASK-0031 uses the standard command set instead (New, Edit, Delete, Refresh,
Back, Save), gated by capabilities. An action bar an administrator publishes
(for example `dd_qaRecordBar` on the demo tenant) has no effect.

## Why It Matters

Action bars are a Customization component an administrator can create, validate
and publish. A published component with no runtime effect is the same
"customization with no end-user outcome" BUG-3494 was filed for, one level down.

## Evidence

- `apps/web/lib/runtime/custom-modules/custom-module-runtime.ts` builds the
  runtime spec without reading published action bars.
- `docs/tasks/TASK-0031-streams/WP-02-report.md`, "Residual risks and open
  items": "Published action bar not consumed."

## Proposed Approach

Include published action bars in the custom-module definition returned by
`GET /metadata/custom-modules/:moduleKey`, map their rows onto registered runtime
commands, and fall back to the standard set when a module has none. Unknown
commands are refused at publish (REG-484 already requires a non-empty command).
No ExecPlan needed unless a command registry has to be introduced on the API.

## Acceptance Criteria

- A custom module with a published detail action bar shows exactly those
  commands, in that order, on its record screen.
- A module with no published action bar shows the standard command set.
- A row naming a command the runtime does not know is not rendered and does not
  break the page.
