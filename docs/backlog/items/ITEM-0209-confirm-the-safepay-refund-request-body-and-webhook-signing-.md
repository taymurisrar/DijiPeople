# ITEM-0209 — Confirm the Safepay refund request body and webhook signing input against a live sandbox run

## Summary

Two Safepay details could not be settled from documentation alone. The refund body is sent as `{ payload: { currency, amount } }` (Safepay's documented example) though its SDK is ambiguous, and the webhook HMAC is accepted over either the raw body or its re-serialised JSON because Safepay's docs, PHP SDK and WooCommerce plugin disagree on the signing input.

## Why It Matters

A wrong refund body means operator refunds fail (they are recorded as FAILED, never assumed successful). A wrong signing input means every real webhook is refused with 400 and settlement falls back to the status poll and the sweeper — slower, but no money is lost.

## Evidence

`services/api/src/modules/billing/providers/safepay.gateway.ts` (`refund`, `parseWebhook`); `docs/billing/safepay.md` "Known limitations". Adapter behaviour is pinned by `safepay.gateway.spec.ts`.

## Proposed Approach

With sandbox credentials: run one checkout with test card 4456 5300 0000 1005, capture the delivered webhook and confirm which candidate verified; refund it from the admin Safepay tab and read the returned tracker state. Remove the losing candidate from `parseWebhook`.

## Acceptance Criteria

- A real sandbox `payment.succeeded` verifies and settles the payment.
- A sandbox refund from the admin tab returns PROCESSED and marks the payment REFUNDED.
- `parseWebhook` accepts exactly the one confirmed signing input.

## Dependencies

Safepay sandbox account and keys (owner).
