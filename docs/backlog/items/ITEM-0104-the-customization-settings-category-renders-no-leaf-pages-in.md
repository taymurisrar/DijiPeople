# ITEM-0104 — The customization settings category renders no leaf pages in server HTML

**DUPLICATE of [[BUG-3374]].** Re-checked 2026-09-12 while diagnosing BUG-3374:
the two questions this item left open — "does the client-only render leaves
after hydration" versus "is the category genuinely empty" — are both the wrong
question. `/settings/customization` never gets far enough to render either
answer. `requireCustomizationAccess` in
`apps/web/app/(authenticated)/settings/customization/layout.tsx` gated on role
membership (`GLOBAL_ADMIN` / `SYSTEM_CUSTOMIZER`) while `customization`'s own
navigation entries and every page beneath it gate on the `customization.read`
permission, and a server-side `redirect()` fired before any leaf link — server
or client-rendered — ever reached the response. A crawler account without one
of those two roles gets the same silent redirect the tenant owner did when
BUG-3374 was reproduced, which is indistinguishable from "zero leaf pages" to
anything reading the SSR HTML for links. See BUG-3374 for the mechanism, the
reproduction and the fix.

## Summary

An inventory of the tenant settings surface counted 11 categories and 100 leaf
pages. Ten categories contribute between 3 and 18 leaf pages each; `customization`
contributes **zero**. `/settings/customization` yielded no leaf links in the
server-rendered HTML.

This is filed as an observation, not a defect: it is not established whether the
category renders its children client-side only — in which case the finding is an
SSR and accessibility observation — or is genuinely empty, in which case a
settings category with no content is being offered to tenants. Either answer is
useful; neither has been confirmed.

## Why It Matters

If the page is empty, tenants are offered a settings category that leads nowhere,
which costs navigation time and support questions. If it renders only on the
client, the links are invisible to anything that does not run JavaScript —
including crawlers, some assistive tooling, and any check built on the server HTML
— and that is a discrepancy worth knowing about before someone builds such a
check.

The cost of leaving it unanswered is small but real: the settings inventory this
came from is the kind of number that ends up in a document, and a zero nobody
explained will be re-derived by the next person.

## Evidence

Measured 2026-08-29 against `https://dijipeople-demo.ws.dijipeople.com`, tenant
`DijiPeople Demo`, production API commit `949f461c`:

```
general-setup 11, regional 12, security-access 10, people 18, integrations 9,
payroll 18, approvals 8, notifications 5, customization 0(!), appearance 3,
audit-compliance 6
```

`/settings/customization` returned no leaf links in the SSR HTML. The category
itself is present in the settings navigation.

Not checked: whether the page renders leaf links after hydration; what
`apps/web/app/(authenticated)/settings/_lib/settings-navigation.ts` declares for
this category; whether the leaves exist and are filtered by permission or
entitlement for this tenant.

## Proposed Approach

Open `/settings/customization` in a browser with JavaScript enabled and compare
with the server HTML, then read the category's declaration in
`settings-navigation.ts`. That settles which of the two cases this is in a few
minutes, and the answer determines whether anything further is needed.

No ExecPlan required.

## Acceptance Criteria

- It is recorded whether `customization` has leaf pages at all.
- If it does, the reason they are absent from the server HTML is stated.
- If it does not, a decision is made about whether the category should be offered.
