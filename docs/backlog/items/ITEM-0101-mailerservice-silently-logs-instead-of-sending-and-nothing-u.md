# ITEM-0101 — MailerService silently logs instead of sending, and nothing uses it

## Summary

`common/mailer/MailerService` offers `sendPasswordResetLink` and
`sendAccountActivationLink`, and both funnel into a private `deliverLink` whose
only behaviour is to write a log line. Every delivery mode other than `log`
falls through to `log` with a warning, so there is no configuration in which it
sends an email. It returns `{ accepted: true }` either way.

It is also **unused**. It is provided and exported by `MailerModule`, and no
other module injects it — password reset actually travels through the
`notifications` module as the `AUTH_PASSWORD_RESET` event, which is the route
`AGENTS.md` documents.

So there is no live defect. What there is, is a trap.

## Why It Matters

The cost is a future outage that looks like nothing at all.

The service is named for the job, exported, has exactly the two methods someone
would reach for, and returns `accepted: true`. The first person who needs to
send a password reset from a new surface will inject it, see `accepted: true`
in the response and a plausible line in the logs, and ship. No email will ever
arrive, and nothing will report a failure — the same silent-success shape as
[[BUG-1304]] and [[BUG-0904]].

`MAIL_DELIVERY_MODE=log` is set on the production service today, which makes it
look configured and intentional rather than inert.

This also cost real time in the 2026-08-25 landing QA run: `MAIL_DELIVERY_MODE=log`
on the live service was read as "production sends no email", which would have
been a go-live blocker. Establishing that it was harmless meant tracing the
onboarding verification code to `platform-communications` and confirming
production's SMTP settings separately.

## Evidence

[`services/api/src/common/mailer/mailer.service.ts`](../../../services/api/src/common/mailer/mailer.service.ts):

```ts
const deliveryMode = this.configService.get('MAIL_DELIVERY_MODE') ?? 'log';

if (deliveryMode === 'log') {
  this.logger.log(`${input.subject} email queued for ${input.to}: ${input.link}`);
  return { deliveryMode: 'log', accepted: true, link: input.link };
}

this.logger.warn(`Unsupported mail delivery mode "${deliveryMode}". Falling back to log.`);
// …logs and returns accepted: true again
```

Consumers, searched across `services/api/src`: only `mailer.module.ts`, which
provides and exports it. Nothing injects it.

The real path, for contrast:
`notification-events.catalog.ts` defines `AUTH_PASSWORD_RESET`, and production
platform email settings are `enabled: true`, `providerType: SMTP`,
`fromAddress: notifications@dijipeople.com` — configured and live.

## Proposed Approach

Delete it. It is dead code whose only effect is to mislead, and the working
route already exists and is documented.

If it is being kept deliberately as a seam for a future provider, then it should
fail rather than flatter: throw on an unrecognised `MAIL_DELIVERY_MODE` instead
of falling back, and return `accepted: false` for the log mode, so a caller
cannot mistake a log line for a delivery. A header comment naming
`notifications` as the real route would stop the next reader reaching for it.

No ExecPlan — a deletion, or a few lines and a comment.

## Acceptance Criteria

- Either the service is gone, or it cannot return `accepted: true` without
  having sent something.
- An unrecognised delivery mode is an error, not a silent downgrade.
- If it stays, its header names `notifications` as the route to use instead.
