# ITEM-0174 — Unify the notification catalog on one key convention (dotted form)

> **Architect triage, 2026-09-12 — `DEFER`.** Renaming roughly thirty catalog keys touches auth, claims, loans, timesheets,
> payroll, payslips and super-admin, several of which are owned by other
> sessions right now, and every rename needs a preference migration so existing
> tenant opt-ins are not orphaned. The two genuinely dead duplicate pairs were
> already collapsed. What is left is consistency rather than correctness, and
> it is not worth taking a migration risk across seven modules to get it.

## Summary

ITEM-0169 asked for the whole catalog to move onto one key convention (the
dotted form — `leave.request.approved.employee` rather than
`LEAVE_APPROVED`). SESSION-0103 collapsed the two genuinely dead duplicate
pairs (`LEAVE_APPROVED`/`LEAVE_APPROVAL_REQUEST`, retired with a preference
migration) but deliberately did not rename the roughly thirty remaining
SCREAMING_SNAKE_CASE codes still in real use — `AUTH_*`, `PAYROLL_*`,
`PAYMENT_BATCH_*`, `JOURNAL_*`, `TIMESHEET_*`, `CLAIM_*`, `LOAN_*`,
`PAYSLIP_*`, `BILLING_INVOICE_ISSUED`, `REPORT_SCHEDULE_DELIVERY`. This item
tracks that remaining rename.

## Why It Matters

Two conventions side by side still reads as unfinished, which is the
complaint ITEM-0169 exists to close, and a genuine full fix eventually
removes the last reason this catalog needs a "which style is this" lookup.

## Evidence

Renaming these codes means changing the literal string in every call site
that passes it as `eventKey`/`eventCode`, not just the catalog:
`auth.service.ts` (x2), `user-invitations.service.ts`,
`claims.service.ts` (x3), `loans.service.ts` (x3),
`timesheet-workflow.service.ts` (x5), `payroll-operations.service.ts` and
`payroll-journal.service.ts` (15 events), `payslips.service.ts`,
`report-scheduler.worker.ts`, `super-admin.service.ts`, plus the matching
`DEFAULT_NOTIFICATION_RULES` eventKey entries in `seed-config.ts` and any
`EmailTemplate.eventCode` rows already stored for these codes in a deployed
database.

## Proposed Approach

Deliberately **not** attempted in SESSION-0103: `auth.service.ts` and
`employee-profiles.service.ts` (which also references an eventCode) were
explicitly out of that session's scope as owned by concurrent agents, and
`claims`/`loans`/`timesheets`/`payroll`/`payslips`/`super-admin` are five
more modules a rename would touch beyond the `notifications` module boundary
— real cross-module blast radius during a period when other sessions may be
concurrently editing those same files. Needs its own ExecPlan under
`PLANS.md` (Large refactor — "anything touching more than roughly ten
files"), run when no concurrent session holds a lease on the affected
modules (`node scripts/session.mjs check --paths ...` first), following the
same alias-and-migrate pattern this session used for the two collapsed
duplicates: add the new dotted code to the catalog, alias the old code via
`RETIRED_EVENT_ALIASES`, migrate `NotificationPreference` rows, then update
each call site's string literal in the same commit as its catalog entry.

## Acceptance Criteria

- Every catalog key uses the dotted convention.
- Existing tenant `NotificationPreference` rows survive the migration
  (verified the same way `migrateRetiredEventPreferences` was verified this
  session).
- No call site is left passing the old SCREAMING_SNAKE_CASE string.

## Dependencies

Blocked by nothing technical beyond coordination with whichever sessions
concurrently own `auth`, `claims`, `loans`, `timesheets`, `payroll`,
`payslips` and `super-admin` at the time this is picked up.

exact-string equality, so a rename must update both together.
