# CI reliability

Evidence: the last 50 runs of `ci.yml` read through `gh` on 2026-11-03 (`node scripts/ci-doctor.mjs`), plus reproductions on Node 22.23.4 / npm 11.9.0. Numbers are measured; where a cause is a hypothesis it says so.

## Baseline

| | Runs | Success | Failure | Cancelled |
|---|---|---|---|---|
| All | 50 | 7 (14%) | 36 (72%) | 7 (14%) |
| `develop` / `main` | 7 | 7 | 0 | 0 |
| `agent/starter-golive-qa` | 25 | 0 | 18 | 7 |
| `dependabot/*` (9 branches) | 18 | 0 | 18 | 0 |

Trunk was green; every failure was a feature branch or a Dependabot branch. **That stopped being true on 2026-11-03: see "The advisory gate is red on `develop`" below.**

## Causes

### 1. Dependabot pull requests target `main` — confirmed, fixed
All nine open Dependabot PRs (#108, #115–#123) have base `main`. `main` is production and its last commit is 2026-10-13, so it predates the framework fixes and advisory dispositions that live on `develop`. Eight of nine fail *Framework validation* (simulations 26b/61/61b, stale dashboards) and the advisory gate for reasons unrelated to the bump. There was **no `dependabot.yml`**: the PRs came from the repository's security-updates setting with defaults. The same electron bump opened twice (#116 in `/apps/agent-desktop`, #117 at the root) because both directories were scanned although one root lockfile governs all workspaces.

*Fix:* `.github/dependabot.yml` — `target-branch: develop`, **one** npm entry at `/`, weekly, grouped (security updates together; minor+patch together), majors of the runtime stack ignored (planned work), 5-PR cap, GitHub-Actions entry monthly. A test (`governance.test.mjs`, CI-007) fails if a second npm entry appears or any entry targets another branch.
*Needs the owner:* the nine existing PRs keep base `main`. Close/recreate them against `develop` (or comment `@dependabot rebase` after changing the base). Not done here — they are not mine to modify.

### 2. `npm ci` EUSAGE on one Dependabot branch — confirmed, fixed
Run 40198343104 (`dependabot/…/apps/agent-desktop/electron-42.11.16`): `EBADENGINE required npm 11.x, current npm 10.9.9` then `EUSAGE` in 14 jobs. `actions/setup-node@v4` with `22.x` ships npm 10.9; the repo requires npm 11. A lockfile regenerated by a different npm then fails `npm ci`.

*Fix:* composite action `.github/actions/setup-npm` replaces the same five lines in 12 `ci.yml` jobs. It reads the node major from `engines.node` and the exact npm from `packageManager` (`npm@11.9.0`), installs that npm, **verifies both before installing dependencies**, then runs a clean `npm ci`. No version literal is repeated. `governance.test.mjs` (CI-006) fails if a job installs with a bare `npm ci`.
*Verified here:* clean `npm ci` on Node 22.23.4 + npm 11.9.0 — 1,608 packages, exit 0, 8 min.

### 3. `qrcode` "missing" — stale local modules, not the manifest
`qrcode@1.5.4` is declared in `services/api/package.json` and locked in `package-lock.json`. The earlier `Cannot find module 'qrcode'` came from the primary checkout's stale `node_modules` (it lacked the package) that my worktree had junctioned. After the clean install `node_modules/qrcode` exists and the API typechecks on the real toolchain with no errors.

### 4. Framework validation on `agent/starter-golive-qa` — NOT reproduced
Run 41472410252: `3 of 6528 checks` failed (simulations 26b, 61, 61b), plus a `DEVELOP_CONTAINS_MAIN could not be checked` warning and four `fatal: not a git repository` lines. **The failing SHA (`7fe24a7b`) is that branch's current tip, which is 0 commits behind `develop`** — so my earlier "stale branch" explanation was wrong for this branch. At that SHA `node scripts/validate-framework.mjs` **passes** locally (6,529 checks) in a full worktree and (6,528) in a `--depth 1` clone, on Windows with Node 22.23.4.

What is established: the three simulations spawn `backlog-review.mjs`/the steward view; the CI log shows git being run where there is no repository. What is not: why that happens only on the runner. *Mitigation applied:* the `validate` job now checks out full history (`fetch-depth: 0`), which also enables the `DEVELOP_CONTAINS_MAIN` ancestry check that was being silently skipped. *The real test is this PR's own Linux run* — if the three simulations pass there, the history hypothesis stands; if they fail, the log will show the reason and this section gets corrected.

### 5. E2E type error on the QA branch — owner's branch, not changed
`TS2551: 'QA_TENANT_C_SLUG' does not exist on type 'QaEnv'` (12 runs). The property is referenced by `e2e/golive/tests/21-desktop-agent-plan-matrix.spec.ts` and declared (by then) in `e2e/golive/fixtures/tenants.ts`; this is in-flight QA work on a branch I must not alter. `preflight --full` (typecheck before push) is the preventive control.

### 6. The advisory gate is red on `develop` itself — new, needs the owner
`node scripts/check-production-advisories.mjs` on **current `develop` content** fails: **1 CRITICAL advisory in `next`**, 19 production advisories with no written disposition (`@nestjs/platform-express`, `multer`, `body-parser`, `qs`, `fast-uri`, `ip-address`, `nodemailer`, `sanitize-html`, `glob`, `minimatch`, …) and 3 dispositions that no longer match (`mammoth`, `argparse`, `sprintf-js`). The last green `develop` run (214433c1) pre-dates these advisories: the failure is the live feed, exactly the "CI goes red while the repo stands still" class. The nine Dependabot PRs are the fixes. **I did not widen the allowlist, bump dependencies or edit dispositions** (SEC-004): a critical advisory has no disposition by design, and a `next` minor bump on the go-live branch is the owner's call.
Consequence: any PR into `develop`, including this one, shows *Runtime schema tests → No undocumented production advisories* red until the dependency fixes land.

Limits: `workflow_run` and `schedule` workflows only fire from the default branch (`main`), so `ci-failure-report.yml` and the nightly trend start working only after a release reaches `main`. Release workflows (`release-app.yml`, `agent-auto-release.yml`) still use `setup-node` directly; they deploy, so they were not edited.

## Retry policy

A retry is a diagnosis, not a fix. Once, only for `NETWORK_TRANSIENT` and `RUNNER_TIMEOUT`, after confirming the duration is in family with prior runs. A failing test, type error, lint error or advisory is never retried; the first failure's excerpt and sha256 are preserved first.

## Self-healing boundaries

Automated: collect, classify, summarise, preserve evidence. Not automated by design: changing CI policy, relaxing a check, rerunning failed tests, merging, bumping dependencies. A merge queue was not assumed: `npm run branch:policy` should confirm whether one exists before `merge_group` is added to the required workflows.
