# QA-AUTH-014 — A Server Component render never spends a refresh token it cannot persist

## Preconditions

`apiRequest` (`apps/web/lib/server-api.ts`) driven with a `next/headers`
`cookies()` stub whose `.set()` throws, matching what Next actually throws
during a Server Component render — no live database or running Next server
required.

## Steps

1. Call `apiRequest` for a path that requires auth, with a refresh cookie
   present, no access cookie, and a cookie store whose `.set()` throws.
   Record every URL `fetch` was called with.
2. Repeat with a cookie store whose `.set()` succeeds (a Route Handler
   shape), everything else identical.
3. Drive the retry-after-401 branch — an access cookie present but rejected
   by the API with `401` — under the same throwing cookie store.

## Expected Result

Step 1: `fetch` is called **zero** times — not even to `/auth/refresh`. The
refresh token the caller holds is never consumed, so it remains valid for
whichever component refreshes next. Step 2: `/auth/refresh` **is** called,
proving the guard is specific to the unwritable case and does not disable
refreshing generally. Step 3: no retry-refresh call is made; the original
`401` from the API is returned unchanged.

## Notes

Before [[BUG-3358]], a Server Component render refreshed anyway, the network
call succeeded, `rotateRefreshToken` revoked the presented token and wrote a
successor — and then `persistRefreshedAuthCookies`'s `try/catch` discarded
the failed cookie write silently. The render succeeded and the session was
dead from that moment, with nothing anywhere recording it. This scenario
pins the reordering: detect the unwritable store **before** the network call
that would otherwise burn the single-use credential.
