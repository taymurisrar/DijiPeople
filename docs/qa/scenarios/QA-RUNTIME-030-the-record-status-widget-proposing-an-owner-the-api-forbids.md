# QA-RUNTIME-030 — The record-status widget proposing an owner the API forbids

## Preconditions

A tenant on which the affected surface is reachable, and a signed-in user with
the permissions the surface requires. REG-332 in the regression register carries
the full root cause; this scenario is the reusable check, not the diagnosis.

## Steps

The leave spec asserts the request body carries neither `ownerId` nor `status` while still carrying the four fields the request is actually made of. The sweep drives the real adapter's `create()` for **every** exported `StandardModuleRuntimeSpec` with a draft carrying an owner under the spec's own owner field and under both spellings the widget has used, and asserts the body carries none of them.

## Expected Result

The behaviour holds as REG-332 describes it. The automated guard is `apps/web/lib/runtime/modules/leave-create-payload.spec.ts`; a run of that suite is sufficient evidence for this scenario.

## Why This Is Reusable

`sanitizeStandardMutationValues` keeps every declared field that is not `isReadOnly` and is present in the submitted values, and the submitted values are the record page's draft — which the record-status header populates with an owner on every standard module. `SubmitLeaveRequestDto` whitelists neither `ownerId` nor `status`, and the global `ValidationPipe` runs with `forbidNonWhitelisted: true`, so either one in the body is a 400: no employee could submit a leave request through the UI
