# QA-TENANT-008 — One rule decides which workspace a hostname addresses

## Preconditions

None. The parser is a pure function of a hostname and the configuration handed
to it, and the spec supplies both.

## Steps

1. `npm --workspace api run test -- public-tenant-host`
2. Manually, against a running stack: with `TENANT_BASE_DOMAIN=localhost`
   configured, open `http://<slug>.localhost:3001/login?next=%2F` for an ACTIVE
   tenant.

## Expected Result

A workspace subdomain resolves under a locally configured base domain, with and
without a port, and against a deployed base domain. `admin.`, `api.`, `app.` and
the bare domain resolve to nothing. A nested label resolves to neither its
leftmost nor its rightmost part. A hostname that merely ends with the base
domain as a substring resolves to nothing. With no base domain configured,
nothing resolves — the parser fails closed.

Manually: the login page loads and the API does not answer `TENANT_NOT_FOUND`.

## Notes

Three of these assertions are about refusal rather than resolution, and they are
the security-relevant half: resolving `admin.dijipeople.com` would hand whoever
registered the slug "admin" the platform's own hostname, and resolving
`evil.maseer.dijipeople.com` as "maseer" would let a nested label address
somebody else's workspace.

Select this scenario whenever a change touches workspace hostnames, tenant
resolution or `packages/config/platform-domains.js`. This rule has now had three
independent implementations; the third was found only because a customer could
not log in.
