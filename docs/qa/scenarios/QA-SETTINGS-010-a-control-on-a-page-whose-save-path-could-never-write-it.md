# QA-SETTINGS-010 — A control on a page whose save path could never write it

## Preconditions

A tenant on which the affected surface is reachable, and a signed-in user with
the permissions the surface requires. REG-321 in the regression register carries
the full root cause; this scenario is the reusable check, not the diagnosis.

## Steps

Neither key is offered by the attendance settings page. Both are writable through `PATCH /attendance/policy` and persist on create and on update; omitting either leaves the stored value alone rather than resetting it.

## Expected Result

The behaviour holds as REG-321 describes it. The automated guard is `services/api/src/modules/attendance/attendance-policy-write.spec.ts`; a run of that suite is sufficient evidence for this scenario.

## Why This Is Reusable

"Allow off-day check-in" and "Allow holiday check-in" were defined in `settings-page-config.ts` against `AttendancePolicy` **column** names. Neither `attendance.allowOffDayCheckIn` nor `attendance.allowHolidayCheckIn` is a tenant-settings catalog key, and `normalizeSettingUpdates` rejects any key the catalog does not know
