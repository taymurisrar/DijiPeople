# QA-AUTH-002 — Sign-out always revokes the session and never 500s while clearing cookies

## Preconditions

A platform user with one live `PlatformRefreshToken`, and a tenant user with one
live `RefreshToken`, against a real PostgreSQL. The API is booted from
`AppModule` and driven over HTTP.

Promoted from PARTIAL on 2026-08-22. Until then this scenario read the admin
route's *source* and recorded, in its own steps, that "live handler execution and
persisted-token verification remain unimplemented" — which is the honest way to
hold a gap open, and [[ITEM-0002]] was the item to close it.

## Steps

1. Sign out with the refresh cookie present; read `revokedAt` back. *(control)*
2. Sign out with the refresh cookie **absent** and the session cookie present —
   the state after the refresh cookie's TTL elapses, which is the ordinary
   sign-out rather than an edge case. Read `revokedAt` back.
3. Sign out with a session id belonging to nobody; confirm a bystander's token
   is untouched.
4. Sign out as `web` with an `agent-desktop` session's id; confirm that token
   survives.
5. Repeat step 2 for the tenant client against `RefreshToken`.
6. Invoke the admin route's GET and POST handlers under a **rejected cookie
   configuration** and assert a redirect and a 200 rather than a 500, with the
   cookies still expired.

## Expected Result

Every sign-out that names a session ends it on the server. Steps 3 and 4 revoke
nothing. Step 6 never throws.

## Notes

Three records, one scenario. [[BUG-0009]] was the missed revocation on the
client, [[BUG-0010]] the 500, and [[BUG-0627]] — found while writing this
scenario's missing half — the **server** never revoking anything when the refresh
cookie was gone.

That last one is the reason the gap was worth closing rather than annotating.
[[BUG-0009]] fixed the route so the API is called; the test that closed it mocked
`fetch`, so it proved the request was *sent* and never that anything was
*revoked*. The defect sat behind a green test until something read a row back.

Steps 1–5 are DB-backed and live in `services/api`. Step 6 stays in the admin
app, where the cookie configuration it exercises actually is.
