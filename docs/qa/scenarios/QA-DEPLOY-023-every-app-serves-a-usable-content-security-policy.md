# QA-DEPLOY-023 — Every app serves a usable content security policy

## Preconditions

- All three apps deployed.

## Steps

1. Run `npm run test:security-headers`.
2. For each of `www`, `app` and `admin` on `dijipeople.com`:
   `curl -sI https://<host>/ | grep -i content-security-policy`.
3. Compare the `connect-src` clause across the three.
4. Open the landing site's checkout and watch the console for CSP violation
   reports.

## Expected Result

- The suite passes.
- All three serve a CSP.
- All three declare the same API origin, **including the scheme**, over
  `https`.
- No violation reports for ordinary API calls.

## Notes

Step 3 is the one that found BUG-1822, and it only works as a comparison — each
header read alone looks fine. Landing declared `http://api.dijipeople.com/api`
while the other two declared `https://`, so its `connect-src` matched nothing a
browser on an HTTPS page could reach.

The build now refuses a non-loopback `http://` origin, so this should not recur
from a fresh build — but the deployed bundle carries whatever the last build was
given, and `NEXT_PUBLIC_*` values are inlined at build time. A stale bundle and
a corrected variable look identical from outside.

**The policy is report-only on all three**, and `script-src` carries
`'unsafe-inline'` because Next's bootstrap needs it. That makes it a monitoring
tool rather than a control, and it should be described as one until a nonce
strategy and enforcement land. BUG-1424 records that as open.
