# QA-RUNTIME-044 — A record-form entity lookup finds and selects a record past the server's default page

## Preconditions

A tenant with more than `ENTITY_LOOKUP_PAGE_SIZE` (50) employees, or any other
entity a standard-module-runtime lookup targets in volume past its server's
default page size (20 for employees, `services/api/src/modules/employees/dto/employee-query.dto.ts`).
Signed in as any tenant user permitted to open a record with an entity lookup
field rendered by the standard module runtime — a Project's Project Manager,
Approval Manager, Account Manager or Delivery Manager field is the named
reproduction.

## Steps

1. Open a Project record (new or existing) in edit mode and focus the Project
   Manager lookup field.
2. Open the lookup's popup and type the exact full name of an employee who
   sorts past the 50th record for this tenant (alphabetically, or by whatever
   order the employees endpoint returns by default).
3. Watch the network request the control issues while typing (after the
   debounce settles, ~300ms after the last keystroke).
4. Confirm the employee appears in the list and can be selected with the
   mouse or keyboard (Enter on the highlighted option).
5. Save the record and reopen it. Confirm the Project Manager field shows the
   selected employee's name, not a raw id, and that the name is a clickable
   link in the field's label row that opens `/employees/<id>`.
6. Type a query broad enough to match more than 50 employees (e.g. a single
   common letter). Confirm the control states the list is truncated
   ("Showing first 50 — keep typing to narrow.") rather than silently
   presenting an incomplete list as complete.
7. Repeat step 2 with a query matching zero employees. Confirm the control
   shows the ordinary "No matching records found." message, not the
   stronger "options unavailable" message reserved for a field with no
   options at all.

## Expected Result

The employee past the server's default page is found and selectable (not
"No matching records found" read as "this person does not exist"). The
request issued while typing carries the typed name as a `search` query
parameter. A result set as long as the requested page size states it may be
truncated. A saved, reopened record still shows the selected employee's name
as an openable link, even though that employee's row is not necessarily on
the hydration effect's first page. A genuinely empty search result reads as
an ordinary empty search, not a field-level failure.

## Why This Is Reusable

`runtime-metadata-form-renderer.tsx`'s `<LookupField>` construction
(`useLookupFieldSearch`) is the one call site for every metadata-driven
record-form entity lookup — this scenario, run against any one of them (not
only Project Manager), covers the whole surface. `TEST_REFERENCE` covers the
one part of this fix that is pure and unit-testable outside a browser (the
reference-route resolution `lookup-reference-route.ts` replaced,
`lookup-reference-route.spec.ts`); the search-wiring hook itself lives inside
a React component this app's jest config cannot render (no jsdom —
`apps/web/AGENTS.md`), so the request/response/truncation/empty-state
behaviour above is this scenario's job, not a unit test's.

## Notes

Written alongside REG-470 while closing BUG-3376 / ITEM-0163 / ITEM-0172 in
SESSION-0103. Re-run this scenario, rather than writing a new one, the next
time the metadata-driven lookup call site or its search wiring changes.

Small, effectively-fixed reference lookups (country, currency, timezone,
state/province, city) are deliberately NOT covered by this scenario — they
keep the original cheap one-shot prefetch (`isSmallReferenceLookupEntity`)
and are not expected to send a `search` parameter at all.
