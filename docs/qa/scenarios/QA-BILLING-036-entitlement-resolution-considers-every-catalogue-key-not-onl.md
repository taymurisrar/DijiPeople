# QA-BILLING-036 — Entitlement resolution considers every catalogue key, not only the plan's own rows

## Preconditions

A tenant on a plan (e.g. Starter) that has genuinely no `PlanFeature` row at
all for a given gated key (e.g. `payroll`) — not a disabled row, an absent
one, matching how `commercial-bootstrap.ts` seeds a real Starter plan.
Entitlement enforcement set to `ENFORCE`
(`node scripts... entitlement:set-mode -- ENFORCE` against a non-production
database, or the mode mocked directly in a unit test).

## Steps

1. With no `TenantFeature` override at all, call
   `TenantEntitlementService.decide(tenantId, ['payroll'])`.
2. Write a `TenantFeature` row `{ key: 'payroll', isEnabled: true, source: 'MANUAL' }`
   and repeat step 1.
3. Change the row's `source` to `'CUSTOM'` and repeat step 1.
4. Attempt the same `CUSTOM` grant via `TenantModulesService.update()` (the
   settings-admin write path) instead of writing the row directly.
5. Hit a real route carrying `@RequireEntitlement('payroll')`
   (e.g. `GET /payroll/cycles`) under each of steps 1-3.

## Expected Result

- Step 1: `NOT_ENTITLED`, `allowed: false`.
- Step 2: still `NOT_ENTITLED` — a MANUAL override cannot grant beyond the
  plan, matching the existing, unchanged rule.
- Step 3: `ENTITLED`, `allowed: true` — a CUSTOM override grants a key the
  plan's own rows never mention at all, proving the resolver now considers
  the full catalogue rather than only the plan's `PlanFeature` rows.
- Step 4: refused with the existing "the current plan does not include
  payroll" message — the ordinary write path still cannot produce a CUSTOM
  grant; only `prisma/grandfather-entitlement-overrides.ts` writes one.
- Step 5: 403 under steps 1-2, 200 under step 3.
