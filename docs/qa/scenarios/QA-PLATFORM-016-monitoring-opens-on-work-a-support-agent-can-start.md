# QA-PLATFORM-016 — Monitoring opens on work a support agent can start

## Preconditions

Platform Admin with incidents recorded, ideally including at least one critical
and one already resolved.

## Steps

1. `npm --workspace admin run test -- monitoring-overview`
2. Open **Monitoring** from the sidebar.
3. Read the four figures at the top. Click **Critical, untriaged**.
4. Return, and use the search box, the severity, source and status selects, and
   the sort control.
5. With filters applied, press **Open in the full queue**.
6. Click the reference chip on a row.
7. Read the bottom band.

## Expected Result

Step 2: you land on the Overview.

Step 3: each figure states what it counts *and what that implies*. Clicking one
opens the incident queue already filtered.

Step 4: the list narrows and re-sorts in place, without a page load.

Step 5: the full queue opens with the same filters applied — not reset.

Step 6: the reference is copied.

Step 7: the platform's event failure rate and its sources, with a link to the
event log. No "Succeeded" tile: nobody triages a success, and it now reads as
the denominator it is.

## Notes

The page deliberately shows the **most recent 25** and says so. Presenting a
slice as the whole queue would be a worse lie than showing nothing, and the full
queue is one click away with pagination and assignment.

Considerations:

- The automated half is structural, over source — `apps/admin` jest has no jsdom
  ([[ITEM-0001]]). It can tell that four click handlers exist; it cannot tell
  that pressing one filters anything. Steps 3–6 are the real verification.
- Step 5 is the hand-off that would be perverse to get wrong: rebuilding the
  same filter on the next screen is exactly the friction this page removes.
