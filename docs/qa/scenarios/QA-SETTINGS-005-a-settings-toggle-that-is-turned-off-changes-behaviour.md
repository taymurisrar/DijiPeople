# QA-SETTINGS-005 — A settings toggle that is turned off changes behaviour

## Preconditions

- A tenant with timesheet background jobs running.
- Access to the tenant audit log and to Settings > Timesheets.

## Steps

1. `npm --workspace api run test -- timesheet-job-audit`
2. With "Audit background jobs" **off**, run a timesheet background job and read
   the audit log.
3. Turn it **on**, run another job, and read the log again.
4. On a tenant that has never touched the setting, run a job and read the log.

## Expected Result

- Step 1: five assertions pass.
- Step 2: no `TIMESHEET_BACKGROUND_JOB_COMPLETED` row is written. Before the fix
  one was written regardless, because nothing read the setting.
- Step 3: the row is written.
- Step 4: no row. The decided default is **off**, deliberately differing from the
  catalog's declared `true`.

## Notes

**This scenario is about a class, not a toggle.** The defect was not that
background jobs were audited; it was that a control existed on screen, read as
an assurance, and was connected to nothing. An administrator could switch it off,
see it save, and change no behaviour at all. That is the same shape as BUG-2015
(a permission key nothing enforced) and BUG-0669 (a validation DTO nothing
referenced) — and it is PLAN-021's risk #2, which is why this scenario is filed
here rather than under timesheets.

**Three sibling toggles are still unwired**: `auditEntryChanges`,
`auditPolicyResolution` and `auditExports` sit in the same catalog category, all
render on screen, and nothing reads any of them. Only `auditBackgroundJobs` was
in scope for BUG-2045. A QA agent running this scenario should assume the other
three still do nothing until a record says otherwise.

**Step 4 is the one to keep honest.** The reader treats "not explicitly enabled"
as off while the catalog still declares `true`. If somebody later migrates the
catalog to `false`, this step's expectation is unchanged — which is the point of
writing it as behaviour rather than as a default value.
