# QA-SETTINGS-020 — An operator with the retry permission can retry a failed delivery, and the outcome shows on the record

## Preconditions

A tenant with at least one `FAILED`, `retryable: true` `EmailDeliveryLog` row
for a non-`AUTH_*` event whose `metadata.originalVariables` was captured
(any send made after this feature shipped). Two users: one holding
`notification.logs.read` only, one additionally holding
`notification.logs.retry`. The tenant's effective email provider is a real
transport (SMTP/SES/etc.), not CONSOLE/DEV.

## Steps

1. As the read-only user, open the `FAILED` delivery log's record at
   `/settings/notifications/logs/<id>`.
2. As the retry-permitted user, open the same record.
3. Click "Retry Delivery".
4. Attempt the same action directly against the API as the read-only user:
   `POST /notifications/email-delivery-logs/<id>/retry`.
5. Open a `NOT_DELIVERED` or non-retryable `FAILED` row (`retryable: false`)
   as the retry-permitted user.
6. As the retry-permitted user, retry a `FAILED` row belonging to an
   `AUTH_ACCOUNT_ACTIVATION` or `AUTH_PASSWORD_RESET` event, and (separately)
   a tenant whose effective provider is currently CONSOLE/DEV.

## Expected Result

Step 1: no retry control is rendered anywhere on the page — not disabled,
absent. Step 2-3: the control is visible, and clicking it shows an inline
outcome panel naming the new delivery's status (via the shared `StatusPill`,
a human label, never a raw enum member), its provider type, and — if
`NOT_DELIVERED` or `FAILED` — its reason. The original row is otherwise
unchanged except its retry count. Step 4: `403`, independent of anything the
UI would have shown — the endpoint enforces `notification.logs.retry`
itself. Step 5: no retry control appears on either row. Step 6 (both cases):
the control is offered (the row looks retryable) but the attempt is refused
with a full, legible sentence rendered in the panel's error banner — for the
`AUTH_*` case, a message directing the operator to re-trigger the original
action instead of retrying; for the sink-provider case, a message naming the
sink provider and pointing at the Providers screen — never a bare error code,
and no second `NOT_DELIVERED` row is created by the attempt.

## Notes

Created 2026-09-12 at `5f546711`. Backend eligibility branches (AUTH
exclusion, sink-provider refusal, non-retryable/non-FAILED refusal, missing
originalVariables refusal, the happy path returning both the retried and the
new log) are pinned at the unit level by `notification-retry.spec.ts`. The
frontend half — the control's visibility gating and the inline outcome
panel — has no automated test in this change (`apps/web`'s Jest config is
scoped to pure `.spec.ts` logic, no jsdom); `AUTOMATION_STATUS: PARTIAL`
reflects that split. This is the scenario ITEM-0168 closes on.
