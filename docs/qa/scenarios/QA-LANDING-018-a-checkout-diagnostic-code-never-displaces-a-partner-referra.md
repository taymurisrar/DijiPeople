# QA-LANDING-018 — A checkout diagnostic code never displaces a partner referral code

## Preconditions

- A browser with no `dijipeople_referral` cookie and empty `sessionStorage` for
  the site — this scenario is about *first* touch, so a pre-existing code
  invalidates it. Clear both before starting.
- A plan/market combination that is **not** purchasable, so the `DP-CHK-01`
  panel renders. While [[BUG-0898]] stands, any QAR plan will do.

## Steps

1. Clear the referral state:
   ```js
   sessionStorage.clear();
   document.cookie = 'dijipeople_referral=; Max-Age=0; path=/';
   ```
2. Open `/subscribe` for the unpurchasable plan. Confirm the "This form is not
   available for the plan you have selected (DP-CHK-01)" panel renders.
3. Click **Ask us to arrange this plan**.
4. Read the stored referral:
   ```js
   ({ session: sessionStorage.getItem('dijipeople_referral'), cookie: document.cookie })
   ```
5. Navigate to `/?ref=REALPARTNER99` — a well-formed partner code.
6. Read the stored referral again.

## Expected Result

- **Step 4** — no referral code is stored. The visitor arrived under no
  partner's link, and clicking a support affordance inside the product is not an
  acquisition event. `dijipeople_referral` must be absent, not set to
  `DP-CHK-01` or to any other diagnostic value.
- **Step 6** — the stored referral is `REALPARTNER99`. The partner code is the
  visitor's *first* genuine referral touch and must take effect.

The second assertion is the one that matters commercially, and the one that
fails today: first-touch-wins is correct policy, so anything that occupies the
slot first permanently excludes real partners for the cookie's 30-day life.

Run the mirror case too, to prove the fix did not break the policy it protects:
arrive under `?ref=REALPARTNER99` **first**, then click through DP-CHK-01, and
confirm the partner code survives.
