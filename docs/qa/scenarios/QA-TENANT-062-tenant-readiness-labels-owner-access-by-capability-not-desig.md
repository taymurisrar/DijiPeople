# QA-TENANT-062 — Tenant readiness labels owner access by capability not designation

## Preconditions

A tenant whose `ownerUserId` is **null** but which has at least one active,
non-service-account user holding `GLOBAL_ADMIN`. `dijipeople-demo` was such a
tenant on 2026-08-30.

A platform administrator signed in to the admin console.

## Steps

1. Open **Tenants** and select that tenant.
2. Read the header field labelled **Primary Tenant Owner**.
3. Read the owner row of the **Tenant readiness** panel on the same screen.
4. Confirm the two are distinguishable without knowing the schema.

The unit case covers the same ground without a browser: `buildReadiness` with
`activeOwnerCount: 1` and `ownerUserId: null` must return `label: 'Owner access'`
for the `owner` check.

## Expected Result

- The header reads **Primary Tenant Owner** — the designation, from
  `Tenant.ownerUserId`. `Unassigned` is a legitimate value.
- The readiness row reads **Owner access**, with the message
  *"1 account can administer this workspace."*
- Neither is labelled "Tenant Owner", so the two facts cannot be read as
  contradicting each other.

Both statements may be true at once. A tenant with no designated primary owner
and one capable administrator is healthy, and the screen must be able to say so.

## Notes

Created 2026-08-30 at `39d8ddc4` for [[BUG-2384]] / REG-366.

Observed in production: the header read `Unassigned` beside "1 active Tenant
Owner" on the same screen. Neither figure was wrong — only the shared label was.

Mutation-tested — reverting the label to `'Tenant Owner'` fails the unit case.

The **behaviour** is unchanged: `countActiveOwners()` is untouched, and the error
messages elsewhere that say "active Tenant Owner" refer to the owner *role* and
were deliberately left alone.
