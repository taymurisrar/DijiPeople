# QA-TENANT-056 — Employee import resolves named lookups into real foreign keys

## Preconditions

A tenant with employee write access for the caller, and lookup rows that the
imported names can resolve to: at least one department, one designation and one
emergency-contact relation type. Their **names** are what the import file
carries, so the values in the file must match seeded rows exactly.

The import file is built from the header the product itself serves, not from a
header written by hand.

## Steps

1. `GET /api/employees/export-template` and read the header row.
2. Build one data row against that exact header, filling `department`,
   `designation` and `emergencyContactRelationType` with the **names** of seeded
   lookup rows rather than ids.
3. `POST /api/employees/import` with that file.
4. Fetch the created employee and read the three fields from step 2.

## Expected Result

1. The template header is the full field-key column set the importer accepts —
   21 columns at the time of writing, including the four emergency-contact
   columns that are mandatory at create time.
2. Not applicable — file construction.
3. 201 with `{"totalRows":1,"successCount":1,"failureCount":0,"errors":[]}`. A
   partial success reported as a success is the failure this step exists to
   catch.
4. Each of the three named values has been **resolved into a real relation**:
   the employee's department, designation and emergency-contact relation type
   point at the seeded lookup rows. Not null, and not the raw string carried in
   the file.

## Notes

Created 2026-08-29 at `8ab1cbff` from the second Starter-plan production pass,
`docs/qa/runs/2026-08-29-starter-plan-e2e-pass-2-8ab1cbf.md` (SESSION-0072),
where every step passed against production API `949f461c`: EMP-0012 came back
with `department` "Marketing", `designation` "Marketing Specialist" and
`emergencyContactRelationType` "Spouse" all resolved to foreign keys.

Step 4 is the point of the scenario, and the reason it is not merely a smoke
test of a 201. A loader that maps columns without resolving lookups still
returns `successCount: 1`, and the rows it creates look created until somebody
opens one and finds the department empty — `silent-degradation` on a write path
that a customer runs once, at onboarding, over their whole workforce.

`POST /api/employees/import` had never been executed by any QA run before this
one; BUG-2026 was written against the *export* column set with the import path
explicitly untested. This scenario is what stops that state returning. BUG-2026
itself remains open on the export side — the two are not the same defect, and
this scenario deliberately proves only the import direction.

Not covered here, and worth adding when this is automated: volume, a duplicate
`employeeCode`, a lookup name that does not resolve, and how a failing row is
reported in `errors`.
