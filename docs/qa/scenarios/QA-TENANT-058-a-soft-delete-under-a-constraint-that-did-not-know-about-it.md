# QA-TENANT-058 — A soft delete under a constraint that did not know about it

## Preconditions

A tenant on which the affected surface is reachable, and a signed-in user with
the permissions the surface requires. REG-311 in the regression register carries
the full root cause; this scenario is the reusable check, not the diagnosis.

## Steps

The schema must not declare a full unique on `(tenantId, name)`; a migration must both create the partial `Department_active_tenant_name_key` index carrying the `isActive = true` predicate and drop the old `Department_tenantId_name_key`; `@@unique([tenantId, code])` must survive whole-table; and a P2002 raised on the update path must surface as a 409 rather than a 500. Schema and migrations are read from disk rather than restated, and a control asserts the model body was actually located, because an assertion over an empty array is green.

## Expected Result

The behaviour holds as REG-311 describes it. The automated guard is `services/api/src/modules/organization/departments-list-contract.spec.ts`; a run of that suite is sufficient evidence for this scenario.

## Why This Is Reusable

Deleting a department is a soft delete — `deleteDepartment` sets `isActive = false` and leaves the row in place — while uniqueness was `@@unique([tenantId, name])` across every row, active or not. The name was therefore never released: a tenant that deleted a department could not recreate one by that name through any route the product offers, and the 409 it got back blamed a record the product had just reported deleted
