# QA-BILLING-028 — Expired subscription orders are swept by a runner that is actually wired in

## Preconditions

A subscription order left in `PENDING_PAYMENT` past its expiry, holding both a
`submissionHash` and a `requestedSlug` — both unique columns, which is why an
unswept order matters.

`SUBSCRIPTION_ORDER_SWEEPER_ENABLED` available to set.

## Steps

1. Boot the billing module with the sweeper flag set to `true` and confirm a
   worker provider starts.
2. Let a tick run without invoking the service by hand, and observe that expired
   orders are abandoned.
3. Boot with the flag unset and confirm no timer starts.
4. Make the sweep reject, and confirm the tick survives it.
5. Attempt to re-use the released workspace address.

## Expected Result

- The sweep runs because the **application** calls it, not because a test does.
  That distinction is the whole scenario: the method was fully implemented and
  fully unit-tested for months while nothing in the running app invoked it.
- With the flag off, nothing is scheduled.
- A rejected sweep is logged and the next tick still happens, so a transient
  database error cannot silently stop the sweeper for ever.
- Once swept, the workspace address and submission hash are free again.
