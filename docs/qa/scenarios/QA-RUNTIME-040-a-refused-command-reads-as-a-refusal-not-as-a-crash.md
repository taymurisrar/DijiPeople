# QA-RUNTIME-040 — A refused command reads as a refusal, not as a crash

## Preconditions

- Any tenant. The clearest fixture is an approval the signed-in user raised
  themselves — the demo tenant's `ACR-000001` is one — because the attendance
  module refuses self-approval with a specific, well-formed 403.
- To exercise the negative half you need a failure that is *not* a business
  refusal. Do not manufacture one by breaking production: use the automated
  cases, which construct 5xx, HTML bodies and network failures directly.

## Steps

1. Open an approval you submitted yourself and press **Approve**, then confirm.
2. Read what appears, and read what does **not** appear.
3. Dismiss it and confirm the page is still usable and the record unchanged.
4. Run the automated cases for the failures that must still be treated as
   defects.

## Expected Result

1–2. A **toast**, carrying the server's own sentence — "You cannot approve or
reject your own attendance correction request." No red `ERROR ACCESS_DENIED`
heading, **no reference id, no timestamp, no Download log button**, and no modal
blocking the page. The generic second line ("You do not have permission to
perform this action.") is not shown, because it only repeats the headline.

3. The toast dismisses, the page stays usable, and the request is still Pending.
Nothing was written.

4. These must still raise the technical dialog with its trace id:

| Failure | Why it stays a defect |
|---|---|
| 5xx | broken by definition |
| 401 | only the dialog can offer **Sign in**; a toast would strand the user |
| 404 | a dead route must stay loud |
| 403 with an HTML body | a proxy or WAF page is not a business refusal |
| a body with no server-written message | the reader's own fallback proves nothing |

## Notes

Created 2026-09-08 at `2cee8b9b`, from the owner's screenshot of the fatal dialog
raised during post-release verification of [[BUG-2718]].

The classification is automated in
`apps/web/lib/runtime/command-failure-classification.spec.ts`, and **the negative
half is the half worth re-running**. The risk in this behaviour is not that a
refusal stays in the dialog — someone will complain. It is that a genuine defect
is dressed as a calm toast and nobody investigates it. Removing the status gate
fails seven cases; removing the envelope shape check fails three.

Step 1 is manual because it proves the wiring, not the classifier: that the
command handler routes a real refusal from a real endpoint into the toast rather
than the dialog.

Attendance keeps its own richer treatment — `AttendanceActionFeedback`, with a
retry affordance and the distance and accuracy numbers. Re-running a refused
check-in must show that, not the generic toast; a regression there would look
like this scenario passing.
