# QA-RUNTIME-017 — An unroutable approval chain refuses the submission and names every step that cannot bind

## Preconditions

- A tenant whose approval matrix for a module has more than one active step.
- At least one step that cannot bind to an active approver — the shipped seed
  provides two: sequence 1 `LINE_MANAGER` for an employee with no manager, and
  sequence 2 `ROLE(hr)` with nobody holding the role.

## Steps

1. `npm --workspace api run test -- approval-matrix-resolver`
2. Against a live tenant, with both seeded leave steps active and neither
   satisfiable, submit a leave request: `POST /api/leave-requests` with a valid
   `leaveTypeId`, `startDate`, `endDate` and `reason`.
3. Give the requester a reporting manager with an active user account, leaving
   the `hr` role empty. Submit the same body again.
4. Populate the `hr` role with an active user. Submit the same body again.

## Expected Result

- Step 1: the suite passes, including the four assertions in the `BUG-1968`
  describe block.
- Step 2: **400**, `errorCode` `APPROVAL_ROUTE_UNRESOLVED`. The message names
  **both** steps — "Step 1 (line manager)" and "Step 2 (role)" — each with what
  to configure. Before the fix it named only the first, with no step number and
  no remedy.
- Step 3: **400** again — the policy is unchanged and this is correct. The
  message now names **only** step 2. Step 1 must not appear: it resolves, and
  listing it would send an administrator to fix something already right.
- Step 4: **201**, and the request routes through both steps.

## Notes

**The refusal in steps 2 and 3 is the intended behaviour, not the defect.** The
repository owner decided on 2026-08-29 that an approval chain with a step nobody
can approve must keep refusing: skipping a step would silently approve around a
control the tenant configured, and accepting the request would strand it with no
route out. What was wrong was that the refusal named neither the step nor the
remedy, and stopped at the first failure — so an administrator fixed one step,
resubmitted, and met the next. A future QA agent should not "fix" steps 2 and 3
into passes.

**Step 3 is the load-bearing step.** It distinguishes "every step must resolve"
from "the first resolvable step wins", and it is the one that inverts under any
of the three policies that were rejected. It corresponds to row 2 of the probe
table in BUG-1968.

**Steps 2 to 4 can now be run through the browser.** They could not when this
scenario was written: BUG-1966 meant the runtime form swallowed the failure and
the employee saw nothing at all. That was fixed by SESSION-0072 (REG-307) while
this work was in flight, and both fixes are on `develop` together — so run these
steps through the UI, which is where the refusal was always meant to be read.
Running them against the API directly still works and is the faster check.

**The demo tenant is not in the shipped default state.** Its two seeded matrices
were deactivated during the original investigation and a probe rule left active,
so that leave demonstrates end to end. Restore them before running step 2 there,
and restore the deactivation afterwards. See the environment note on BUG-1968.
