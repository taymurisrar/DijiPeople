# QA-AUTH-009 — Refresh is budgeted as machine traffic, not as a credential attempt

## Preconditions

None beyond the unit under test. `PublicRateLimitGuard` keys its window
on (client IP, path), so each assertion uses a unique synthetic path and needs
no database, no server and no fixture.

## Steps

Drive the guard past the credential budget on a refresh path and assert every
call succeeds: 200 consecutive non-GET requests from one address, comfortably
past the old limit of 20 and past what a real fleet of tabs behind one NAT
would produce in a ten-minute window. Then drive it to 600 on a second refresh
path and assert the 601st is refused, so the endpoint is still bounded.

Then, on seven separate paths named individually — `auth/login`,
`admin/auth/login`, `agent/auth/login`, `auth/forgot-password`,
`auth/activate-account`, `public/subscribe`, `public/leads` — assert the 21st
request is still refused.

## Expected Result

Refresh sustains machine-rate traffic and is still refused at an implausible
flood. **Every credential route still refuses the 21st request.** That second
half is the point of the scenario: raising one budget is only safe if the other
provably did not move with it, and BUG-0013, BUG-0031, BUG-0033 and BUG-0075
are what those seven routes cost to learn the first time.

## Why This Is Reusable

Any future per-route budget lands in the same `ROUTE_LIMITS` table, and a
suffix match is easy to write too loosely — `/auth/login` ends with `/login`,
and a careless entry would exempt exactly the routes that must never be
exempt. Re-run this whenever that table changes.
