# QA-TENANT-028 — Migrations run over a direct connection under either variable name

## Preconditions

- A Neon-backed deployment where `DATABASE_URL` names the pooled endpoint.

## Steps

1. Run `npm run test:database-urls`.
2. On the deployed service, confirm a direct (non-pooled) connection is set
   under `DIRECT_DATABASE_URL` or `DIRECT_URL`.
3. Trigger a deploy and watch `prisma migrate deploy`.

## Expected Result

- The suite passes.
- Either variable name resolves the migration connection; `DIRECT_DATABASE_URL`
  wins when both are set.
- Migrations apply. They do not fail `P1002` after a ten-second lock timeout.

## Notes

The failure this prevents is not slow, it is impossible: `migrate deploy` takes a
session-scoped advisory lock, and under PgBouncer transaction pooling consecutive
statements are not guaranteed to reach the same backend, so the lock can never be
established. BUG-0086.

What made BUG-0905 hard to see is that the variable *looked* set. `DIRECT_URL` is
the name Prisma's docs and Neon's guide use, so it is the natural thing to
configure, and it did nothing at all. A variable that is absent produces a
question; one that is ignored produces a wrong answer.

The value itself lives on the service and cannot be asserted from the repository.
What the suite holds is the resolution rule.
