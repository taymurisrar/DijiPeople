# QA-TENANT-012 — Confirming wildcard DNS reaches the hostnames already issued

## Preconditions

A tenant whose workspace hostname was issued while `wildcardDnsReady` was false,
so it reads Pending.

## Steps

1. `npm --workspace api run test -- tenant-domain`
2. Open the tenant → **Domains**. Read the amber panel.
3. Follow **Confirm wildcard DNS readiness** and save the setting.
4. Return to the tenant's Domains panel.
5. Add a custom domain, leave it unverified, and save the setting again.

## Expected Result

Step 2: the panel says this is a one-time manual platform setting, that nothing
here probes DNS, and — on localhost — that there is no DNS to configure at all
because browsers resolve `*.localhost` themselves.

Step 4: the workspace subdomain now reads Verified / Active.

Step 5: the **custom** domain is still unverified. It must not be promoted.

## Notes

Step 5 is the load-bearing one. A customer's own domain is verified against
records they control, and the platform wildcard says nothing about it — sweeping
it to Verified would assert something nobody checked, which is the same defect
this scenario exists for, pointed the other way.

Consideration: the reconciliation runs on the settings save, outside its
transaction. If it fails, the flag is still correct and saving again repeats the
sweep — so a failure here is recoverable and must not roll back the operator's
setting.
