# QA-RUNTIME-010 — Theme precedence holds and web route handlers decide nothing

## Preconditions

`apps/web` builds and its jest project runs.

## Why this scenario exists

Three defects that all made the product quietly disagree with itself.

*Theme (resolution order).* A tenant could set `defaultThemeMode` to DARK, save
it successfully, and see nothing change — because three writers competed for
`data-theme` and one of them installed a MutationObserver that reverted every
write it had not made. The setting worked; the resolution order did not exist.

*Theme (pre-paint).* [[BUG-3373]] — even with the resolution order fixed, the
*first painted frame* of every full page load still resolved from
`localStorage` and the operating system only, because the blocking bootstrap
script in `apps/web/app/layout.tsx` was a static string with no way for a
tenant value to reach it. A Light tenant on a dark-preferring machine painted
dark for the first several hundred milliseconds of every load. The server now
resolves as much of the precedence as it can (explicit cookie choice → tenant
default) and stamps `data-theme` into the server-rendered HTML directly; the
bootstrap script is narrowed to finishing a `system` resolution via
`matchMedia`, seeded from the server-stamped `data-tenant-theme` rather than
guessing.

*Proxies.* `apps/web/AGENTS.md` says a route handler forwards the request,
forwards the response, and decides nothing. Three handlers decided anyway, and
each failure was invisible in a different way: `teams` returned a fabricated
empty list a denied caller could not distinguish from "you have no teams";
`dashboard-views` turned any API failure into an invented "Administration"
dashboard; `reverse-geocode` sent employee IP addresses to OpenStreetMap next to
their punch coordinates.

## Steps

1. `npm --workspace web run test -- --testPathPatterns theme-precedence`
2. `npm run check:proxies-forward-refusals`
3. `npm --workspace web run test` (the forwarded-headers invariant runs here)

## Expected Result

Theme resolves explicit choice → tenant default → device, and `data-theme` is
only ever a concrete `light` or `dark`. `resolveThemePrecedence` (the pure
function shared by the client's DOM-based resolution and the server's
cookie-based one) returns the tenant default with no stored choice, an
explicit choice over the tenant default, an explicit `system` choice over the
tenant default, and `system` when neither is known. No route handler reads
permissions to decide access, substitutes data the API did not return, or
forwards client headers anywhere but to the API.

## Negative Case

Reverting `effectiveThemeChoice()` to `readStoredThemeChoice() ?? "system"` — the
expression that caused the bug — fails `uses the tenant default when the user has
chosen nothing`. Verified 2026-08-18.

## Notes

`data-theme` is the *resolved answer* the stylesheet keys on; the tenant default
now lives in `data-tenant-theme`. Keeping them in one attribute is what created
the race, and a literal `data-theme="system"` matched no rule in `globals.css`,
so a tenant default of SYSTEM read as light regardless of the device.

Two proxy instances remain and are deliberately not covered here: payroll
`basicSalary` derivation and branding-asset upload orchestration, both carried by
[[ITEM-0050]]. The first is money and needs its domain owner rather than a
mechanical move.
