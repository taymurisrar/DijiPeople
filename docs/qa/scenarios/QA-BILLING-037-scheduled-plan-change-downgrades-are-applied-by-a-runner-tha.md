# QA-BILLING-037 — Scheduled plan-change downgrades are applied by a runner that is actually wired in

## Preconditions

A tenant with a Stripe-backed subscription and a `PlanChangeRequest` row
`status: SCHEDULED`, `direction: DOWNGRADE`, `effectiveAt` in the past.
`SUBSCRIPTION_CHANGE_SWEEPER_ENABLED` available to set.

## Steps

1. Boot the billing module with the sweeper flag set to `true` and confirm a
   `SubscriptionChangeSweeperWorker` provider starts.
2. Let a tick run without invoking `PlanChangeService` by hand, and observe
   the due downgrade is applied.
3. Confirm the tenant's `Subscription.planId`/`planPriceId` moved to the
   downgraded plan, and the Stripe subscription item's price was updated
   with `proration_behavior: 'none'`.
4. Boot with the flag unset and confirm no timer starts.
5. Make `applyDueChanges` reject, and confirm the tick survives it.
6. Request an UPGRADE through `POST /billing/plan-changes` and confirm it
   applies immediately (no sweep needed) and pushes to Stripe with
   `proration_behavior: 'create_prorations'`.

## Expected Result

- The scheduled downgrade is applied because the **application** calls
  `applyDueChanges()`, not because a test does — the method was fully
  implemented and covered by its own e2e test for as long as it existed, with
  nothing in the running app ever invoking it.
- With the flag off, nothing is scheduled and the request stays `SCHEDULED`
  past its `effectiveAt` indefinitely.
- A rejected sweep is logged and the next tick still happens.
- Stripe is updated on both the immediate (UPGRADE) and scheduled
  (DOWNGRADE) paths, with the proration behaviour appropriate to each — never
  prorated at the renewal boundary the customer already paid through.
