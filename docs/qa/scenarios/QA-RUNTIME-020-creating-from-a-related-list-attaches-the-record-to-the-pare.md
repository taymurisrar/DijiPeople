# QA-RUNTIME-020 — Creating from a related list attaches the record to the parent it was opened from

## Preconditions

- A tenant with at least one Department, one Leave Policy and one State.
- A user who may create teams, leave-policy assignments and cities.

## Steps

1. `npm --workspace web run test -- related-record-parent-key`
2. Open a Department record, go to its Teams tab, and create a team from that
   tab. Then **reload the department** and look at the same tab.
3. Open a Leave Policy, go to Assignments, and create an assignment.
4. Open a State, go to Cities, and create a city.
5. Open an Organization, go to Business Units, and create one.

## Expected Result

- Step 1: all assertions pass, including that the create body carries the parent
  foreign key when the create path does not name `{parentId}`, and does not
  carry it when the path does.
- Step 2: the team saves **and is still there after the reload**, listed under
  the department it was created from.
- Steps 3 to 5: each record saves and appears under its parent. Before the fix
  each failed with a 400 naming a field the dialog has no control for —
  `leavePolicyId must be a UUID`, `Country is required.`, `organizationId must
  be a UUID`.

## Notes

**The reload in step 2 is the whole test, and skipping it is how this defect
survived.** Department > Teams was the one case of seven that did *not* fail
loudly: the POST returned **201** and created a team with `departmentId = null`.
The dialog closes, the toast says saved, and the row is simply absent from a list
nobody re-reads in the same breath. A team with no department appears in no
department's list at all, so nothing surfaces it later either.

Steps 3 to 5 are the ordinary case and fail with a visible 400, which is the
easier half.

The automated half asserts the **request body**, not the response, for the same
reason: a response cannot distinguish "saved correctly" from "saved as an
orphan". It walks both registries — the standard module specs and the settings
adapter registry — because six of the seven broken subgrids live in settings,
which is not in `SPECS` at all.

**A pre-existing data question this does not answer:** teams created through that
tab before the fix still carry `departmentId = null` and are invisible in the UI.
They need a direct query to find, and deciding what to do with them is not this
scenario's job. See BUG-2011.
