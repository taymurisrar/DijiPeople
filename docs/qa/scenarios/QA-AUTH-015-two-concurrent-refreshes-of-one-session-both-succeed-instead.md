# QA-AUTH-015 — Two concurrent refreshes of one session both succeed instead of one being revoked

## Preconditions

`AuthService.refresh()` driven with a mocked Prisma client that can present a
token as "recently revoked, live successor exists in the same family" — the
shape the losing side of a race sees — and `proxy.ts`'s `refreshSessionTokens`
driven with a mocked `fetch`. No live database required.

## Steps

1. Present a refresh token to `AuthService.refresh()` that does not match any
   currently-live `RefreshToken` row, but does match a row revoked moments
   ago whose family (`tokenFamilyId`) has a live successor.
2. Present a refresh token that matches a row revoked five minutes ago (well
   outside the grace window), with the same live-successor shape.
3. Call `proxy.ts`'s `refreshSessionTokens` twice concurrently with the same
   refresh token; count the underlying `fetch` calls.
4. Drive `proxy()`'s refresh branch so the first `refreshSessionTokens` call
   reports `shouldLogout: true`, and confirm a second attempt is made before
   `redirectToLogout`.
5. With a tenant configured `allowMultipleActiveSessions: false`, perform an
   ordinary (non-racing) successful rotation and confirm no other session is
   revoked.

## Expected Result

Step 1: `refresh()` resolves with a fresh token pair rather than throwing
`SESSION_REVOKED`, and does not run a revoke-other-sessions sweep. Step 2:
`refresh()` throws `SESSION_REVOKED`, and an
`AUTH_REFRESH_TOKEN_REUSE_DETECTED` audit event is recorded. Step 3: exactly
one `fetch` call, not two. Step 4: `redirectToLogout` is only reached after
the retry also reports `shouldLogout: true` — not after the first failure.
Step 5: the sweep never runs during a rotation, regardless of the tenant's
single-session setting — that sweep exists for a new sign-in, not for a
session continuing itself.

## Notes

The grace window works from the existing `RefreshToken.tokenFamilyId` column
with no schema change — see
[[EXECPLAN-0037-refresh-rotation-grace-window-and-middleware-dedupe]]. It
does not attempt literal token-for-token convergence (recreating the exact
JWT bytes the winner received is not possible from a stored bcrypt hash);
"converge on one session" is satisfied by both callers ending up with a
valid, current pair for the same continuing session. Reuse **outside** the
window stays a hard refusal and gains an audit trail it did not have before,
so a genuine replay is distinguishable from an ordinary race after the fact.
