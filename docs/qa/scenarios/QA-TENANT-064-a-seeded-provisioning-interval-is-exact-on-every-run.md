# QA-TENANT-064 — A seeded provisioning interval is exact on every run

## Preconditions

A migrated, seeded test database — the `Database e2e` job runs `verify-database`,
`seed:demo` and `seed:admin` before any spec, and four suites fail without them.
The database name must carry a `test`, `ci`, `ephemeral`, `scratch` or `tmp`
marker or `assert-test-database` refuses to touch it.

Provisioning runs seeded at fixed ages: one still running and past its target, one
completed 48 hours ago in exactly five minutes.

## Steps

1. Run the provisioning queue suite. Read the completed run’s `elapsedMs`.
2. Run it again, and again, at different moments.
3. Read the still-running run’s `elapsedMs` in the same runs.
4. Run the whole 38-suite e2e job, not just this spec.

## Expected Result

- The completed run’s `elapsedMs` is exactly 300000 on every run. Not 300001: the
  fixture seeds an interval, so the interval is what it must get, and a helper
  that reads the clock once per timestamp makes that a race with the scheduler.
- The still-running run’s elapsed time stays a **lower bound** against the real
  clock. It is deliberately not exact, because a live run is still counting, and
  tightening it would reintroduce the same class of flake from the other side.
- The full job passes. A single spec passing against a bare database proves
  nothing about the job, which is how 66 failures in four suites were mistaken for
  a regression.
