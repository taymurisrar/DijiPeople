# QA-PLATFORM-040 — The monitoring health, occurrence, module-facet and related-event redesign is correct

## Preconditions

An error occurring more than once (same fingerprint); a related outbox event
with an embedded credential in `lastError`; a request whose route falls under
`platform/`, `super-admin/` or `settings/`.

## Steps

1. Trigger the same error fingerprint twice; inspect the resulting
   `ErrorLog` row's `module` field on both the create and the update branch.
2. Trigger an error under `/api/platform/tenants/xyz`, `/api/super-admin/billing/diagnostics`
   and `/api/settings/monitoring/error-logs`; check the derived module.
3. `listEvents` filtered by `module` and by an exact `correlationId`, and by
   `page`/`pageSize` on a large result set.
4. Open an incident's detail view (`getEvent`); check `relatedOccurrences`,
   `relatedAuditEvents` and `relatedOutboxEvents`.
5. Inspect a related outbox event whose `lastError` contains an embedded
   credential.

## Expected Result

Step 1's `module` is set on the first occurrence and preserved (not nulled)
on the second. Step 2 derives `platform/tenants`, `super-admin/billing` and
`settings/monitoring` — two-segment, not the bare umbrella prefix. Step 3's
module filter and exact correlation-id match reach the real Prisma `where`,
and pagination is database-side (`skip`/`take`), not an in-memory slice. Step
4 returns other occurrences of the same fingerprint (excluding the incident's
own trace id), related audit events across tenant and platform tables sorted
newest-first, and related outbox events matched on `correlationId`. Step 5's
credential is redacted before it reaches the response.
