# QA-ATT-014 — An on-premise attendance integration can be verified and then activated

## Preconditions

- A tenant with the attendance `integrationEnabled` setting **on**. It defaults
  to `false` and its absence stops the gateway's device loop before it reaches
  any integration, which will look exactly like this bug if it is missed.
- An attendance integration on a `LOCAL_GATEWAY` connector, status `UNVERIFIED`,
  `isActive = false`, with a schema-valid configuration.
- One enabled device on that integration, `verificationStatus = UNVERIFIED`,
  bound to a gateway.
- A gateway paired to the tenant and `ONLINE`, running against a worker that can
  answer — the bundled `DijiPeople.Gateway.FakeWorker` is sufficient and needs no
  hardware.

## Steps

1. As a tenant administrator, open the device and press **Verify device**
   (or `POST /integrations/attendance/devices/:id/verify`).
2. Wait for the gateway's next configuration refresh — up to
   `gatewayConfigRefreshSeconds`, 300 by default. It is not stuck before then.
3. Read the gateway log, the device's verification status, and the integration's
   readiness.
4. Activate the integration.
5. Let one scheduled cycle run, then read the attendance events and the run.
6. Separately, set the integration to `DISABLED` with an outstanding request and
   confirm the gateway leaves the terminal alone.

## Expected Result

1. The gateway contacts the terminal and reports it: the device becomes
   `VERIFIED` with the serial it actually read.
2. **Nothing else happens on that pass.** No attendance is read, no events are
   queued or uploaded, and no `IntegrationRun` is recorded — a verification is
   not a sync. The integration is still `UNVERIFIED` / `isActive = false`,
   because verifying a device does not activate anything.
3. The verification happens **once**, not on every cycle. The gateway
   acknowledges the request locally even though it skipped the sync that
   normally does the acknowledging.
4. Readiness then reports `deviceVerified: true` and `blockers: []`, and
   activation succeeds where it previously returned 400 "This integration is not
   ready to activate."
5. Only after activation does a cycle read attendance: records outside the
   import window are excluded, malformed records are dropped rather than
   guessed at, and the rest arrive as `RawAttendanceEvent` with their raw codes
   unchanged.
6. A `DISABLED` or `ERROR` integration is never dialled, however old the
   outstanding request is.

## Notes

Created 2026-09-09 at `aff47c47`, guarding [[BUG-2732]] — two safety rules that
composed into a deadlock so that no on-premise integration could ever be
activated.

`AUTOMATION_STATUS` is **PARTIAL** and the reason matters. The automated test
covers step 6, the DISABLED/ERROR boundary, which is where a careless fix would
do damage. Steps 1 to 5 span an API, a separate .NET service, a child process
and a database, and were verified by rehearsal rather than by a suite: on
2026-09-09 a device left `UNVERIFIED` since 31 August verified within one
refresh, and the integration then activated with `blockers: []`.

Re-running by hand costs about ten minutes and needs no hardware. Point a paired
gateway at `DijiPeople.Gateway.FakeWorker` — with no `DIJI_FAKE_WORKER_MODE` set
it answers whichever operation it was actually asked for, so one process serves
the whole sequence.
