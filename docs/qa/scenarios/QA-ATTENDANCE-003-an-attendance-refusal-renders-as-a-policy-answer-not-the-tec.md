# QA-ATTENDANCE-003 — An attendance refusal renders as a policy answer, not the technical error dialog

## Preconditions

- An employee whose work arrangement is on-site only, or any other configuration
  that produces a refusal the engine has a reason code for.
- Location capture working — QA-ATTENDANCE-002 passing is a prerequisite, since
  a refusal cannot be reached until a position can be captured.

## Steps

1. Check in from a position that will be refused (for an on-site-only employee,
   anywhere outside a work site geofence).
2. Read `errorCode` in the `POST /api/attendance/check-in` response body.
3. Look at what the screen shows.

## Expected Result

- Step 2: `errorCode` is the engine's own reason code — for this case
  `WORK_MODE_DISALLOWS_REMOTE`. It must **not** be `VALIDATION_FAILED`, which is
  the erasure BUG-2332 describes.
- Step 3: the employee sees the refusal sentence alone. No `ERROR ...` heading,
  no reference id, no **Download log** button. A refusal is the system working,
  and the technical dialog is for defects.

Repeat for at least one location refusal (`ACCURACY_TOO_LOW`) and one work-site
refusal (`WORK_SITE_REQUIRES_DEVICE`) — the classifier branches differ and only
the work-mode branch has been observed end to end.

## Notes

Created 2026-08-30 at `f77c0abb`.

`LAST_RESULT: FAIL` records the 2026-08-30 run against production, which is what
produced BUG-2332: `errorCode` came back `VALIDATION_FAILED` and the technical
dialog opened over the friendly message. Re-run after the fix deploys.

Known still-open gap: even with the reason code preserved, the structured
evidence (`fallbackAvailable`, `accuracyMeters`, `requiredAccuracyMeters`) is
dropped by the exception filter, because the attendance throw puts it at the top
level of the payload and the filter only forwards `details`. So the accuracy
sentence and the "Request Web Attendance" fallback still cannot render. That is
recorded in BUG-2332 as deliberately out of scope for its fix.
