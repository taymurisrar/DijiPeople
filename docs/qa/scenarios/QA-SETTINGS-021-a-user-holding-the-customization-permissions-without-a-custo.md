# QA-SETTINGS-021 — A user holding the customization permissions without a customizer role uses every Customization page

## Preconditions

- A tenant on a throwaway database (then the demo tenant after release).
- User A: role `system-admin` holding every `customization.*` key, and neither
  `global-admin` nor `system-customizer`.
- User B: only a custom role granted `customization.read` and
  `customization.tables.read` (no columns, forms or views read).
- User C: no `customization.*` key at all.
- At least one module, one package and one draft component exist.

## Steps

1. As user A, open `/settings/customization`, `/settings/customization/modules`,
   a module detail `/settings/customization/tables/<key>` and each of its tabs,
   `/settings/customization/packages`, one package, `/settings/customization/publish-center`,
   the form designer and the view designer.
2. As user B, open `/settings/customization/modules`, then
   `/settings/customization/tables/<key>`.
3. As user C, open any `/settings/customization/*` route, then call
   `GET /api/customization/tables` directly.
4. As a user holding `customization.read` but not `customization.publish`, try
   Publish in Publish Center; as one without `customization.packages.manage`,
   try New package.
5. After release: remove the temporary System Customizer role from the demo
   workspace owner and repeat step 1 as that owner.

## Expected Result

- Step 1: every page renders its data; no server error page, no error digest.
- Step 2: the modules list loads; the module detail shows the in-place Access
  denied state with the URL unchanged.
- Step 3: Access denied in place on every route; the API answers 403 with
  `CUSTOMIZATION_PERMISSION_REQUIRED`.
- Step 4: publish is refused without `customization.publish`; package create is
  refused without `customization.packages.manage`.
- Step 5: identical to step 1.
