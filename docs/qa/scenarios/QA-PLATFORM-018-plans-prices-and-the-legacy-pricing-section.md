# QA-PLATFORM-018 — Plans, prices and the legacy pricing section

## Preconditions

A database whose commercial catalogue predates 2026-08-20 — or any database
where `npm run report:commercial` disagrees with `pricing.catalog.ts`.

Platform Admin access. `STRIPE_MODE=test`, so nothing here can touch a live
Stripe account.

**Take a backup first.** This scenario runs a reconcile that deactivates rows.
Nothing is deleted, but "nothing is deleted" is not the same as "nothing
changed".

## Steps

1. `npm --workspace api run test -- commercial-bootstrap.reconcile`
2. `npm --workspace admin run test -- plan-record-form`
3. `npm run report:commercial` — record the output. This is the before.
4. `npm run seed:commercial`. Read the counters **and the warnings**.
5. `npm run report:commercial` again.
6. `npm run seed:commercial` a second time, with nothing changed in between.
7. Open a plan in Platform Admin, Pricing tab.
8. Open the Plans list.
9. Open the public pricing page for a Qatar visitor and for a Pakistan visitor.
10. Change one amount in `pricing.catalog.ts`, run the seed again, and read that
    price back in Admin.

## Expected Result

Step 3, on a stale database: prices that are not the catalogue's. The state
recorded at `99dc70a` was eight active prices, all FLAT, all `SELF_SERVICE`,
all USD, four with no market, none for `starter`.

Step 4: the run reports what it changed and warns about each retirement and
supersession by name. A run that reports only totals has hidden the part that
needs acting on.

Step 5: **36 active prices** — 3 plans x 3 markets x 2 cycles x 2 models. Every
FLAT row reads `SALES_ASSISTED`; every per-seat row reads `SELF_SERVICE`. PKR,
QAR and USD each appear. No row has a null market. Every annual amount is
exactly ten times its monthly one.

Step 6: **zero writes.** `0 created, 0 superseded, 0 retired`, everything
`already on catalogue terms`, no warnings. This is the step most likely to be
skipped and the one that matters most — see the note below.

Step 7: no "Legacy pricing compatibility" section, and no `currency`,
`monthlyBasePrice`, `annualBasePrice` or `legacyPricingMigratedAt` anywhere on
the form — including under "Additional details", which is where they reappeared
when the declarations alone were deleted.

Step 8: the list does not lead with a legacy price column.

Step 9: per-seat prices only, in QAR and PKR respectively. **No flat price is
reachable from either page.**

Step 10: the new amount is live, on a new price row whose version is one higher,
whose `supersedesPriceId` names the old row, and which reports itself **not
checkout-ready** until it is synced to Stripe.

## Notes

Step 6 is the acceptance criterion for the whole change. A reconciler that
rewrites correct rows is worse than one that never runs: `seed:config` executes
on every deployment through `release:api`, so a non-idempotent reconcile would
re-stamp `publishedAt` and detach every price from Stripe on each deploy. If
step 6 reports any write at all, stop — the drift detector is comparing
something it should not, most likely a `Prisma.Decimal` against a JavaScript
number, which is never `===` and so reports drift forever.

Considerations:

- **Seeded prices are published and unbuyable, and that is correct.**
  `deriveCheckoutReadiness` requires a verified, synced, active Stripe price and
  the seed creates none. Publication is a catalogue decision; sellability is a
  Stripe fact. Expect `stripe:NOT_SYNCED` on all 36 and do not read it as a
  failure.
- **A plan carrying subscriptions is never deactivated**, only withdrawn from
  sale. If a plan the catalogue dropped has customers, step 4 warns and leaves
  it active — verify those customers still render, because that is the whole
  reason for the exception.
- `enterprise-plus` deliberately has **no** price. The offer resolver answers
  `CUSTOM_CONTRACT_ONLY` for it. An Enterprise+ row appearing in step 5 is a
  defect, not a gap being filled.
- Step 9 is the one with money attached. Flat is roughly 60% more than per-seat
  at the small end and roughly 69% less at the large end; that spread is why it
  is quoted by a person, and a `SELF_SERVICE` flat row on the public site is
  BUG-0531 returning.
