# QA-AUTHZ-015 — Sibling endpoints on one permission pair enforce one shared rule

## Preconditions

An actor holding `roles.assign-permissions` and `SETTINGS:configure` but not
`payslips.read-all`. A second actor whose effective employee access level is
`SELF` or `TEAM`, and an employee record outside that scope.

## Steps

1. As the first actor, attempt to grant `payslips.read-all` to an editable role
   through `updatePermissions`, then `update`, then `create`.
2. Rename a broader role without touching its permissions.
3. As the second actor, request the profile CSV export for the out-of-scope
   employee.
4. Request the same record through `GET /employees/:employeeId`.

## Expected Result

- All three role-writing paths refuse the key the actor does not hold.
- Renaming a broader role **succeeds** when permissions are untouched: the check
  guards widening, not editing, so an actor is not blocked from tidying a role
  somebody else built.
- The export refuses the out-of-scope record, matching what the read path already
  refuses. An export that skips the row-scope its sibling read applies is a BOLA:
  it hands over in bulk what the caller cannot fetch one at a time.
- Spies confirm each site calls the shared method, because this defect's shape is
  a call site drifting from a rule while still answering correctly for whichever
  cases a test happens to cover.
