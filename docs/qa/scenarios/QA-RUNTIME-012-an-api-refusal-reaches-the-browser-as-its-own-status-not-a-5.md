# QA-RUNTIME-012 — An API refusal reaches the browser as its own status, not a 500

## Preconditions

A running API and web app, and a user lacking a permission some screen needs.

## Steps

1. `npm --workspace web run test -- proxy-error`.
2. `npm run check:proxies-forward-status`.
3. Manual form: trigger a validation failure through a runtime form, and a
   permission failure through a screen the user cannot use.

## Expected Result

Steps 1 and 2 pass. In step 3 the browser receives **422 with `fieldErrors`**
for the validation failure, so the form can highlight the offending field, and
**403** for the permission failure, so the access-denied state renders rather
than a generic error.

`traceId` is present on both, so the user's report can be matched to the API's
error log. A genuine crash inside a handler is still a 500 — that distinction
is the point.
