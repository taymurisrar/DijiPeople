# QA-ATTENDANCE-005 — A browser location failure renders its own reason with the right retry

## Preconditions

- A tenant workspace with attendance enabled, signed in as an employee.
- QA-ATTENDANCE-002 passing — the Permissions-Policy header must allow the site
  to ask, or every case below fails identically as PERMISSION_DENIED and the
  scenario measures nothing. That is precisely how BUG-2334 stayed hidden.

## Steps

Exercise each failure from the attendance module's **own Check In button**, not
the generic runtime command handler — there are two capture paths and the other
one has always behaved correctly, so testing the wrong one passes while the
defect is live.

1. **Denied** — deny the browser's location prompt, then press Check In.
2. **Position unavailable** — switch off OS location services and press Check In.
3. **Timeout** — throttle or block the location provider so the capture exceeds
   the tenant's `locationTimeoutSeconds` (15 by default).
4. **Unsupported** — a browser or context with no `navigator.geolocation`.

## Expected Result

Each case shows its **own** message, and none opens the platform's technical
error dialog — no `ERROR …` heading, no reference id, no Download log button.

| Case | Message theme | Retry offered |
|---|---|---|
| Denied | allow location access, then try again | yes |
| Position unavailable | turn on location services | yes |
| Timeout | took too long, move near a window | yes |
| Unsupported | web attendance unavailable on this browser | **no** |

The Unsupported row is the one worth being strict about: a browser without
geolocation fails identically forever, so offering Try again is a lie. Before
BUG-2334 was fixed, all four rendered the same generic failure *and* the
technical dialog.
