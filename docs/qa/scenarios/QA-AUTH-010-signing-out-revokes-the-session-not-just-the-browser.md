# QA-AUTH-010 — Signing out revokes the session, not just the browser

## Preconditions

A signed-in tenant session with all three cookies present, a signed-in platform
admin session, and — for the live form of this scenario — more than twenty live
refresh tokens issued for the same client since the session under test began.

## Steps

1. Sign out with the access, refresh and session cookies all present.
2. Assert the revocation was issued against
   `{ sessionId, appClientId, revokedAt: null }`, not against a scan of recent
   token hashes.
3. Replay the captured refresh token at `POST /api/auth/refresh`.
4. Repeat with only the session cookie present, which is the state after a
   session-expired modal.
5. Repeat as a platform admin and confirm `PlatformRefreshToken` is revoked and
   `RefreshToken` is not.
6. Sign out with no session cookie at all.
7. Sign out twice and compare `revokedAt`.

6. With the same signed-out access token, call `GET /auth/me` as well as a
   guarded route such as `GET /employees`. Both must refuse it. `/auth/me` is
   `@Public()` and used to answer 200 while `/employees` answered 401 — see
   BUG-2547.

## Expected Result

Steps 1, 4 and 5 revoke exactly one session. Step 3 is refused. Step 6 clears
the browser and claims nothing. Step 7 leaves `revokedAt` at the moment of the
first sign-out.

## Why this scenario exists

The ordinary sign-out did not revoke anything. Exact revocation by session id
ran only when the refresh cookie was *absent*; with it present, logout fell
through to a bcrypt scan of the twenty newest live tokens for the client, across
the whole deployment, with no tenant, user or session filter. Past twenty, the
signer-out's own token was not in the list, and their session stayed resumable
for up to thirty days.

**A bound that reads as an optimisation can be a correctness limit.** `take: 20`
looks like a sensible cap on a hash scan. It made the control fail more reliably
the busier the system got — weakest exactly when it mattered most. Where you
already know the key of the row, revoke by it; do not search for it.

## Re-run guidance

The live form needs step 0: twenty logins, to push the token under test out of
the scan window. Without that precondition the old code passes this scenario,
which is precisely how it survived. Mind the login budget — twenty writes per
ten minutes per IP — and use more than one source address, or drive it through
the service rather than the endpoint.

Note while here that remember-me on the platform path has no policy able to
refuse it, which is what makes the unrevoked window as long as thirty days. That
is [[BUG-2509-platform-admin-remember-me-has-no-policy-able-to-refuse-it]],
pinned by the same spec and awaiting a product decision.
