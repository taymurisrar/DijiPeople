# QA-TENANT-039 — Runtime form controls have accessible names

## Preconditions

- Platform Admin, signed in as a `PLATFORM_OWNER`.
- axe-core, or a browser extension running it.

## Steps

1. Run `npm --workspace admin run test -- form-accessibility`.
2. Open **Leads → New**, **Partners → New**, **Customers → New** and
   **Contracts → New**.
3. Run axe-core on each.
4. Tab through one form and listen to what each control announces.
5. Trigger a validation error and check the control announces it.

## Expected Result

- The suite passes.
- axe reports **0** controls with no accessible name. The number to compare
  against is 28.
- Each control announces its visible label.
- An invalid control announces the error text rather than only showing it.
- A password manager or autofill offers values, which it could not before.

## Notes

`/plans/new` and `/templates/new` are bespoke forms and were always clean — they
are the control group, not a target. If they ever fail this, the cause is
different from the one this scenario covers.

Composite controls take a different route: a searchable select renders a button
and a listbox, so it cannot be the target of `htmlFor` and points at the label
with `aria-labelledby` instead. Both routes should announce the same words.

The count is what matters on a re-run. A form that improves from 28 to 3 has not
passed.
