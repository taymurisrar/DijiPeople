# QA-RUNTIME-032 — A feed that would have 404d even after the release it was waiting for

## Preconditions

A tenant on which the affected surface is reachable, and a signed-in user with
the permissions the surface requires. REG-358 in the regression register carries
the full root cause; this scenario is the reusable check, not the diagnosis.

## Steps

Asking for the URL alias queries the catalogue key; passing the catalogue key directly still works; the artefact-by-filename lookup resolves the alias too, since electron-updater derives the download URL from the feed and a fix to only one half would leave the download 404ing; an app outside the catalogue serves nothing and does not fall through to an unfiltered query.

## Expected Result

The behaviour holds as REG-358 describes it. The automated guard is `services/api/src/modules/app-releases/update-feed.service.spec.ts`; a run of that suite is sufficient evidence for this scenario.

## Why This Is Reusable

The publisher and the update feed disagreed about what an application is called. `release-publisher.service.ts` persists `appKey` from the catalogue — `APP_KEYS.AGENT_DESKTOP`, the string `AGENT_DESKTOP`
