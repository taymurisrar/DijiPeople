# QA-DEPLOY-017 — A deploy never changes an existing platform super admin

## Preconditions

The automated part needs nothing: `decideAdminSeedAction` is exported from
`services/api/src/common/utils/admin-seed.util.ts` and is pure, which is why it
was extracted from the script in the first place.

The end-to-end part needs a reachable local PostgreSQL and a **throwaway**
database with the migration chain applied. Never run it against the populated
`dijipeople` development database.

This scenario exists because `seed:admin` runs inside `npm run release`, which
`render.yaml` sets as `preDeployCommand`. Everything below therefore describes
what happens on a real deploy, not a helper's edge cases.

## Steps

1. Run `npm --workspace api run test -- admin-seed.util`.
2. For the end-to-end part, against a throwaway database with all migrations
   applied and a super admin already seeded:
   - re-run `seed:admin` with a **different** `PLATFORM_SUPER_ADMIN_PASSWORD`;
   - re-run `seed:admin` with **no** admin variables set at all;
   - re-run `seed:admin` with `PLATFORM_SUPER_ADMIN_PASSWORD_RESET=true`.
   Read `left("passwordHash", 16)` from `PlatformUser` before and after each.
3. Against a **virgin** migrated database with no admin variables, run
   `seed:admin` and observe the exit code.

## Expected Result

| Situation | Required outcome |
|---|---|
| Redeploy, different password in the environment | `SKIP`. The stored hash is **unchanged**. |
| Redeploy, no variables set, an active super admin exists | `SKIP`, exit 0. Hash unchanged. |
| `PLATFORM_SUPER_ADMIN_PASSWORD_RESET=true` | `RESET`. Hash changes; role and status restored. |
| Virgin database, no variables set | Fails loudly, exit 1, with a message naming the variable and why. |
| Virgin database, variables set | `CREATE`. |

The second row is the one that matters most and is easiest to lose: it is what
lets an operator **remove the password from the deployment dashboard** after
bootstrapping, instead of leaving a live credential there forever to keep
deploys green.

## Notes

The original defect had no third configuration: unset aborted `preDeployCommand`
on a new environment — taking `seed:legal` and `legal:publish` down with it — and
set reset the super admin's password on every deploy, including a password just
rotated because it leaked.

**Re-running this scenario is worth more than it looks.** CI sets both variables
against a fresh database, so CI exercises only the `CREATE` path; every other row
in the table above is invisible to it. That is exactly why the defect survived to
the eve of a production release.

When re-running, assert the reset and non-reset cases **as a pair**. Checking
only that `_PASSWORD_RESET=true` resets would also pass against the original
code, which reset unconditionally.
