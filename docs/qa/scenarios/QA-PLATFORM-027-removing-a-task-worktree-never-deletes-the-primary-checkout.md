# QA-PLATFORM-027 — Removing a task worktree never deletes the primary checkout

## Preconditions

A repository with at least the primary checkout. The scenario creates and
destroys its own fixtures and must never be pointed at a real task worktree
somebody is using.

## Steps

**A — the structural half, run by `npm run validate:framework`.**

1. `scripts/remove-worktree.mjs` exists and is exposed as
   `npm run worktree:remove`.
2. It refuses the primary worktree by name.
3. It refuses a path that is not a registered worktree.
4. It finds reparse points *without descending into one*, and unlinks them with
   `rmdirSync`/`unlinkSync` — never a recursive delete.
5. It verifies the primary's sentinel paths after removing, and prints the
   `git restore .` recovery if they are gone.
6. Both documents that teach the worktree lifecycle name the script.

**B — the live half, run by hand when the guard changes.**

```bash
# a canary the junction will point at
mkdir ../wt-guardtest-canary
for i in 1 2 3 4 5; do echo x > ../wt-guardtest-canary/precious-$i.txt; done

git worktree add ../wt-guardtest --detach HEAD
cmd /c mklink /J ..\wt-guardtest\node_modules ..\wt-guardtest-canary

node scripts/remove-worktree.mjs ../wt-guardtest
ls ../wt-guardtest-canary | wc -l     # must still be 5
```

## Expected Result

**A** — every check passes, and each one fails when the behaviour it names is
removed. A check that passes against a guard with its refusal deleted is not
guarding anything.

**B** — the worktree is gone, the junction is unlinked, and **all five canary
files remain**. The guard prints `Primary checkout verified intact.`

Run unguarded, `git worktree remove --force` empties the canary instead. That is
the whole defect: the delete follows the junction, and Git reports only that the
*worktree* directory was non-empty — never that it emptied something else.

## Notes

From BUG-1494. On 2026-08-26 the unguarded command removed 3,072 tracked files
from the user's primary checkout, plus every installed dependency and the
generated Prisma client, because a task worktree's `node_modules` was junctioned
to the primary's and npm workspaces links back out of `node_modules` into
`apps/*`, `services/*` and `packages/*`.

Mutation-tested the same day: deleting the primary-worktree refusal fails 1
check; replacing `rmdirSync(link)` with a recursive delete fails 2.

**Recovery, if it happens again.** Check first, then act — in that order:

```bash
git status --short          # every entry must be ` D`, and nothing `??`
git restore .               # additive only *because* of the line above
npm ci                      # node_modules is gitignored; restore cannot help
npm run prisma:generate     # nor can it restore the generated client
```

`git restore .` is safe only when every entry is a deletion. With real edits
mixed in, the same command destroys them — which is why the check is a step and
not an aside.
