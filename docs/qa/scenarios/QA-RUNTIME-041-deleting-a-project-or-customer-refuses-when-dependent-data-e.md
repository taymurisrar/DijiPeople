# QA-RUNTIME-041 — Deleting a project or customer refuses when dependent data exists, succeeds when it does not

## Preconditions

- A tenant with `projects.delete` / `customers.delete` granted (the `hr` and
  `system-admin` base roles carry both after this fix).
- A project with at least one assignment, timesheet entry or payroll
  cost-allocation line, and a project with none of the three.
- A customer with at least one project, and a customer with none.

## Steps

1. `npm --workspace api run test -- projects.service customers.service`
2. Against a live tenant: `DELETE /api/projects/:id` for a project that has an
   active assignment.
3. `DELETE /api/projects/:id` for a project with no assignments, timesheet
   entries or cost-allocation lines.
4. `DELETE /api/customers/:id` for a customer that still owns a project.
5. `DELETE /api/customers/:id` for a customer with no projects.
6. Repeat step 2 or 4 for an id that does not belong to the tenant, or does not
   exist.

## Expected Result

- Step 1: the suite passes, including `ProjectsService.remove` and
  `CustomersService.remove`.
- Step 2: **409**, `errorCode` `PROJECT_DELETE_HAS_DEPENDENTS`, naming the
  dependent counts. The project and its assignment are unchanged, and no audit
  row is written for a deletion that did not happen.
- Step 3: **200** (or the route's success shape), the project is gone, and an
  audit row is written with `action: PROJECT_DELETED`, a `beforeSnapshot` and a
  `null` `afterSnapshot`.
- Step 4: **409**, `errorCode` `CUSTOMER_DELETE_HAS_DEPENDENTS`, naming the
  project count. Before this fix there was no `DELETE` handler on
  `CustomersController` at all, so this request 404'd on the route itself
  rather than being refused for a reason.
- Step 5: the customer is deleted, with an audit row `action: CUSTOMER_DELETED`.
- Step 6: **404**, not a 409 or a 200 — the tenant-scoped lookup must not find
  a record belonging to another tenant or one that never existed.

## Notes

**The route not existing was the defect, not a wrong answer from it.** Before
this fix `DELETE /api/projects/:projectId` returned the framework's bare 405
(the only declared `DELETE` was on `:projectId/assignments/:assignmentId`), and
`customers.controller.ts` had no `DELETE` handler to call at all — `customers.
delete` existed as an unused legacy permission key with nothing consuming it.

**The dependent-data check exists because the database would not have refused
on its own.** `ProjectAssignment.project` cascades on delete, and
`TimesheetEntry.project` / `PayrollCostAllocationLine.project` both `SetNull`
their `projectId` — so an unchecked delete would either silently destroy
assignment history or silently orphan timesheet and payroll records, not fail.
`Customer.projects` **is** `onDelete: Restrict` at the database level, so
without the service-level check step 4 would still refuse, but as a raw
Postgres foreign-key violation rather than a catalog `AppError` naming the
cause.

**Retire-by-status was considered and rejected.** BUG-2007 asked whether
cancel-only was the intended model; the repository owner decided on
2026-09-11 to add real delete instead, tenant-scoped, refusing with a reasoned
error rather than cascading.
