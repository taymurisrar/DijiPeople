# QA-SETTINGS-006 — A settings catalog that could declare keys nothing read

## Preconditions

A tenant on which the affected surface is reachable, and a signed-in user with
the permissions the surface requires. REG-325 in the regression register carries
the full root cause; this scenario is the reusable check, not the diagnosis.

## Steps

Every catalog key is either read by production code or listed in `INERT_TENANT_SETTING_KEYS` with a reason code. The check fails in four directions: a declared key that nothing reads and nothing exempts; a key listed as inert that something now reads; an editable control for an inert key; and an inert entry naming a key the catalog no longer declares. The reader index is built by walking the repository and tokenising every code file, excluding the catalog, the dispositions list, the two settings UI config files, specs, `e2e/` and `docs/`. The UI side is a `(category, key)` **pair** test and reads the `timesheetField(...)` and `payrollValidationField(...)` factories explicitly.

## Expected Result

The behaviour holds as REG-325 describes it. The automated guard is `services/api/src/modules/tenant-settings/tenant-settings-reader-coverage.spec.ts`; a run of that suite is sufficient evidence for this scenario.

## Why This Is Reusable

Nothing required a declared setting key to have a reader. The catalog declared 591 keys; 246 had no reader anywhere in the monorepo and 230 of those were rendered as live, editable controls
