# QA-PROV-005 — A tenant reaches ACTIVE and its owner can sign in

## Preconditions

Against a real PostgreSQL, with the API booted from `AppModule` and driven over
HTTP:

- a tenant at `PENDING_SETUP` with an organization and a business unit;
- an `ACTIVE` subscription to a plan;
- one `ACTIVE` user holding the `global-admin` role — the owner rule counts
  those, so the role and the assignment are both fixture, not just the user;
- a platform operator who **signs in** through `POST /api/admin/auth/login`
  rather than holding a hand-minted token.

The tenant starts at `PENDING_SETUP` on purpose. `Tenant.status` defaults to
`ACTIVE` in the schema, and a fixture that took the default would make every
assertion here vacuous.

## Steps

1. Attempt activation. It is refused — the workspace has no address.
2. Attempt an owner sign-in. It is refused — the tenant is not `ACTIVE`.
3. Issue the primary system subdomain and mark platform wildcard DNS ready.
4. Activate, with a reason.
5. Read the `Tenant` row back: `status` and `subStatus`.
6. Sign in as the owner again.
7. Read the audit trail for a `TENANT_LIFECYCLE_CHANGED` entry naming `ACTIVE`.
8. Fetch all eight tenant tabs as the operator: overview (and readiness),
   configuration, access, commercial, modules, apps, operations, timeline,
   system.
9. Re-read readiness and confirm no owner or reachability blocker stands.

## Expected Result

Steps 1 and 2 refuse. Steps 4–9 succeed, and step 5 reads the state from the
record rather than the response.

## Notes

This is the end of the primary commercial journey, and until 2026-08-22 it had
never been observed. The 2026-08-15 commercial onboarding run proved five
activation gates and reached none of this, because [[BUG-0015]] stranded the
tenant with no owner; its verdict recorded `TENANT_PROVISIONING = FAIL`. See
[[ITEM-0004]].

**The owner sign-in is a pair, not one assertion.** Refused before, accepted
after, against the same account. Asserting only the second would pass on a build
where a suspended workspace never locked anybody out — the half with the security
consequence.

**One gate is re-driven rather than cited.** A16.01–A16.05 cover the gates
already, and repeating them would be waste; the routing refusal is re-driven
because without a refusal immediately before it, "activation succeeded" is
consistent with a build where the gate was deleted.

**Step 8 is A17 at the level that decides whether a tab has anything to show.**
The eight names come from `TENANT_PANEL_TABS`; each is rendered from the
control-plane endpoint driven here. A browser would additionally prove the panels
paint — it would prove nothing more about the tenant, and this runs in CI on
every push, which A17 never did.

The suite also pins [[ITEM-0079]]: the tenant reaches `ACTIVE` with the
`modules` readiness blocker still standing, so its owner signs in successfully
and finds nothing to open. That assertion states today's behaviour deliberately —
if the gate is ever extended, it fails, and the failure is the reminder.
