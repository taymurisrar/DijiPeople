# QA-TENANT-011 — A workspace URL resolves on every surface that renders one

## Preconditions

A tenant with an issued workspace hostname, in a development environment where
`TENANT_BASE_DOMAIN=localhost` and the web app is on 3001.

## Steps

1. `npm --workspace api run test -- workspace-url`
2. `npm --workspace admin run test -- open-external`
3. Open the tenant record → Configuration and read **Workspace URL**.
4. Follow it.
5. Press **Open Tenant** on the record, and again from the list with one row
   selected.
6. With pop-ups blocked for the site, press **Open Tenant** again.
7. Open a tenant with no workspace slug and press **Open Tenant**.

## Expected Result

Step 3: `http://xoul-ltd.localhost:3001` — the port the web app listens on, and
`http`, not `https`.

Step 4: the workspace login loads.

Step 5: a new **tab** opens, not a popup window.

Step 6: the message says the browser blocked it and includes the URL, and the
action reports failure rather than success.

Step 7: refused, saying the tenant has no workspace slug.

## Notes

Step 6 is the one that matters and the one a casual run skips. The reported
symptom was "Open Tenant still doesnt do anything" beside a green toast reading
"Tenant workspace opened." — a features string turned the call into a popup
request and the `null` return was discarded.

Consideration: this rule has now had five implementations. If a new surface
renders a workspace link, check it calls `buildWorkspaceUrl` rather than
building one — the automated half asserts the absence of the template-literal
shape precisely because counting call sites passed while a third one existed.
