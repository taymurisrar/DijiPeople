# QA-PLATFORM-023 — Runtime form validation names the field it rejected

## Preconditions

A platform user signed in to the admin console. Any metadata-driven module whose
create form routes through `POST /platform-runtime/:moduleKey/validate` — leads,
customers, partners, support cases and contracts all do.

## Steps

1. Open a runtime create form, e.g. `/leads/new`.
2. Fill the fields marked with an asterisk, giving at least one of them a value
   its DTO rejects — a work email of `not-an-email` is enough.
3. Press **Save and close**.
4. Read the response to `POST /api/platform-runtime/leads/validate`, and read
   the form.

## Expected Result

The response carries the reason **and** the field it belongs to:

```json
{
  "success": false,
  "message": "workEmail must be an email",
  "errors": [{ "field": "workEmail", "message": "workEmail must be an email" }]
}
```

The form renders that message beneath the work email field.

The user-facing message is **never** the string `Bad Request Exception`. That
string is the name of a Nest exception class, and its appearance means the
payload carrying the real reasons was discarded — the defect in BUG-1422.

A failure that is not a validation error — a `NotFoundException`, say — still
answers with `success: false`, its own message, and an empty `errors` array,
rather than throwing again inside the handler.
