# QA-AUTH-006 — A tenant workspace URL survives a multi-label root domain

## Preconditions

- An `ACTIVE` tenant whose workspace is served at `<slug>.ws.dijipeople.com`.
- The `apps/web` production deployment built **since** the last change to
  `NEXT_PUBLIC_WEB_ROOT_DOMAIN`. This precondition is the whole point of the
  scenario: the setting and the running bundle can disagree.

## Steps

1. Run `npm --workspace web run test -- tenant-root-domain`.
2. `GET /api/public/tenants/resolve?slug=<slug>` and again with
   `?host=<slug>.ws.dijipeople.com`.
3. In a browser, open `app.dijipeople.com/login`, enter the slug, press
   Continue.
4. Open `<slug>.ws.dijipeople.com/login` directly.

## Expected Result

- Step 1 passes, both directions covered.
- Step 2 returns `200` for **both** query forms with the same tenant.
- Step 3 navigates to `https://<slug>.ws.dijipeople.com/login` — with the `ws.`
  label present — and the page renders a credential form.
- Step 4 presents the credential form directly, with no company-code step, and
  names the tenant in its heading.

## Notes

Steps 3 and 4 are the ones that matter and the ones most easily skipped. The API
resolves the workspace correctly even while the browser cannot reach it, so
step 2 passing proves nothing about the customer's experience — that asymmetry
is exactly how BUG-1644 survived to a paying customer.

Two failure modes produce identical symptoms here: a wrong value, or a correct
value in a bundle built before it was set. They cannot be told apart from the
browser. Before reporting the value is wrong, check whether a production build
has happened since it changed — assuming the wrong one sends someone to edit a
setting that was already correct.

Judge step 4 by the tenant name in the heading, not by the page's colours. A
non-existent workspace subdomain still renders a branded-looking login using the
platform defaults, which reads as tenant branding and is not.
