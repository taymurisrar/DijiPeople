# QA-PROV-006 — Customer-facing URLs resolve on the customer domain in production

## Preconditions

The four production values as the Render service now holds them:
`WEB_APP_URL=https://app.dijipeople.com`, `WEB_APP_PROD_ROOT_DOMAIN=ws.dijipeople.com`,
`NEXT_PUBLIC_WEB_ROOT_DOMAIN=ws.dijipeople.com`, `APP_ENV=production`. No
database, no network.

## Steps

1. Build a tenant login URL.
2. Build a tenant activation URL with a token.
3. Assert neither contains a deployment host.
4. Clear the root-domain variables and build a login URL again.

## Expected Result

1. and 2. `https://{slug}.ws.dijipeople.com/...` — the workspace address the
   platform actually issues that tenant.
3. No `vercel.app`, no `onrender.com`, HTTPS in both.
4. Falls back to `https://app.dijipeople.com` — a *shared* host rather than a
   *wrong* one.

## Notes

These URLs are mailed to customers. [[BUG-0714]] had every one of them pointing
at `diji-people-web.vercel.app`, which resolves, fails no request, and simply
sends a paying customer somewhere that is not their address.

Step 4 documents the half-configured state rather than endorsing it. Production
had `TENANT_BASE_DOMAIN` set — read by the hostname *issuer* — and
`WEB_APP_PROD_ROOT_DOMAIN` absent, which the URL *builder* reads. Two variables
for one concept, and setting half is not an error today.

**Why this scenario is separate from `tenant-url.config.spec.ts`.** That file has
a passing test asserting `https://diji-people-web.vercel.app/login`. It is a true
statement about the function and it encoded the misconfiguration as the expected
result, so the suite agreed with production and both were wrong together. Those
tests describe the function across configurations; this one describes the
configuration DijiPeople deploys.
