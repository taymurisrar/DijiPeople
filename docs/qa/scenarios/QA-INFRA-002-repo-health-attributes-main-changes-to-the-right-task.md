# QA-INFRA-002 — repo-health attributes main changes to the right task

## Preconditions

- `origin/main` contains at least one merge of `develop` — any release produces
  this, and it is the ordinary state of this repository.
- A checkout whose HEAD is `develop`. The primary checkout normally sits there,
  and it is where a final health check runs once a task worktree is removed.
- The SHA `main` sat at when the task being audited began, to pass as
  `--main-baseline`.

## Steps

Automated coverage — `node --test scripts/task-sha-ref.test.mjs` — pins the
decision. The end-to-end check below is what proves it in the real repository,
and is worth re-running whenever `repo-health.mjs` changes:

1. From a checkout standing on `develop`, run
   `node scripts/repo-health.mjs --main-baseline <baseline>` for a task that
   put nothing on `main`.
2. Confirm none of that task's commits are actually on the production branch:
   `git merge-base --is-ancestor <task sha> origin/main` for each, and
   `git rev-parse main` against the baseline.
3. Run it again with `--task-sha <a commit genuinely on origin/main>`.
4. Run it from a task worktree with no flags, where HEAD is the task branch.

## Expected Result

1. `MAIN_CHANGE_STATUS = UNTOUCHED`, with the count of commits other sessions
   advanced `main` by. **Not** `CHANGED_BY_THIS_TASK`, and no blocker.
2. Every ancestry check reports "not an ancestor", and `main` equals the
   baseline — the two must agree with step 1, since a status that disagrees
   with the ancestry is the defect itself.
3. `CHANGED_BY_THIS_TASK`, **with** the blocker. A `RELEASE` task is supposed to
   report this, and a fix that suppressed it would be worse than the bug.
4. `UNTOUCHED` — the task branch is genuinely not on `main`, and the HEAD
   fallback still works where it is meaningful.

## Notes

Created 2026-08-25 at `ddb457ff`, from a false positive on TASK-0022's own
final health check.

The scenario exists because the failure is **silent in the direction that
matters**. A false `CHANGED_BY_THIS_TASK` is loud and merely wrong; the risk
being guarded is the reverse — that a fix for it might suppress the true
positive, leaving an actual unauthorised mutation of the production branch
unreported. Step 3 is not a formality, and it is the case to re-run first if
this logic is ever touched again.
