# QA-AUTH-020 — TOTP MFA enrolment, sign-in, recovery codes and administrator reset are correct end to end

## Preconditions

`SECRET_ENCRYPTION_KEY` set (and, separately, unset for the negative case); a
tenant user and a platform operator, neither MFA-enrolled.

## Steps

1. Start MFA setup, restart it, then confirm with the current code — check the
   TOTP against RFC 6238 Appendix B at all six published times, ±1 step
   accepted, ±2 refused, replay of an accepted step refused.
2. Confirm setup with a wrong code, then check MFA is still off.
3. View the ten recovery codes once; use one twice; use one on another
   account.
4. Regenerate recovery codes without a current TOTP, then with one.
5. Sign in as the enrolled user/operator: check no tokens/cookies are issued
   before verification, an enrolled-but-unverified session cannot use an
   access-token-guarded route, and a challenge token from one client is
   refused by another.
6. As a tenant global admin, reset another same-tenant user's MFA; attempt to
   reset a user in a different tenant; attempt to reset your own MFA this way.
7. Inspect every audit row and log line touched by steps 1-6 for the seed,
   manual key, otpauth URI, TOTP, password or any recovery code.
8. Start MFA setup with `SECRET_ENCRYPTION_KEY` unset.

## Expected Result

Step 1's HOTP/TOTP match the RFC vectors exactly; the step-window and replay
rules hold. Step 2 leaves MFA off. Step 3's codes work once each, are
account-bound, and case/spacing-insensitive. Step 4 requires a current TOTP,
and invalidates the old set. Step 5's challenge is single-use, client-bound,
and issues tokens only after verification. Step 6's same-tenant reset
succeeds and is audited with the admin as actor; the cross-tenant and self
attempts are refused. Step 7 finds no secret anywhere. Step 8 is refused with
`503` and stores nothing.
