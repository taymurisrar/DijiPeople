# QA-SETTINGS-018 — An event with no notification rule reports Not configured, not Enabled

## Preconditions

A tenant with the notifications module seeded. An administrator with
`notifications.read` (for the read step) and `notifications.manageRules` (for
the write step).

## Steps

1. `GET /notifications/rules`. Find a catalog event this tenant has no
   `NotificationRule` row for (or seed a fresh tenant and pick any claims,
   loans or timesheets event, which have catalog entries and a real trigger
   but no seeded rule).
2. Read that event's `ruleStatus` in the response.
3. Find a different event this tenant DOES have an enabled rule for (e.g.
   `leave.request.submitted.approver`). `PATCH /notifications/rules/:id` with
   `{ "enabled": false }` on its rule.
4. Trigger the underlying action (submit a leave request) and check both the
   in-app notification and, if the rule's event also sends email, the
   `EmailDeliveryLog` for that event.
5. `GET /notifications/rules` again for `AUTH_ACCOUNT_ACTIVATION` and attempt
   `PATCH /notifications/preferences` disabling its EMAIL channel.

## Expected Result

Step 2: `ruleStatus` is `NOT_CONFIGURED`, never `ENABLED` — an event with no
rule must not look identical to a working one. Step 3-4: after disabling the
rule, no new in-app notification is created for that event, and no new
`EmailDeliveryLog` row is created for it either (both dispatch paths honour
the same gate — ITEM-0171). Step 5: the request is rejected with
`NOTIFICATION_EVENT_NOT_CONFIGURABLE`; `AUTH_ACCOUNT_ACTIVATION` reports
`ruleStatus: ALWAYS_ON` and `configurable: false` and can never be turned off
through either endpoint. Every successful rule or preference change in this
scenario writes an `AuditService.log()` entry naming the actor, the entity and
a before/after snapshot.

## Notes

Created 2026-09-12 at `f5f43805`. `notification-rules.spec.ts` covers the read
model (`listRules`) and the audit write (`updateRule`) at the unit level;
`email-execution-rule-gate.spec.ts` covers the email-side gate in
`EmailExecutionService.execute()`. This scenario is the end-to-end path across
both dispatch mechanisms that no single unit test spans.
