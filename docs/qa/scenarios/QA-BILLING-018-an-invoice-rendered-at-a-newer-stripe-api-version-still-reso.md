# QA-BILLING-018 — An invoice rendered at a newer Stripe API version still resolves its subscription

## Preconditions

None. Pure unit scenario over two exported helpers — no database, no Stripe
account, no running service. That is deliberate: the defect is a payload-shape
assumption, and a fixture is a truer test of it than a live call, which would
only ever exercise whichever version that account happens to be configured at.

## Steps

```bash
npm --workspace api run test -- src/modules/billing/invoice-subscription-resolution.spec.ts
```

To confirm the scenario still has teeth, revert both helpers in
`webhook.service.ts` to reading only the flat field:

```ts
// invoiceSubscriptionId
return getStripeId(invoice.subscription);
// invoiceMetadata
return invoice.metadata ?? {};
```

and re-run.

## Expected Result

| | Expected |
|---|---|
| Full suite | 10 passing |
| `dahlia` payload | resolves `sub_1U7WpoHSlnE5ArNFxsF2O6mA`, and metadata carrying `subscriptionOrderId` and `customerAccountId` |
| `clover` payload | still resolves its flat `subscription` and top-level metadata |
| Both present | the `parent` value wins |
| Neither present | `null` and `{}` — **not** a throw; a one-off invoice legitimately has no subscription |
| With the fix reverted | **6 of 10 fail** |

That last row is the scenario. The four that survive the revert are the
legacy-shape and null cases, and they are there so that a future change chasing
the new shape cannot quietly drop the old one.

## Notes

The defect this guards is not really a renamed field — it is a **version skew
nothing asserts**. `STRIPE_API_VERSION` pins outbound calls; Stripe renders
webhook events at the version configured on the *endpoint*. So the handler was
written against `2026-02-25.clover` and exercised against `2026-07-29.dahlia`,
and a dashboard dropdown nobody deployed moved the field out from under it.
It rejected a real PKR 12,000 payment with `400 VALIDATION_FAILED`.

This scenario covers the shape. **It does not cover the skew**, and nothing yet
does — no check compares the pinned version against the endpoint's. Until one
exists this class recurs on any field Stripe relocates, and
`payment_intent` on the same type is the next candidate. Tracked on [[BUG-1128]]
and adjacent to [[ITEM-0094]].

Related: [[BUG-0989]] hid this completely — every delivery failed on signature
before reaching the handler, so two defects were stacked on one endpoint and
fixing the outer one revealed the inner.

Run 2026-08-24 — 10 passing with the fix, 6 failing without it.
