# QA-SETTINGS-003 — A currency conversion uses the rate in force on the date it was given

## Preconditions

Three consecutive `ExchangeRateSnapshot` windows for one currency pair, which is
the shape a rate history actually has:

| Rate | Effective from | Effective to |
|---|---|---|
| 3.60 | 2026-01-01 | 2026-03-31 |
| 3.70 | 2026-04-01 | 2026-06-30 |
| 3.80 | 2026-07-01 | *(open)* |

## Steps

1. Resolve the rate for a date inside each window in turn.
2. Resolve with no date at all.
3. Resolve for a date **before** any window.
4. Convert an amount through `convertMoney`, passing an effective date.
5. Inspect the `where` clause the resolver sent for each lookup.

## Expected Result

1. 3.60, 3.70, 3.80 respectively — one per window, not the newest three times.
2. The open-ended window's rate: the default still means "now".
3. Refused, with the requested date named in the message. "No rate on this date"
   is not the same claim as "no rate exists".
4. The caller's date reaches the resolver, so the converted amount uses that
   window's rate.
5. Every lookup carries `effectiveDate: { lte: at }` and the
   `effectiveEndDate is null OR >= at` pair.

## Notes

Step 5 is not redundant. The behaviour under test is *which rows are eligible*,
and that lives entirely in the Prisma filter — a test that stubbed one row and
checked the returned rate would pass with the filter deleted, because the stub
returns that row whatever is asked for. Asserting the `where` is what makes this
a test of the production query rather than of the double.

Before [[BUG-0668]] was fixed, all three lookups in step 1 returned 3.80.
`convertMoney` forwards its caller's date, so a caller who supplied the right
date still got the wrong number, silently, on money.

Not reachable in production today — `convertMoney` has no callers. This scenario
exists because multi-currency payroll and invoicing are the callers it is waiting
for, and a wrong rate there is a wrong number on a payslip.
