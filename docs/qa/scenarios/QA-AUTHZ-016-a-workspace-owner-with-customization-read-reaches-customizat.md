# QA-AUTHZ-016 — A workspace owner with customization.read reaches Customization without a redirect to Roles

## Preconditions

`apps/web` builds and its jest project runs. No live tenant or session is
needed — `getSessionUser` is mocked directly, since the whole defect was one
function's authorization decision.

## Why This Scenario Exists

`/settings/customization` and its twelve child routes silently redirected to
Roles for the workspace owner: the section's layout gated on role membership
(`GLOBAL_ADMIN`/`SYSTEM_CUSTOMIZER`) while the navigation catalog and every
page under the section gated on the `customization.read` permission. A user
who held the permission but neither role — the workspace owner, as reproduced
live — passed every page's own check and was still thrown out by the layout
before any page ran.

## Steps

1. `npm --workspace web run test -- --testPathPatterns require-settings-permission`

Within that suite: call `requireCustomizationAccess(["customization.read"])`
against a mocked session holding `customization.read` and neither
administrator role (the exact workspace-owner fixture), and separately
against `GLOBAL_ADMIN`, `SYSTEM_CUSTOMIZER`, `SYSTEM_ADMIN` with no explicit
permission grant, a role-and-permission-less user, and no session at all.

## Expected Result

`allowed` is `true` for the permission-only fixture and for all three
administrator roles with no permission grant, `false` for the role-and-
permission-less user and for no session, and the function never redirects —
it returns a value for the caller (the Customization layout) to act on.

## Negative Case

Restoring the old `hasCustomizationAdministratorRole(user) && hasAnyPermission(...)`
gate fails "allows the exact regression case: permission held, neither
administrator role" and "matches requireSettingsPermissions's own model
rather than a second one" — the two assertions that pin the workspace-owner
fixture and the `SYSTEM_ADMIN` case the old, narrower role set excluded.

## Notes

The redirect-to-`AccessDeniedState` half of the fix (no more teleport to a
hardcoded legacy Roles URL) is not exercised here — it needs a rendered
route, and `apps/web`'s jest has no jsdom. It is stated as an acceptance
criterion in [[BUG-3374]] and should be re-run live by a QA pass that can
follow a redirect.
