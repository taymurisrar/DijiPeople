# QA-TENANT-010 — A workspace states what it is missing and repairs what it can

## Preconditions

A tenant that is ACTIVE with no `TenantDomain` row — the reported case. Failing
that, any tenant, to confirm a healthy workspace reports nothing wrong.

## Steps

1. `npm --workspace api run test -- workspace-health`
2. Open the tenant record → **Operations**.
3. Read the **Workspace health** card.
4. Press **Repair workspace**.
5. Reload and re-read the card, and the header's Status reason.
6. Open a healthy tenant and read the same card.
7. Open a tenant with no business unit.

## Expected Result

Step 3: every deficiency is listed at once — not the first one — each saying
whether it is repairable here and what to do if not.

Step 4: the hostname is issued and the contradictory sub-status cleared. If the
tenant base domain is not configured, that specific repair fails with a message
naming it, and the **others still run**.

Step 5: the header no longer shows "Active" beside a status reason of
"Provisioning". Workspace shows the issued hostname.

Step 6: "Nothing is missing", and Repair is disabled.

Step 7: the business-unit finding is Blocking, marked **Needs a person**, and
names BUG-0015. Repair must not claim to fix it.

## Notes

The reported symptom was a tenant that was ACTIVE, reachable and signed into,
reporting "Workspace: Not provisioned" with no recorded provisioning run and a
disabled Retry button. The mistake was reading health off the *record of the
attempt*: a run is evidence a build happened, and a workspace can be perfectly
usable with no run rows at all.

Considerations:

- **Step 7 is the honesty check.** [[BUG-0015]] is open. The provisioning step
  that creates a business unit is not replayed, so a repair that claimed to fix
  it would report success and change nothing — which is BUG-0015's own shape.
- Repair is deliberately narrow: a hostname and a sub-status. It creates no
  owners, subscriptions or invoices. If a future change adds one of those here,
  this scenario should fail on review, not on a duplicated invoice.
- Step 4's partial-failure case matters more than the happy path. One failed
  repair must not abandon the others, and a missing tenant base domain is the
  common cause — a configuration answer, not an error to swallow.
