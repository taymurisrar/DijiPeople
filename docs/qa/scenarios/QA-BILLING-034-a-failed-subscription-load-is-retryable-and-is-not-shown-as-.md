# QA-BILLING-034 — A failed subscription load is retryable and is not shown as access denied

## Preconditions

A user who holds the billing view permission. A second user who holds an
elevated tenant role but not that permission. A way to make the subscription
loader fail — a 500, a timeout, or a malformed payload.

## Steps

1. Navigate to a subscription view and watch the frame between the click and
   the data arriving.
2. Make the loader fail, then reload the view.
3. Use the action offered on the failure state.
4. Sign in as a user holding the permission but no elevated role, and open the
   same view.

## Expected Result

A skeleton renders before data arrives, rather than the previous screen
persisting while three server-side calls resolve.

A failed load renders a retryable error state carrying the trace id, and it is
visually distinct from the access-denied state. A user is never told they lack
permission because a request timed out.

The set of users the screen admits equals the set the API admits. The screen
gates on the same permission keys the API checks, not on elevated role
membership, which the repository's own rules single out as a guard bypass rather
than a gate.

## Notes

Three failures with one cause: the nearest existing full-page failure component
was reused for a different kind of failure, and the loader swallowed its own
errors so it always returned something renderable, which is why no boundary was
ever added.

The permission half is the part worth re-testing by hand. Two authorities
disagreeing about who may see a screen produces no error and no log — it produces
a user who is quietly refused, or quietly admitted and then shown a failure
dressed as a refusal.
