# QA-LANDING-010 — Every direct-API route handler forwards the visitor address

## Preconditions

None beyond a checkout. This is a static property of the source tree, which is
deliberate: the behaviour it protects is only observable in production, under
load, from more than one client — conditions no test environment reproduces
honestly.

## Steps

1. Walk `app/api/` in each of `apps/landing`, `apps/web` and `apps/admin` and
   collect every `route.ts`.
2. Select the handlers that call the API directly — those naming
   `getApiBaseUrl` and calling `fetch(`. Handlers reaching the API through
   `server-api.ts` are out of scope; see Notes.
3. Assert the selection is non-empty and at least as large as the count
   recorded at the time of writing: landing 9, web 10, admin 5.
4. Assert each selected handler spreads `forwardedClientHeaders(request)` into
   its outbound headers.

Run: `npm --workspace landing run test`, and the `web` / `admin` equivalents.

## Expected Result

Every direct-API handler forwards. Removing `...forwardedClientHeaders(request)`
from any single handler fails that app's run and names the file.

Step 3 is not padding. When this scenario was written the convention was already
intact across all 24 handlers, so a check that quietly found nothing to inspect
would have reported the same green as a check that inspected everything, and
would have stayed inert indefinitely. The count is what tells the two apart.

## Notes

Written after [[BUG-0081]]: all three apps carried a comment asserting that a
file named `forwarded-headers.invariant.test.ts` enforced this rule, and no such
file existed. The rule itself is real — a route handler runs server-side, so
without a forwarded address the API sees the app's egress IP for every visitor
on earth, and `PublicRateLimitGuard` keys on exactly that. One handler that
forgets converts the public rate limit from a per-visitor budget into a switch
any single visitor can flip for everybody, which is [[BUG-0032]].

`server-api.ts` handlers are excluded, and not because they are safe:
`server-api.ts` does not forward either. They are excluded because the endpoints
they reach are authenticated and `PublicRateLimitGuard` does not run on them, so
the gap there is attribution rather than a bypass. Deciding what should carry
the address on that path is separate work; widening the check first would only
fail the build with nothing to do about it.
