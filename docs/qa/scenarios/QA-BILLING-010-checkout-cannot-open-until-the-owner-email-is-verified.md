# QA-BILLING-010 — Checkout cannot open until the owner email is verified

## Preconditions

Real PostgreSQL, a checkout-ready plan price, a Stripe double that **counts**
customer and session creations, and a mail double that captures the message
body.

## Steps

1. Submit a subscribe request for a new buyer. Record the Stripe session count
   before and after.
2. Read the six-digit code out of the captured mail body — not out of the
   database.
3. Submit a deliberately wrong code, then read `emailVerificationAttempts`.
4. Submit five wrong codes, then submit the **correct** one.
5. Request a resend immediately after the first send.
6. Verify with the real code, resubmit the original request, and read the order.
7. Verify again on the already-verified order.

## Expected Result

1. `verificationRequired: true`, no URL, and **the Stripe session count is
   unchanged**. That last clause is the assertion that matters: a gate which
   returns a warning while still handing back a checkout URL is not a gate, and
   only counting provider calls catches it.
2. The code is six digits and was mailed to the owner address and no other.
3. The wrong code is refused and `emailVerificationAttempts` is 1.
4. After five wrong guesses the **correct** code is refused too — the attempt
   budget belongs to the code, not to the guess.
5. The resend is throttled.
6. The resubmission returns a checkout URL, the order carries
   `ownerEmailVerifiedAt`, and `emailVerificationCodeHash` is null — consumed.
7. Succeeds. A double-clicked Verify button must not undo the verification.

## Notes

Reading the code from the mail rather than the row is deliberate: the stored
value is a SHA-256 hash and cannot be reversed, so a test that could verify
without the mail would be exercising a path the customer never takes.

The rule being enforced is `paidAt` implies `ownerEmailVerifiedAt`. A card proves
somebody can pay; it proves nothing about whether they typed their own address,
and the owner email is the one credential that cannot be corrected from inside a
workspace nobody can sign into — the recovery is a support case against a paid
account.

The failure mode guarded against is `gate-with-a-way-around-it`: the obvious
implementation adds a verified route beside the existing one and leaves the
unverified route as the one everybody keeps using. That is why the gate lives in
`createPublicSubscriptionCheckout` itself rather than in a new endpoint.
