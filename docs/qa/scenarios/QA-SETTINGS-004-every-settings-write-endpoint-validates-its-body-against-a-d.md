# QA-SETTINGS-004 — Every settings write endpoint validates its body against a DTO

## Preconditions

The `settings-context` controller and `UpdateMyPreferencesDto`. No database and
no running application: this is about what the global `ValidationPipe` is given
to work with.

## Steps

1. Read `design:paramtypes` for `updateMyPreferences` and check the `@Body()`
   parameter's type.
2. Validate a well-formed body.
3. Validate an empty body.
4. Validate an over-long timezone.
5. Validate a time format that is neither `12h` nor `24h`.
6. Validate a non-string where a string is required.
7. Validate a field the DTO does not declare.

## Expected Result

1. `UpdateMyPreferencesDto`, not `Object`.
2. and 3. accepted — updating one preference must not require restating the
   others.
4. through 7. refused, each naming the offending property.

## Notes

**Step 1 is the one that matters**, and it is the whole reason this scenario is
worth having. A DTO's rules can be perfect and never run: [[BUG-0669]] was
exactly that — the class existed with the right rules and the handler took
`Record<string, unknown>`, which gives the pipe no metadata at all. Without step
1, steps 2–7 would all pass while the endpoint accepted anything.

That is `declared-but-unwired-step`, and its signature is that the declaration
reads as cover. Anybody auditing the controller would see a validated DTO and
move on.

The DTO must be declared **above** the controller. `design:paramtypes` is
evaluated when the controller class is defined, so a DTO below it is in a
temporal dead zone — `wiring-invariants.spec.ts` reports "Cannot access ... before
initialization" rather than anything about validation.
