# QA-PLATFORM-009 — A paged list clamps a page number that outlived it

## Preconditions

None. Pure arithmetic over a list length, a requested page and a page size.

## Steps

1. `npm --workspace admin run test -- list-paging`
2. Manually, for the rendered half: open a tenant with substantial history at
   `/tenants/<id>`, select Timeline, page to the last page, then switch the
   category filter to one with fewer entries than that page number implies.

## Expected Result

A 154-entry list at 25 a page reports seven pages, stops the last page at the
end of the list, and covers every row exactly once across all its pages. A page
number beyond the end clamps into range rather than rendering nothing. An empty
list stays on a valid page. A nonsense request — `0`, negative, `NaN` — resolves
to the first page. A page size of zero does not produce an infinite page count.

Manually: the panel states "Showing 1–25 of 154", the pager disables at both
ends, and changing the filter returns to the first page with rows on screen.

## Notes

The failure worth guarding is not the slice — it is state that outlives what it
indexes. A page number held in a component survives the list being filtered or
refetched, and correcting it from an effect still renders the broken state once.
`describePage` clamps instead, so the window cannot be stale by construction.
