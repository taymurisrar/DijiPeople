# QA-SECURITY-002 — The rate limiter does not trust a client-supplied X-Forwarded-For

## Preconditions

The API reachable both directly and through its edge, so a caller can set
`X-Forwarded-For` themselves. A public endpoint under the rate limiter, and an
authenticated one.

## Steps

1. Send repeated requests to a rate-limited public endpoint, varying a forged
   `X-Forwarded-For` on each.
2. Send a chain too short to contain the configured number of trusted hops.
3. Send no forwarded header at all, direct to the service.
4. Exceed the limit on an authenticated endpoint.
5. Drive ordinary token refresh traffic at volume.

## Expected Result

- Varying a forged header does not reset the limit. Rotating that value was the
  bypass.
- A chain that cannot confidently identify the client resolves to `unknown`
  rather than falling through to the socket address, which behind a trusted
  proxy is the deployment's own edge and not a meaningful identity.
- Authenticated endpoints are covered, not just public writes.
- Token refresh is **not** throttled by the login limiter. That regression signed
  users out once already, so a fix here must not reintroduce it.
