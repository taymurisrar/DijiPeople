# QA-AUTH-016 — A session row records the visitor's own user agent and address, not the proxy's

## Preconditions

`buildForwardedClientHeaders` (`packages/config/client-ip.js`) and the web
app's `forwardedClientHeaders` wrapper, driven with constructed incoming
headers — no live database, browser, or running API required.

## Steps

1. Call `buildForwardedClientHeaders` with an incoming request carrying both
   `X-Forwarded-For` and a real browser `User-Agent`.
2. Call it with an incoming request carrying `X-Forwarded-For` only (no
   `User-Agent` header at all).
3. Call it with a `User-Agent` longer than 500 characters.
4. Call `apps/web/lib/forwarded-headers.ts`'s `forwardedClientHeaders`
   wrapper with the same inputs.

## Expected Result

Step 1: both headers are forwarded unchanged. Step 2: only the address is
forwarded — no placeholder `User-Agent` is invented. Step 3: the forwarded
value is truncated to exactly 500 characters, matching the bound
`AuthService`'s `getAuthRequestInfo` already applies where the value is
written into `RefreshToken.userAgent`, so the two cannot disagree. Step 4:
identical behaviour through the web app's own wrapper, which is what every
proxied route handler actually calls.

## Notes

Before [[BUG-3360]], every browser sign-in produced a `RefreshToken` row with
`userAgent: "node"` and a Cloudflare edge address, because the web app's
server-side `fetch` to `/auth/login` / `/auth/refresh` never carried the
visitor's own `User-Agent` across the proxy hop, and `persistRefreshToken`
read the raw request instead of the forwarded-aware resolver
(`getAuthRequestInfo`) the audit log already used two functions away. The
address half of this forwarding hop exists for a different, older reason
(`X-Forwarded-For`, [[BUG-0032]], the public rate limiter) — this bug added
the same treatment for the user agent because the same proxy hop hides it.
This scenario deliberately does **not** re-test the forwarded-hop trust
arithmetic in `readForwardedForClientIp` (hop-count guard); that is
`services/api/src/common/security/client-ip.spec.ts`'s scope, and it is not
an off-by-one — see that file's own comment before ever touching it.
