# QA-RUNTIME-018 — A failed save always tells the user, even when the server names fields the form does not render

## Preconditions

Any module rendered through the tenant product's metadata runtime. The scenario
is about the runtime's command handler rather than about one module; the leave
request is only the example that exposed it.

The decision under test is `fieldValidationErrorsAreVisible(data, form)`: the
runtime may go quiet on a failed save **only** when the failure's field errors
will actually appear against a control the user can see.

## Steps

1. Fail a command with the real production payload — field errors naming
   `ownerId` and `status` — against a form whose sections render leave type,
   start date, end date and reason.
2. Fail a command whose single named field **is** on the form.
3. Fail a command naming two fields, only one of which is on the form.
4. Repeat step 2 with the map error shape (`fieldErrors: { name: message }`)
   rather than the array shape (`details.fields: [{ field, message }]`).
5. Fail a command carrying no field detail at all, and again with a null body.
6. Fail a command with a renderable field error while no form is active.

## Expected Result

- **1** — `false`. Neither field is on the form, so nothing inline can render
  and the dialog must be allowed through. This is the case that was silent in
  production.
- **2** — `true`. The error lands on its control; the dialog stays withheld.
- **3** — `true`. One renderable error is enough to give the user something
  actionable.
- **4** — `true`. Both supported error shapes are read, at the root and under
  `details`, so a contract change in either direction does not reintroduce
  silence.
- **5** — `false` for both. A failure with no field detail always reaches the
  dialog.
- **6** — `false`. With no active form there is nowhere to render, so silence is
  never justified.

The invariant behind all six: the runtime never withholds its error surface on
an assumption about the form that it has not checked against the form.

## Notes

Re-run with jest against the web workspace config, filtering on
`command-failure-visibility`. Executed 2026-08-29 at `the SESSION-0072 fix commit` alongside the
two related-create specs — 3 suites, 13 cases, all passing.

**What this scenario does not establish.** It is a unit scenario over a pure
predicate. It proves the decision is correct; it does not prove that a dialog is
painted, that it is announced to a screen reader, or that the form retains the
user's input — those are acceptance criteria on BUG-1966 that only a browser
test or a live retest can settle.

**Where the fix is.** It exists as commit `the SESSION-0072 fix commit` on
`agent/starter-blocker-fixes`. It is **not** on `develop` and **not** on `main`,
which is what production runs, so the demo tenant still shows the silent
failure. Live verification is pending integration and a release.

A useful pairing when that retest happens: the leave request is still rejected,
because BUG-1965 is only half fixed and `status` is still serialised into the
create body. The correct observation after this fix is therefore a *visible*
400, not a successful save.
