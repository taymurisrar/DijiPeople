# QA-DEPLOY-022 — The deployment says whether it is draining the outbox

## Preconditions

- A deployed API, reachable at its health endpoint.

## Steps

1. Run `npm --workspace api run test -- app.service`.
2. Run `npm run smoke:deployment` against the deployment.
3. `GET /api/health` and read `outboxWorker.enabled`.
4. Complete a paid signup and confirm a workspace is provisioned, or query
   `PlatformOutboxEvent` for `PROVISIONING_REQUESTED` rows and confirm they
   reach a delivered state.

## Expected Result

- The suite passes.
- `/api/health` reports `outboxWorker.enabled: true`.
- The smoke run passes the `outbox worker is draining events` check.
- Provisioning events are delivered rather than accumulating.

## Notes

Step 4 is the one that actually closes BUG-0904. Steps 2 and 3 confirm the flag
is on; only step 4 confirms the consequence, and the consequence is the whole
point — `ProvisioningRequestedHandler` is an outbox consumer and by its own
header the only thing that creates a self-service tenant. With the worker off, a
customer pays and no workspace is ever built.

The smoke check fails in two distinguishable ways on purpose. A deployment that
does not report `outboxWorker` at all predates the fix and cannot answer the
question; one reporting `false` answers it, badly. Those need different
responses, so they must not look alike.

Exactly one deployed service should set `OUTBOX_WORKER_ENABLED`. Several is safe
— claims use `FOR UPDATE SKIP LOCKED` — but none means events accumulate
undelivered, silently, which is how this went unnoticed. Nothing in the
repository can assert the value; it lives on the service.
