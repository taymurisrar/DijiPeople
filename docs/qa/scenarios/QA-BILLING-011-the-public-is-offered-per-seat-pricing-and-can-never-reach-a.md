# QA-BILLING-011 — The public is offered per-seat pricing and can never reach a sales-assisted flat price

## Preconditions

The automated part needs nothing: `resolveCommercialOffer` is pure, which is why
the commercial rules live in a file free of Prisma and Nest.

The end-to-end part needs a throwaway database with the migration chain applied
and `seed:config` run. Never the populated `dijipeople` development database.

The state that matters: a plan carrying **both** an active `PER_SEAT`
`SELF_SERVICE` price and an active `FLAT` `SALES_ASSISTED` price for the same
market, cycle and currency. Both models coexisting is the entire point — every
case below passes trivially when only one exists.

## Steps

1. `npm --workspace api run test -- commercial-offer`
2. `npm --workspace api run test -- pricing.catalog`
3. `npm --workspace landing run test -- plan-presentation`
4. Against a seeded throwaway database, confirm the schedule landed:
   `select m.code, p.key, pp."billingCycle", pp."billingModel", pp."unitAmount",
   pp."minimumSeats", pp."includedSeats", pp."overageUnitAmount", pp."salesModel"
   from "PlanPrice" pp join "Plan" p on p.id = pp."planId"
   join "Market" m on m.id = pp."marketId" order by m.code, p."sortOrder";`

## Expected Result

| Case | Required outcome |
|---|---|
| Self-service, both models present | The **per-seat** price, every time |
| Self-service, either row written first | The same answer — order must not matter |
| Self-service, N seats | `subtotal = N × unit`, not the flat amount |
| Self-service, seats below the plan minimum | Sold, billed at the minimum, with `quantity` still reported as asked |
| Self-service, only a flat price exists | `SALES_ASSISTED_ONLY` — **not** `NO_PUBLISHED_PRICE` |
| Self-service, `CUSTOM_ONLY` plan | `CUSTOM_CONTRACT_ONLY`, even with a permissive price row |
| Self-service, no price at all | `NO_PUBLISHED_PRICE` |
| Operator asking for `FLAT` | The flat price, billable quantity 1 |
| Operator asking for `PER_SEAT` | The per-seat price |
| Landing estimate | The same billable seat count the server charges |

Seeded schedule: 36 prices — 3 plans × 3 markets (PK/PKR, QA/QAR, INTL/USD) ×
2 cycles × 2 models. Enterprise+ carries **none**, which is what makes it answer
`CUSTOM_CONTRACT_ONLY` rather than quoting a figure.

## Notes

**Why the ordering case is parameterised over both orderings.** The defect was
that `resolveCommercialOffer` picked a price by recency and only then checked
whether the channel could buy it. Both rows are seeded in the same run,
milliseconds apart, so the flat row won roughly half the time — and when it did,
the plan disappeared from public sale with `SALES_ASSISTED_ONLY` for a reason
invisible in the data. A test fixing one ordering would have passed against that
defect half the time, which is worse than having no test.

**Why `SALES_ASSISTED_ONLY` and `NO_PUBLISHED_PRICE` must stay distinct.** They
send an operator to different places: the first means "a price exists and a
human can sell it", the second means "nobody has set one". Collapsing them
sends somebody hunting for a row that is right in front of them.

**Why the arithmetic guard does not restate the price list.**
`pricing.catalog.spec.ts` asserts relationships — annual is monthly × 10, a
minimum charge is `minimumSeats × unitAmount` — and then checks those against
the minimum-charge table the owner published *separately*. Two independent human
statements of the same fact agreeing is evidence; retyping the seat rates and
asserting they match would only prove somebody copied them twice.
