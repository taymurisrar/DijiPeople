# QA-RUNTIME-027 — Self-approval reachable because the role bypass was asked first

## Preconditions

A tenant on which the affected surface is reachable, and a signed-in user with
the permissions the surface requires. REG-329 in the regression register carries
the full root cause; this scenario is the reusable check, not the diagnosis.

## Steps

Both elevated roles refused on approve and on reject, with `$transaction`, `updateLeaveApprovalStep` and `updateLeaveRequest` asserted never called. The record payload no longer offers `canCurrentUserApprove` or `canCurrentUserReject` on the requester's own request. Two negative controls: an elevated role still acting on somebody else's request, and the assigned approver still acting with no elevated role at all.

## Expected Result

The behaviour holds as REG-329 describes it. The automated guard is `services/api/src/modules/leave/leave-self-approval.spec.ts`; a run of that suite is sufficient evidence for this scenario.

## Why This Is Reusable

`LeaveService.canUserActOnStep` evaluated `hasElevatedTenantRole(currentUser)` **before** testing whether the current user is the requester, so a `global-admin` or `system-admin` who submitted a leave request was reported as the assigned approver of their own pending step. `processLeaveRequestDecision` treats a true answer from that helper as `isAssignedApprover` and consults `canOverrideLeaveDecision` only when it is false — and `canOverrideLeaveDecision` is the one that orders the two checks correctly
