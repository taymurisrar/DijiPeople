# QA-API-001 — Plan entitlements survive a save and are never silently emptied

## Preconditions

- A platform administrator signed in to Platform Admin.
- A plan with a known, non-empty entitlement set. The seeded `starter` plan
  grants seven: `employees`, `organization`, `leave`, `attendance`, `documents`,
  `notifications`, `branding`.

## Steps

1. Open the plan record, Entitlements tab. Note which capabilities are ticked
   and the "N enabled" count.
2. Without changing the entitlements, edit the plan's Overview — the
   description will do — and save.
3. Return to the Entitlements tab and read the ticks and count again.
4. Enter edit mode, tick one further capability, and save the entitlements.
5. Reload the record from the server and read the entitlement set once more.

## Expected Result

- Step 3 shows exactly the set from step 1. A save of an unrelated field changes
  nothing about which capabilities are ticked, and the count does not fall to 0.
- Step 5 shows the original set **plus** the one capability added — never that
  capability alone.

The second assertion is the one that matters. `updatePlan` applies `featureKeys`
by replacement (`deleteMany` then `create`), so a page that renders an empty set
and then submits it deletes real entitlements from a plan live tenants are on.
Correct rendering is not cosmetic here; it is what stands between an operator and
data loss.

## Notes

Automated at the API boundary by `plan-record-shape.spec.ts`, which pins the
runtime GET's `features` shape to the shape the runtime PATCH returns — the two
disagreeing is the whole defect — and at the client boundary by
`apps/admin/lib/runtime/plan-entitlement-keys.spec.ts`, which proves the
derivation reads both shapes and returns `[]` only for input it genuinely cannot
read.

Steps 1–5 remain the manual scenario, because neither automated test exercises
the browser round trip that produced the report.
