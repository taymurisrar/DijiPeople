# QA-AUTH-013 — Remember me cookie lifetimes survive a middleware refresh

## Preconditions

`buildAuthSessionCookies` (`apps/web/lib/auth-session-cookies.ts`) and
`proxy.ts`'s `continueWithRefreshedTokens`, exercised directly with
constructed token responses — no live database or browser required.

## Steps

1. Sign in with **Remember me** checked; note the API's returned
   `accessTokenExpiresIn` / `refreshTokenExpiresIn`.
2. Build the three auth cookies from a refresh response carrying
   `rememberMe: true` and those same expiry strings, through
   `buildAuthSessionCookies` directly.
3. Build them again through `proxy.ts`'s `continueWithRefreshedTokens`, from a
   mocked `/auth/refresh` response carrying the same fields.
4. Repeat steps 2–3 with `rememberMe: false`.
5. Change only the expiry strings between two calls to
   `buildAuthSessionCookies` and confirm the resulting `maxAge`s differ.

## Expected Result

Steps 2 and 3: the access and refresh cookies' `maxAge` equal the response's
own `accessTokenExpiresIn` / `refreshTokenExpiresIn`, converted to seconds —
never `900` (15 minutes) and never an independently-resolved environment
variable. Step 4: no `maxAge` is set at all (a browser-session cookie). Step
5: the two calls produce different `maxAge` values, proving the number is
derived from the response rather than a literal in either file.

## Notes

[[BUG-3357]] found that the sign-in route and `lib/server-api.ts` already
read the lifetimes correctly; only `proxy.ts` — the writer that refreshes on
the most navigations — used a hardcoded `15 * 60` and a separately-resolved
env var. `buildAuthSessionCookies` is now the single function all three
writers call, so the same regression test protects all three. What Remember
me means for the access token itself (it does not lengthen it; it lengthens
only the refresh token and keeps the browser signed in across restarts) is
recorded in `services/api/src/modules/auth/PASSWORD-LOGIN-POLICY.md`.
