# QA-ATTENDANCE-009 — A manager sees what changed, and only what changed

## Preconditions

A correction request of each shape: a time change, a work-mode change, a
work-site change, an overtime request, a device-fallback reason, a request that
changes nothing, and one for a day with no attendance entry at all.

## Steps

1. Run `correctionChanges` over each request.
2. Open `/attendance/corrections/[id]` as the approver and read the
   "What changed" card.
3. For each of the five change kinds, confirm the row appears once, carries the
   previous value struck through, and names the new one.
4. Confirm a field whose requested value equals the current one produces no row.
5. Confirm two spellings of the same instant produce no row.
6. Confirm a request that proposes nothing renders a sentence saying so, not an
   empty card.

## Expected Result

The card lists exactly the fields that moved. Overtime shows no struck-through
previous value, because the attendance record holds none and rendering a zero
would claim one. A request against a day with no entry still renders, with no
previous value on either time.

## Why this scenario exists

Four of the eight correction kinds — work mode, work site, overtime and the
fallback reason — were stored by the API, returned by the API, and rendered
nowhere, because the web app's hand-written type did not declare them. The two
cards that were rendered listed check-in and check-out unconditionally, so an
unchanged field looked identical to a changed one and a mode-only correction
looked like no correction at all.

**A hand-written frontend type is a claim about a payload that nothing checks.**
When it is narrower than what the API sends, the product silently loses a
feature, and no error is raised anywhere to say so.

## Re-run guidance

The pure `correctionChanges` function carries the logic and is asserted
directly. When re-running by hand, the case worth doing live is the mode-only
correction: it is the one that used to render as two identical cards.
