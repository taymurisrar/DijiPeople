# QA-TENANT-006 — Database e2e fixtures build two isolated tenants and clean up after partial setup

## Preconditions

A migrated, disposable PostgreSQL reachable at `DATABASE_URL`. **No seed is
required, and that is the point** — this scenario exists because the suites it
underpins used to require one and did not say so.

The recipe is in [`database-e2e-reproduction.md`](../../development/database-e2e-reproduction.md).

## Steps

1. Run `npx jest --config ./test/jest-e2e.json --testPathPatterns db-fixtures-contract --detectOpenHandles`
   from `services/api`.
2. Against a database with **zero** tenants, run any of `attendance-engine`,
   `attendance-integrations-http` or `gateway-runtime` and confirm they still
   pass — they must not need a seeded tenant to exist.

## Expected Result

- `createTenantPair()` yields two tenants with different ids **and different
  customer accounts**. Sharing a customer account would hide a leak through the
  commercial side behind a legitimately shared parent row.
- Each side carries an organization and a business unit whose `tenantId` matches
  its own tenant. `BusinessUnit.organizationId` is required on the composite
  `(organizationId, tenantId)`, so "a tenant with a business unit" is three rows,
  and a fixture that returns two is not usable by the attendance, gateway or
  user modules.
- `cleanup()` removes the tenants, their customer accounts, **and** the
  organizations and business units underneath them. Asserted rather than assumed:
  `BusinessUnit → Organization` is `Restrict`, and whether a cascade from Tenant
  can delete two rows joined by a restricted key is a question only a real
  PostgreSQL answers.
- `cleanup()` after partial construction resolves rather than throwing, and is
  safe to call twice. That is the state a failed `beforeAll` leaves, and the
  state in which teardown used to send `in: [undefined, undefined]` to Prisma
  and fail on top of the failure that caused it.
- Two `DbFixtures` instances built with the same label generate different names,
  so a run that skipped cleanup cannot collide with the next one.
- Zero open handles. No "force exited", no "Jest did not exit".
