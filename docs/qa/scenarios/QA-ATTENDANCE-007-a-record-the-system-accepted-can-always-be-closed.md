# QA-ATTENDANCE-007 — A record the system accepted can always be closed

## Preconditions

An attendance entry with an open `checkIn`, `attendanceMode: OFFICE` and
`officeLocationId: null`. Reached in production naturally; reached in the
suite by constructing the entry directly.

## Steps

Check out of that entry, supplying a device position.

Then the counterpart: attempt an `OFFICE` check-in with no work site.

Manually, to cover the route that makes this a fleet-wide problem rather
than a one-record one: with an employee checked in against a work site,
delete that work site, then have them check out.

## Expected Result

The entry closes. The device position is still required — omitting it fails
with "Current location is required", which is the correct refusal and is
what `validateAttendanceLocationPayload` is for.

The `OFFICE` check-in is still refused with "Office location is required for
office attendance." **Both halves are necessary.** Letting check-out through
is only safe if the precondition provably still holds at check-in; without
that assertion the fix reads as "stop caring about work sites".

After the work-site deletion, the employee can still check out.

## Why This Is Reusable

The general rule, and it is worth more than the single message: **a record
the system accepted must always be closable.** Any check-in precondition
re-validated at check-out will eventually stop holding — through a deleted
work site (`onDelete: SetNull`), a policy change disabling a mode, or a
schema default — and every one of those traps the entry open, because
check-out has no field the employee could correct.

Re-run whenever `checkOut` gains a validation, and treat any new one that
reads stored state rather than the submitted payload as suspect.
