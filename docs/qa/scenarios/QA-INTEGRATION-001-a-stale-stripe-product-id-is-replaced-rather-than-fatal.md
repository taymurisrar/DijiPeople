# QA-INTEGRATION-001 — A stale Stripe product id is replaced rather than fatal

## Preconditions

- A platform administrator signed in to Platform Admin.
- A plan whose `stripeProductId` names a product that is **not** present in the
  connected Stripe account. This happens for ordinary reasons: the sandbox was
  reset, the account was switched, someone removed the product in the dashboard.
- A Stripe secret key that is valid for the connected account.

## Steps

1. Open the plan, Pricing tab, and edit any price — the amount will do.
2. Save.
3. Read the plan's stored `stripeProductId`.
4. Edit a second price on the same plan and save.
5. In the Stripe dashboard, count the products created for this plan.

## Expected Result

- Step 2 succeeds. It must not return `500 SYSTEM_UNEXPECTED_ERROR` with
  `No such product: '<id>'`.
- Step 3 shows a **new** product id — the stale one has been replaced, not kept
  alongside a product that was created and then forgotten.
- Step 4 succeeds without creating anything further.
- Step 5 shows exactly one new product, not one per attempt.

Steps 3–5 are the second half of the defect and are easy to skip: catching the
missing-product error alone makes the first save succeed while quietly leaking a
Stripe product on every subsequent one, because the plan still points at the
dead id.

## Negative case

With an invalid or unauthorised Stripe secret key, the same save must **fail**
and create nothing. An implementation that treats every Stripe error as "the
product is missing" would mint duplicate products during an outage or on a bad
key — worse than the failure it replaces, and silent.

## Notes

Automated by `stripe-product-resolution.spec.ts`: missing product, deleted
product, existing product reused, and the negative case above. Mutation-tested —
replacing the guard with `if (true) throw error` fails the missing-product case.

Reported from production on 2026-08-23 with the full 500 and stack trace against
`PATCH /api/super-admin/plans/{planId}/prices/{priceId}`.
