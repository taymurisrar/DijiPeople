# QA-AUTH-011 — Concurrent sessions are allowed by default unless a tenant opts out

## Preconditions

A tenant with **zero** `TenantSetting` rows in category `security` (the
production shape at the time [[BUG-3355]] was found), driven against
`AuthService.persistRefreshToken` with a mocked Prisma client — no live
database required for this scenario.

## Steps

1. Sign in (or refresh) as a tenant user on the `web` client, for a tenant
   with no `security` settings row at all.
2. Read whether `persistRefreshToken` revoked any of the user's other live
   refresh tokens on that client.
3. Repeat with the tenant's `allowMultipleActiveSessions` setting explicitly
   set to `false`.
4. Repeat again with it explicitly set to `true`.
5. Sign in twice in quick succession as the same user on `web` and assert
   the first session's refresh token is left live in step 1's tenant.

## Expected Result

Step 1: no other session is revoked — an absent setting means concurrent
sessions are **allowed**. Step 3: every other live token for that user+client
is revoked (single-session opt-out honoured). Step 4: no other session is
revoked (explicit opt-in). Step 5 confirms the same at the `refresh()` level,
not only inside the private helper.

## Notes

[[ADR-0009]] records the product decision this scenario pins: the owner chose
concurrent-sessions-by-default over documenting the old restrictive default,
because the restrictive reading silently destroyed work in progress on a
device the acting session could not see, rather than merely denying an
action. [[ITEM-0162]] is the related consolidation that made
`allowMultipleActiveSessions` resolve through the same
`TenantAuthPolicyService` as every other session-policy value.
