# QA-PLATFORM-025 — The admin console refuses unauthenticated access and hardens its session

## Preconditions

Two browser contexts: one with no session at all, one signed in as a platform
user. The unauthenticated context must never be given cookies.

## Steps

1. From the unauthenticated context, call the platform APIs directly:
   `platform-runtime/tenants`, `/customers`, `/leads`, `/monitoring-incidents`,
   `/preferences`, and `platform/events/notifications`.
2. From the same context, load `/tenants`, `/customers`, `/settings/users` and
   `/security`.
3. Sign in, and inspect every cookie the session sets.
4. Inspect the response headers on an authenticated navigation.
5. POST a create payload carrying `id`, `tenantId`, `createdAt`, `createdById`,
   `stripeCustomerId` and `isDemoData`.
6. Attempt sign-in with a real address and a wrong password, then with an
   address that does not exist. Compare the two responses byte for byte.

## Expected Result

1. Every platform API answers **401**. Not 200-with-empty, not 404.
2. Every page redirects to `/login?next=...` **without rendering the shell**. A
   redirect that renders first has already leaked.
3. Every auth cookie is `httpOnly`, `secure`, and `SameSite` is not `None`. A
   cookie that is deliberately readable — the theme — is fine, and should be the
   only one.
4. `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`,
   `X-Frame-Options`, `Referrer-Policy` and `Content-Security-Policy` are all
   present, and `X-Powered-By` is not.
5. The create is **rejected**, naming each forbidden property. This is
   `forbidNonWhitelisted`. A create that succeeds while silently ignoring the
   forged fields is a weaker pass and should be recorded as such.
6. The two sign-in responses are **identical**, so the endpoint does not
   enumerate accounts.

## Notes

Established 2026-08-26 against production at `8d6be21b`. Steps 1, 2, 3, 5 and 6
passed. Step 4 failed on `Content-Security-Policy`, which is absent — BUG-1424.
The other four headers are present.

**What this scenario cannot tell you.** It ran as `PLATFORM_OWNER` holding
`platform.*`. A role that can reach everything cannot demonstrate that a
narrower role cannot, so nothing here is evidence about over-permissive access.
Driving the same steps as a restricted platform role is the missing half, and
the more valuable half.

Login throttling was probed and deliberately *not* concluded on: ten bad
attempts all returned 401 with no 429. Reading the code afterwards showed both
thresholds are 20 — `PublicRateLimitGuard` allows 20 writes per 10 minutes per
IP and path, and `LoginLockoutService` locks at 20 attempts. The probe was
simply below both, and reporting it as "no throttling" would have been wrong.
Do not re-run this by brute force against production: it locks a real account.
