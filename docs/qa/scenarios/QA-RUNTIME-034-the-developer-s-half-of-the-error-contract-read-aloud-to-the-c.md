# QA-RUNTIME-034 — The developer's half of the error contract, read aloud to the customer

## Preconditions

A tenant on which the affected surface is reachable, and a signed-in user with
the permissions the surface requires. REG-334 in the regression register carries
the full root cause; this scenario is the reusable check, not the diagnosis.

## Steps

A validation failure resolves to the contract's `description`, and the resolved message contains neither a DTO property name nor `/api/`. A domain refusal keeps its own message, because that is the useful half. An HTML body at status 404 resolves to a written sentence, keeps the body in `details` for the log, and does not report a database error code — while a 404 the API really sent as `DATABASE_RECORD_NOT_FOUND` still reports one. A `traceId` is present on every path.

## Expected Result

The behaviour holds as REG-334 describes it. The automated guard is `apps/web/lib/api-error.spec.ts`; a run of that suite is sufficient evidence for this scenario.

## Why This Is Reusable

The API's `HttpExceptionFilter` writes `message` for a developer and `description` for the person at the screen. The client rendered `message`
