# QA-RUNTIME-042 — The responsive record tab strip exposes tab semantics and its measurement copy is not tabbable

## Preconditions

`apps/web` builds and its jest project runs. `apps/web`'s jest has no jsdom
(see `apps/web/jest.config.js`), so this cannot render the strip and inspect
a live accessibility tree — see Notes for what a browser-based QA pass still
owes.

## Why This Scenario Exists

`responsive-runtime-tabs.tsx` renders an invisible, off-screen copy of every
tab purely to measure widths before deciding how many fit visibly. That copy
was `aria-hidden="true"` but not `inert`, so its buttons stayed thirteen live
keyboard stops a screen reader had been told did not exist. Separately, the
visible strip exposed zero `role="tab"`/`role="tablist"`/`role="tabpanel"`
elements — a screen reader had no way to know it was looking at tabs at all.
This is the shell [[ITEM-0167]] proposes propagating to every other record
page, so it has to be right before that happens.

## Steps

1. `npm --workspace web run test -- --testPathPatterns responsive-runtime-tabs`

Within that suite: the roving-tabindex arrow-key math (`resolveNextTabIndex`)
is exercised directly for wrap-around, Home/End, and a selection outside the
selectable set. The shared id helpers (`getResponsiveTabId`,
`getResponsiveTabPanelId`) are checked for determinism and collision-freedom
across two different `idPrefix` values. The component's own source is read
and checked structurally for `inert` on the measurement copy, `role="tablist"`
on the visible container, and `role`/`aria-selected`/`aria-controls`/roving
`tabIndex` on each visible tab.

## Expected Result

The measurement copy carries `inert` (not merely `aria-hidden`). The visible
strip exposes one `tablist`, one `tab` per visible tab with `aria-selected`
and `aria-controls`, and (in `runtime-metadata-form-renderer.tsx`) one
`tabpanel` with `aria-labelledby` pointing at the selected tab. Only the
selected tab carries `tabIndex={0}`; the rest carry `-1`. Arrow-key movement
wraps at both ends, jumps to the first/last tab on Home/End, and treats a
selection outside the selectable set (disabled, or mid-collapse into the
overflow menu) as before the first rather than doing nothing. The More menu
is unaffected and stays reachable by ordinary Tab order after the strip.

## Negative Case

Removing `inert` from the measurement copy, or reverting any of
`role="tablist"`, `role="tab"`, `aria-selected`, `aria-controls`, or the
roving `tabIndex` pattern, fails the corresponding structural assertion by
name rather than failing silently.

## Notes

**Not verified in a browser.** The assertions are over the source and over
pure functions, because that is what this jest project can do — a live pass
against an employee record with a screen reader and a keyboard, counting
actual focus stops and listening for tab announcements, is still owed and is
exactly what [[BUG-3378]]'s own Acceptance Criteria describe ("an automated
accessibility scan of an employee record reports no `aria-hidden-focus`
violation"). `apps/admin`'s `console-theme.spec.ts` established the
source-structural-check technique this scenario reuses for the same reason:
no jsdom, no rendering library.
