# QA-ATTENDANCE-008 — Every correction type the form offers can actually be submitted

## Preconditions

An employee with attendance read, and the eight entries of
`CORRECTION_TYPE_OPTIONS` as the form renders them.

## Steps

1. For each correction type, read the fields the form will render, via
   `fieldsFor` / `showsField`.
2. For every type except `OVERTIME_APPROVAL`, confirm at least one of
   `requestedCheckInAtUtc` and `requestedCheckOutAtUtc` is among them.
3. Build a draft of that type with only the fields it shows and run
   `validateDraft` over it.
4. Compare the resulting payload against what
   `AttendanceService.createCorrectionRequest` requires: a timestamp on every
   type except `OVERTIME_APPROVAL`, minutes on that one, and no `HYBRID` work
   mode.

## Expected Result

Every offered type produces a payload the API accepts. A type that the server
would refuse for a missing field is refused by `validateDraft` first, naming the
field, rather than reaching the API and returning a 400 about a field the
employee was never shown.

## Why this scenario exists

`TIME_ADJUSTMENT` was offered in the product and refused by the server on every
single submission, because the form hid both timestamps and the API required
one. It had a test, and the test passed — it asserted the form's field map from
the form's side only, so it confirmed the defect instead of catching it.

**Assert the contract, not one end of it.** A form's field map and its
endpoint's validation are two statements of the same agreement; whichever one
you write the test against, the test has to reach the other.

## Re-run guidance

Run over the whole `CORRECTION_TYPE_OPTIONS` list rather than type by type. A
ninth correction type added later is exactly how this comes back, and only a
loop catches it.
