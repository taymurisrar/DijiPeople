# QA-RUNTIME-046 — Custom-module records are unreachable before publish, from another tenant and without custom-records privileges

## Preconditions

- A throwaway database with two tenants, A and B, that each create a custom
  module with the same key (for example `e2eAsset`).
- In tenant A: a user with full `custom-records` privileges, a user with
  `custom-records` READ only, a SELF-scope reader, and a user with no
  `custom-records` privilege.

## Steps

1. Tenant A, before publishing: `GET /api/data/e2eAsset`, `POST /api/data/e2eAsset`,
   and `GET /api/metadata/custom-modules`.
2. Publish the module in both tenants. Repeat step 1 in A.
3. Create a record in A. List and read it in A.
4. In B: list `e2eAsset`; `GET`, `PATCH` and `DELETE /api/data/e2eAsset/<A-record-id>`.
5. In A, as the READ-only user: `POST`, `PATCH` and `DELETE /api/data/e2eAsset`;
   `GET /api/data/e2eAsset/<id>`.
6. In A, as the SELF-scope reader: list and read another user's record.
7. In A, as the user with no privilege: `GET /api/metadata/custom-modules`.
8. Deactivate the module in A; repeat step 1 in A and list in B.

Run the automated part with
`DATABASE_URL=<throwaway> npm --workspace api run test:e2e -- custom-module-runtime`.

## Expected Result

- Step 1: 404 for both record calls; the module is not listed.
- Step 2: both succeed; the module is listed.
- Step 3: the record is listed and readable in A.
- Step 4: B's list is empty; every call on A's id is 404; A's row is unchanged.
- Step 5: 403 for create, update and delete; 200 for the read.
- Step 6: the other user's record is not listed and reads 404.
- Step 7: 403.
- Step 8: 404 again in A and the module leaves A's list; B's module is unaffected.
