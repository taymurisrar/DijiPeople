# QA-ATTENDANCE-006 — The IP fallback setting is locked off and cannot be re-enabled

## Preconditions

- Signed in as a tenant administrator.
- Ideally a tenant whose **stored** `allowIpFallback` is already `true` — the
  demo tenant was one. A tenant already storing `false` cannot distinguish a
  working mandate from a coincidence, which is the whole risk this covers.

## Steps

1. Open Settings → People → Attendance and find **Allow approximate IP
   fallback**.
2. `GET /api/attendance/runtime-context` and read `policy.allowIpFallback`.
3. Attempt to write it `true` directly:
   `PATCH /api/tenant-settings` with
   `{"updates":[{"category":"attendance","key":"allowIpFallback","value":true}]}`.

## Expected Result

- Step 1: the control renders **disabled**, with "Enforced by platform policy
  and cannot be changed." — matching the seven mandated location settings beside
  it.
- Step 2: `allowIpFallback` is `false`, **even on a tenant whose stored value
  was `true`**. This is the assertion that matters; the UI is cosmetic and the
  runtime reads the stored value, so a fix that only disabled the checkbox would
  pass step 1 and fail here.
- Step 3: the request is **refused and names the key**. It must not succeed
  silently, and it must not be quietly swapped to `false` — a silent swap makes
  the change-diff drop it as a no-op, which is how the original mandate went
  unnoticed (BUG-1979).

## Notes

Created 2026-08-30 at `a1b51025`. Not yet run against a deployed build.

The setting was withdrawn rather than implemented, by owner decision. If it is
ever implemented for real, this scenario is the one to revisit — it asserts the
capability is *off*, not that it is absent, so it will correctly fail the day
somebody wires a provider without also relaxing the mandate.
