# QA-TENANT-055 — Employee document upload validates, stores and returns the same bytes

## Preconditions

A tenant on a plan that entitles `documents`, one employee record, and a caller
with document write access on that employee — the tenant owner satisfies this.
The document-type lookup must be seeded; a tenant with no document types cannot
satisfy the required `documentTypeId` and this scenario would fail for the wrong
reason.

One small file of an allowed type (a few hundred bytes of valid PDF is enough)
and one of a disallowed type (`text/plain`).

## Steps

1. `GET /api/lookups/document-types` and keep one `id`.
2. `POST /api/employees/<employeeId>/documents/upload` with the `text/plain`
   file and a valid `documentTypeId`.
3. `POST /api/employees/<employeeId>/documents/upload` with the PDF and **no**
   `documentTypeId`.
4. `POST /api/employees/<employeeId>/documents/upload` with the PDF and the
   `documentTypeId` from step 1.
5. `GET /api/employees/<employeeId>/documents`.
6. `GET /api/employees/<employeeId>/documents/<documentId>/download`.
7. `GET /api/employees/<employeeId>/documents/<documentId>/view`.

## Expected Result

1. 200 with a non-empty list of document types.
2. 400 `VALIDATION_FAILED`, refused on content type, with a message that says so
   rather than a generic failure.
3. 400 naming `documentTypeId` in the message **and** in `details.fields`. A
   required-field refusal that does not name the field leaves the form with
   nothing to highlight.
4. 201 carrying the new document id.
5. 200 with the uploaded document present and its `documentType` expanded, not
   returned as a bare id the caller has to resolve.
6. 200, `Content-Type: application/pdf`, byte length equal to the uploaded file,
   and the body begins `%PDF`.
7. Identical to step 6 — same content type, same length, same leading bytes.
   View and download must serve the same object.
