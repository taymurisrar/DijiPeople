# QA-PLATFORM-029 — A client cannot store a rendered web page as an incident message

## Preconditions

None. `toStoredClientMessage` is a pure function.

## Steps

Pass a full Next.js error page (doctype, inlined CSS custom properties, ~14 KB
body) and assert the stored message names the status instead. Repeat for a
lowercase doctype, leading whitespace, a bare `<html>` with no doctype, and an
XML fault document. Pass an ordinary sentence and assert it is unchanged. Pass
a 5,000-character non-markup string and assert it is bounded. Pass a string of
exactly the maximum length and assert it is untouched. Pass `null`,
`undefined`, empty, whitespace, a number and an object.

Then the guarding case: pass `Expected <input name="email"> to be present in
the form.`

## Expected Result

A markup document is **replaced**, not truncated — 500 bytes of doctype and
inline CSS is as useless to an operator as 14 KB of it. Non-markup messages
are bounded at 500 characters with an ellipsis. Every unusable input falls
back to `Client error`.

The guarding case survives **verbatim**: a validation message quoting an
element is real information, and the check is anchored at the start of the
string rather than searching it.

## Why This Is Reusable

The admin monitoring queue renders `message` as the row title, and
`POST /error-logs/client` accepts whatever any client sends — the
agent-desktop app is a second reporting client. Re-run whenever the client
error reporter or the markup heuristic changes.
