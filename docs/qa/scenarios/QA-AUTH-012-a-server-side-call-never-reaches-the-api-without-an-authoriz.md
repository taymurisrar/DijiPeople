# QA-AUTH-012 — A server-side call never reaches the API without an Authorization header when it cannot authenticate

## Preconditions

`apiRequest` (`apps/web/lib/server-api.ts`) driven with `next/headers`'s
`cookies()` mocked and `fetch` mocked — no live database or running API
required.

## Steps

1. Call `apiRequest` with a refresh cookie present, no access cookie, and a
   mocked `/auth/refresh` response of `401 SESSION_REVOKED`. Record every URL
   `fetch` was actually called with.
2. Call `apiRequest` with **no** access cookie and **no** refresh cookie at
   all (a caller expecting auth, `includeAuth` not set to `false`).
3. Call `apiRequest` against a route explicitly marked `includeAuth: false`
   with no cookies present.
4. Call `apiRequest` with a valid access cookie already present.

## Expected Result

Step 1: `fetch` is called exactly once, to `/auth/refresh` — never to the
originally requested path — and the returned `Response`'s `errorCode` is
`SESSION_REVOKED` (the refresh failure's own code), not `AUTH_TOKEN_MISSING`;
its `traceId` matches the id the refresh call itself carried. Step 2: `fetch`
is called zero times; the response is a 401 with an error code other than
`AUTH_TOKEN_MISSING`. Step 3: `fetch` is called once, unauthenticated, exactly
as before — genuinely anonymous callers are unaffected. Step 4: the request
proceeds with `Authorization: Bearer <token>` set, unaffected.

## Notes

[[BUG-3356]] is what [[BUG-3355]]'s third acceptance criterion depended on: a
displaced session must be told it ended rather than failing blankly with
`AUTH_TOKEN_MISSING`, a code deliberately kept off the incident queue
([[BUG-2465]]) because it is supposed to mean "anonymous caller", not "our own
app gave up mid-request". [[BUG-3358]] shares this test file — the unwritable
cookie-store case is `QA-AUTH-014`.
