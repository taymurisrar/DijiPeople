# QA-BILLING-020 — A stale Stripe price id marks the row unsynced instead of returning 500

## Preconditions

None. `StripeBillingService` is constructed with a stubbed `prices.retrieve`,
so no Stripe account is involved.

## Steps

```bash
npm --workspace api run test -- src/modules/billing/stripe-price-resolution.spec.ts
```

Read it alongside `stripe-product-resolution.spec.ts`, which is its counterpart
for the product path.

## Expected Result

| Case | Expected |
|---|---|
| `resource_missing` from `prices.retrieve` | `valid: false`, `priceId: null`, `active: false` — **no throw** |
| The reason text | names the price id and says to re-sync; it is surfaced verbatim as `stripeVerificationError`, so it must read for a person |
| Environment | reports the runtime mode, not a default — a gone price has no `livemode` of its own, and defaulting would stamp a LIVE row as TEST |
| `StripeAuthenticationError` | **still throws** |
| A price that exists | verifies unchanged, `valid: true` |

## Notes

The fourth row is the one that keeps this honest. Swallowing every error would
mark good prices unsynced during a Stripe outage, and an operator would then
re-sync prices that were fine — worse than the 500 this replaces.

The asymmetry with the product path is intentional and worth not "fixing" later:
[[BUG-0995]]'s product recovery auto-creates a replacement, and this one does
not. A price determines what customers are charged; minting one behind an
operator's back is a pricing change, not a recovery.

Note also that [[BUG-1134]] was *limiting* [[BUG-1133]]'s blast radius — the 500
was the only thing stopping further silent price destruction — so the two landed
in the same change.
