# QA-RUNTIME-016 — A column added to a module reaches operators who saved table preferences

## Preconditions

A platform operator with saved table state for a runtime list — any operator who
has ever changed a column setting, since state is persisted automatically via
`/api/platform-runtime/preferences` at `tableStateJson.version === 2`.

## Steps

1. Save table state on a list, then add a column to that module's definition.
2. Reload the list.
3. Repeat with a column the operator had explicitly turned off.
4. Repeat with a column whose definition ships it hidden.
5. Repeat with a saved state carrying no `columnOrder` at all.

## Expected Result

- **2** — the new column is visible, at its definition position. A new first
  column appears first, not appended to the right.
- **3** — the column stays hidden. That was a decision and must survive.
- **4** — stays hidden, honouring the definition's default.
- **5** — falls back to definition visibility, because "hidden on purpose" and
  "did not exist yet" cannot be told apart without the order.
- Re-running the merge on its own output changes nothing.

## Notes

`columnOrder` is what makes this recoverable: it lists every column the saved
state knew about, hidden ones included. Without it the choice is between ignoring
the operator's preferences and ignoring the module's current definition.

Reported as "the tenant list doesn't look updated", which is exactly what it was
— the definition was current and the screen was not, for the people who use it
most.
