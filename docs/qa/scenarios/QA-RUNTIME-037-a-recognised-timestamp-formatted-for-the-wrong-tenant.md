# QA-RUNTIME-037 — A recognised timestamp, formatted for the wrong tenant

## Preconditions

A tenant on which the affected surface is reachable, and a signed-in user with
the permissions the surface requires. REG-342 in the regression register carries
the full root cause; this scenario is the reusable check, not the diagnosis.

## Steps

With `setDefaultFormattingContext` set to one tenant configuration (`MM/dd/yyyy`, 12h, UTC), a timestamp formats to that shape and contains no raw `T`. With a *different* configuration (`dd/MM/yyyy`, 24h) over the *same* input, the result changes accordingly — proving the fix reads configuration rather than coincidentally matching one tenant's format. A date-only ISO string formats through the same helper.

## Expected Result

The behaviour holds as REG-342 describes it. The automated guard is `apps/web/app/components/dashboard/dashboard-widget-formatting.spec.ts`; a run of that suite is sufficient evidence for this scenario.

## Why This Is Reusable

`dashboard-widget-renderer.tsx`'s `formatValue` already recognised an ISO-8601 timestamp and formatted it, but with `Date.prototype.toLocaleString(undefined, {...})` — the visiting browser's own locale and local timezone, not the tenant's configured `dateFormat`/`timeFormat`/`timezone`. This is the direct violation of the AGENTS.md rule this record's own Evidence section cites ("never call `toLocaleDateString` ad hoc"), on the one widget that had partially tried to handle it and gotten the source of truth wrong.
