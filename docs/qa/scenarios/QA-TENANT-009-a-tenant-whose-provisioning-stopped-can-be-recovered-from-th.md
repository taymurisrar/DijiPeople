# QA-TENANT-009 — A tenant whose provisioning stopped can be recovered from the console

## Preconditions

A tenant in `PROVISIONING` or `PROVISIONING_FAILED`, and the ability to stop the
API process mid-run for the manual half.

## Steps

1. `npm --workspace api run test -- provisioning-operations`
2. Manual: start provisioning a tenant and stop the API process before the run
   completes. Restart the API.
3. Open the tenant record → **Operations** immediately.
4. Wait past the stall threshold (thirty minutes) and reload.
5. Press **Retry provisioning**.
6. While a genuine run is executing, open the panel and check the button.

## Expected Result

Step 3: State reads IN_PROGRESS, Retry is disabled, and the reason says retry
becomes available if the run stops making progress.

Step 4: State reads **STALLED**. A "Next step" line above the panel says the
process that owned the run is gone and to retry. Retry is **enabled**.

Step 5: the retry runs, replaying only retryable steps.

Step 6: Retry is disabled while steps are recording, whatever the target says.

## Expected Result — the part that is not fixed

A tenant that failed at or before the business-unit step still cannot be
activated, and the retry may report SUCCEEDED anyway. That is [[BUG-0015]],
which is open. This scenario verifies that a stuck tenant becomes *recoverable*;
it does not verify that every recovered tenant is usable.

## Notes

The stored `TenantProvisioningRunStatus` has no terminal value for "the process
died holding this" — the row is created RUNNING and moved on by the process
executing it, so a crash leaves it RUNNING for ever and nothing sweeps it. The
retry gate refused on that raw status, so the only control that could recover
the tenant was disabled permanently under a sentence that was false.

Consideration when re-running: allowing retry from STALLED is safe *because*
replay is idempotent by design — only retryable steps re-run, and owner,
subscription and invoice creation never do. If that ever stops being true, this
gate becomes unsafe and this scenario is the place it should fail.

Thirty minutes is a long wait for a manual test. To exercise step 4 without it,
run the automated half, which asserts the same boundary in both directions.
