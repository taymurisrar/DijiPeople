# QA-PLATFORM-031 — The under-investigation count is measured from the states it names

## Preconditions

None. The predicate and the view filter are pure functions.

## Steps

Assert `INVESTIGATING_SUPPORT_STATUSES` is exactly `INVESTIGATING` and
`FIX_IN_PROGRESS`, and that it contains none of `NOT_AN_INCIDENT`, `NEW`,
`RESOLVED` or `WAITING_ON_CUSTOMER`. Assert
`incidentViewWhere("investigating")` equals `investigatingIncidentWhere()`.
Assert the `new`, `resolved` and default views are unchanged.

On the screen: read the "Under investigation" tile, then click it and count
the rows the queue returns.

## Expected Result

The tile equals the number of incidents actually in an investigating state,
and equals the row count of the list its link opens. With only `NEW` and
`NOT_AN_INCIDENT` rows present — which is production today — it reads 0.

The four excluded statuses each mean "nobody is working on this", for four
different reasons. Readmitting any of them is the original defect.

## Why This Is Reusable

This screen has now had the same fault twice: REG-281 was a tile counting 11
and linking to 0, where "critical" had been spelled three different ways.

The transferable lesson is about the *shape*, not the field: **inferring a
count by subtracting the states you know about is only correct until someone
adds a state.** `total - open - resolved` was true for years and became false
the day `NOT_AN_INCIDENT` was introduced, with nothing to fail. Re-run on any
change to the support-status set — adding a status is exactly the event that
breaks a derived count.
