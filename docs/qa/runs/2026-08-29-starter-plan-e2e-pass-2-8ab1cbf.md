## Requirement

The first Starter-plan production pass returned FAIL, and its Known Limitations
named three things it had not established: documents were only shown to *have*
New/Edit/Delete buttons, `POST /api/employees/import` had **never been executed**
in either direction, and no mobile or tablet width was exercised at all. This
pass exists to close those three gaps — to turn "unverified" into either a
verified pass or a recorded defect, so the Starter release decision rests on
measurement rather than on the absence of measurement. There is no ExecPlan: this
is exploratory QA against production, not a change.

## Risk Areas

- **Documents were the weakest claim in the first pass.** "The related list has
  New/Edit/Delete buttons" is the `unreachable-surface` pattern waiting to
  happen: a control that renders is not a path that works, and upload crosses
  MIME validation, storage and a read-back — three places to fail quietly.
- **Import is a bulk write.** A loader that maps columns but does not resolve
  lookups produces rows with null foreign keys that look created and are not —
  `silent-degradation` on a write path.
- **BUG-2026 asserted a broken round trip without ever calling the importer.**
  Its own Evidence section says so. A record naming one endpoint broken while
  never exercising it invites the reader to conclude the whole capability is
  dead — `doc-code-drift` inside the bug register itself.
- **BUG-1668 was deferred on measurements taken against an empty tenant.** A
  layout defect measured with no data is measured at its best case.
- No entry in `docs/qa/regressions/index.md` covers the document upload path, the
  employee import path, or any viewport assertion.

## Manual Validation

Everything in the scenario table was executed by hand.

The documents and import scenarios were driven as authenticated HTTP calls
against the production API as the tenant owner, reading the responses directly —
status, headers, and the first bytes of each returned body, which is what
distinguishes a real PDF from an error page served under the wrong content type.
The 192-byte length and the `%PDF-1.4` prefix were checked on **both** the
download and the view route, because a viewer that streams a different object
than the downloader is a failure that a status-code-only check would miss.

The responsive scenarios were measured, not eyeballed. Horizontal overflow is
`max(body.scrollWidth, documentElement.scrollWidth) - innerWidth`, taken at
390×844 and 768×1024 signed in as the tenant owner. The sidebar width and the
collapse control's computed style and bounding rectangle were read from the live
DOM at each width. BUG-1668's own QA Retest section asks for exactly this:
"retest by measuring, not by looking".

Two pieces of demo data were added and deliberately kept — both keepable, neither
generating email: one PDF document on Fatima Zahra (EMP-0005), type
"CV / Resume", and one employee, EMP-0012 Rania Fahmy, created through the import
path so the tenant carries a record demonstrating bulk import.

## Known Limitations

What could **not** be established here:

- **One document, one type, one employee.** The upload path was exercised with a
  single 192-byte PDF. No size limit, no multi-file upload, no archive or delete
  of an uploaded document, and no second document type were tested.
- **No authorization boundary was crossed on documents.** Every call was made by
  the tenant owner. Whether a SELF-scoped employee can reach a colleague's
  document is REG-041's question and remains unanswered on this environment.
- **One import row.** `successCount: 1` proves the loader resolves lookups; it
  does not prove behaviour at volume, on partial failure, on a duplicate
  `employeeCode`, or on a lookup name that does not resolve. The `errors` array
  was empty, so nothing was learned about how a bad row is reported.
- **The export side of BUG-2026 was not re-tested** — pass 1's header comparison
  stands unaltered, and this pass does not soften it.
- **Four routes, two widths, layout only.** `/`, `/employees`, `/leaves` and
  `/attendance` at 390×844 and 768×1024. Settings pages, record pages and the
  admin console were not measured at these widths, and no touch interaction was
  tested: a control being on screen is not the same as it being usable with a
  thumb.
- **Everything the first pass covered was out of scope** and was not re-run. This
  pass revises no verdict in it.

## Final QA Verdict

**FAIL** — on the responsive scenarios alone.

Two of the three gaps closed cleanly. Documents is genuinely shippable: the write
path validates its input, refuses what it should refuse with a message that names
the offending field, and returns the stored bytes byte-identical on both read
routes. The employee importer works, and does more than column mapping — it
resolves department, designation and emergency-contact relation type by name into
real foreign keys, which is the part that would have been most expensive to
discover broken in the middle of a customer's onboarding.

The third does not close. At 390px the landing screen of the tenant workspace is
790px wide against a 390px viewport, the navigation occupies 56% of the screen,
and the control that would collapse it is `display: none` below 1280px — the one
width at which it costs nothing. That is BUG-1668, already recorded and currently
`DEFERRED` on measurements taken against an empty tenant. A scenario failed, so
the verdict is FAIL; the failure being already known does not convert it into a
pass.

Record validation: `npm run backlog:check`, `npm run qa:check` and
`npm run validate:framework` were run after these records were written and staged,
and all three passed with zero errors.
