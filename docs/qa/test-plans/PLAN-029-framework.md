# PLAN-029 — Agent framework record and id integrity

## Scope

The machinery that keeps durable records addressable: id allocation, the
generated indexes, and the graph the vault is published into. Covers `scripts/`
and `scripts/lib/`.

**Deliberately excludes** the product. Nothing here touches `services/api` or
`apps/*`; a failure in this area costs traceability, not behaviour.

The area existed before this plan did — `validate-framework.mjs` runs 4,600+
structural checks — but with no QA plan, a framework scenario had nowhere to be
filed and would never be selected for a re-run.

## Risks

Ranked by what has actually gone wrong here, not by imagination:

1. **An id collision.** Two records sharing a number makes every link to it
   ambiguous, and renumbering afterwards touches every record that cites it.
   Happened three times: twice by agents counting files, once by the allocator
   itself ([[BUG-2413]]).
2. **A check that passes vacuously.** The orphan check reported 0 while 182 notes
   were disconnected, because four whole categories were exempt and two of the
   exemption reasons asserted an edge that did not exist. A guard nobody can see
   failing is worse than no guard.
3. **A generated artefact drifting from its source.** `database-architecture.md`
   described "~285 models" against a schema holding 318.
4. **Byte comparison against a CRLF checkout** — a check green on Linux CI and
   permanently red on Windows. BUG-1208, and repeated in the data-model generator
   before it shipped.

## Preconditions

A git checkout. No database, no server, no credentials, no network.

Both plan families must be present — `docs/qa/test-plans/` and `docs/plans/` —
because the id cases turn on a prefix that spans them.

## Test Types

**UNIT** applies and is the whole of it: `node --test` over the scripts, plus
`validate-framework.mjs` as a structural pass.

**API, DATABASE, INTEGRATION, E2E, BROWSER_E2E, SECURITY** do not apply. This
area has no runtime surface, no tenant data and no external boundary.

## Data Requirements

Temporary fixture trees created per test and removed after — never the
repository's own records. A case asserting against live records stops failing for
the right reason as soon as somebody files a new one.

## Security Cases

Not applicable. No tenant data, no authorization, no external input.

## Negative Cases

- A kind whose directory does not exist returns an empty scan rather than
  throwing.
- A kind declaring a single string `dir` keeps working after `dir` became a list.
- An unreadable file is skipped rather than aborting a ceiling scan.

## State Transitions

Not applicable — the allocator has no state machine. The one ordering rule that
matters: a reservation is taken **before** the record exists, and `--prune` never
releases a reservation whose record was never created. A gap in a sequence is
cheaper than a collision.
