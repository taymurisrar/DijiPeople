# PLAN-003 — Tenant Isolation

## Scope

The single most important invariant in this codebase, and the one enforced by
**convention alone**. There is no PostgreSQL row-level security, and the
`PrismaService` `$use` middleware scopes by business unit rather than tenant —
and on `@prisma/client@7.8.0` `$use` is unavailable, so it is inert. Every
tenant-scoped query is scoped because somebody wrote `tenantId` into the
`where` clause by hand.

That is why this plan exists as its own area rather than as a section of
`authorization`: the failure mode is silent, and nothing in the product surfaces
it.

## Risks

- `findUnique` by bare id on a tenant-owned model.
- A `tenantId` taken from a request body, query string, path parameter or header
  rather than from `request.user`.
- An update or delete that filters by id alone.
- A background job, queue processor or seed with no request context that forgets
  to thread `tenantId` through.
- A platform-path endpoint widened to serve tenant needs, or the reverse
  (`BUG-0005`).

## Preconditions

Two fixture tenants with a per-run identifier, so a failed run that skipped cleanup cannot collide with the next.

## Test Types

`UNIT` runs locally. `DATABASE` and `E2E` run in CI against ephemeral
PostgreSQL. In run `32009837400`, the generic tenant-isolation, workspace-domain
and erasure suites passed while attendance-integration isolation failed; WP-04
must classify that failure before this plan returns to `CURRENT`.

## Data Requirements

`services/api/test/helpers/db-fixtures.ts` is the shape to copy: two tenants, a write under one, a scoped read and a scoped write attempted from the other, then cleanup.

## Security Cases

Cross-tenant read, cross-tenant write, and enumeration — all three, for every model the change touches. Never risk-weighted down.

## Negative Cases

Foreign-tenant id on read · on update · on delete · in a filter · in a relation include.

## State Transitions

Tenant lifecycle: provisioning → active → suspended → erased. An erased tenant's rows must not be reachable.

## Integration Cases

Attendance integrations hold per-tenant device credentials, which makes them the highest-value isolation target outside core HR data.

## Browser Cases

Not meaningful — isolation is a server property and a browser cannot demonstrate its absence safely.

## Review — 2026-08-22, against `0c61b7e`

Moved from `NEEDS_REVIEW`. One scenario added: [[QA-TENANT-015]], which closes
the half of tenant erasure [[QA-TENANT-005]] could not reach.

[[QA-TENANT-005]] proves the delete **order** is one PostgreSQL accepts, on a
single fixture tenant. That answers "is the tenant gone?", which is the easy half
and not the risk. Erasure is 242 `deleteMany` calls whose correctness rests
entirely on a `tenantId` predicate; one missing predicate deletes a neighbour's
rows, the transaction commits, and nothing notices — because no neighbour was
there to notice with.

[[QA-TENANT-015]] seeds two tenants identically, erases one, and probes the other
across all three erasure collections, including each detached model's cleared
fields. Detachment is not deletion: the relation-scoped clear can reach a
neighbour's contract, order or refund and gut it while leaving the row present,
and those belong to a different paying customer.

The other coverage claims are unchanged and were not re-verified beyond that.
