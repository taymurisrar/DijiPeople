# BUG-2333 — storeUserAgent is ignored on the attendance module check-in path

## Summary

`storeUserAgent` is a tenant privacy setting controlling whether the employee's
browser user-agent string is recorded with their attendance. The attendance
module's own check-in path ignored it and attached the user agent to every
request unconditionally.

## Expected Behavior

With `storeUserAgent: false`, a check-in carries no `userAgent` field.

## Actual Behavior

The full browser UA string was sent on every check-in and check-out regardless
of the setting.

## Reproduction

1. On a tenant whose attendance policy reports `storeUserAgent: false`
   (confirmed via `GET /api/attendance/runtime-context`), open `/attendance`.
2. Press **Check In** with DevTools open on the Network tab.
3. Read the `POST /api/attendance/check-in` request body.

## Evidence

`GET /api/attendance/runtime-context` on the demo tenant, 2026-08-30:

```json
"policy": { "storeIpAddress": false, "storeUserAgent": false, ... }
```

The check-in that followed, same session, same page:

```json
{"userAgent":"Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 ...",
 "locationLatitude":25.2854, "locationSource":"GPS", ...}
```

Source, `apps/web/lib/runtime/modules/standard-module-data.adapter.ts`:

```ts
const locationPayload = buildLocationPayload(location, {
  userAgent: typeof navigator === "undefined" ? undefined : navigator.userAgent,
});
```

No reference to `policy.storeUserAgent`, though `policy` is already in scope on
the line above and is consulted for three other values.

## Root Cause

Two capture paths exist and only one honours the policy.
`module-runtime-command-handler.tsx` gates correctly on
`policy.storeUserAgent`; this adapter — the path the attendance module's own
Check In button uses — never did. The duplication is the defect: the same
decision is made in two places and drifted.

## Impact

A tenant that switches off user-agent storage still has it transmitted and
persisted on the surface where nearly all attendance is recorded. A privacy
control that reports itself as off while being on is worse than not offering it.

Limited to the user-agent string. `storeIpAddress` is resolved server-side and
was not affected.

## Affected Areas

- `apps/web/lib/runtime/modules/standard-module-data.adapter.ts` —
  `attendance.checkIn` and `attendance.checkOut`

## Proposed Resolution

Gate on `booleanValue(policy.storeUserAgent)`, matching the sibling path. The
longer-term fix is for one function to own this decision instead of two, but
that is a refactor of the runtime command layer and is not required to stop the
leak.

## Acceptance Criteria

- With `storeUserAgent: false`, the check-in body contains no `userAgent`.
- With `storeUserAgent: true`, it does.

## Regression Coverage

`apps/web/lib/runtime/modules/attendance-location-payload.spec.ts` — REG-362.
Source-level with comments stripped first, which is load-bearing rather than
hygiene: the fix's own comment names `storeUserAgent` while describing the bug,
so without stripping the test would pass against reverted code on the prose
alone. It asserts the adapter consults the policy and that the shipped defect
shape — a `userAgent` guarded only by `typeof navigator === "undefined"` — is
absent. Mutation-tested: restoring the exact shipped line fails two of three.

A behavioural test would be better. `buildAttendanceLocationPayload` is
module-private and reachable only through a command handler needing a full
runtime context, so the harness for one does not exist yet; that gap is real and
is recorded here rather than papered over.
