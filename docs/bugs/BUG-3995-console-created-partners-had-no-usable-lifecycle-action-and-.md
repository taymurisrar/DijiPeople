# BUG-3995 — Console-created partners had no usable lifecycle action and the review actions failed with an opaque submission error

## Summary

A partner created in the admin console starts at DRAFT (ADR-0026, TASK-0037 WP-04), but there was no action that could move it on. The DRAFT record offered only Delete and Reject. Create agreement was hidden. The inquiry-review actions (Start review, Approve, Request information, Reject) assume the partner came from a partner inquiry. When run on a console partner they failed with "The immutable partner application submission was not found.", which was shown as a generic validation error.

## Expected Behavior

There are two entry paths, and each offers only the actions that can work.
- **Inquiry partners:** review, approve and reject.
- **Console partners (agreement-first):** DRAFT, then Create agreement, then signing, then the onboarding link, then onboarding approval, then Activate.

## Actual Behavior

- `create-agreement` was only visible in APPROVED_AWAITING_AGREEMENT and ACTIVE.
- Approve and reject threw a bare BadRequestException whenever no PartnerInquiry existed.
- Record commands had no condition-based visibility, so there was no way to hide review actions on a console partner.

## Reproduction

1. In admin, create a partner. It starts in DRAFT.
2. The only actions offered are Delete and Reject. No action leads towards an agreement.

## Evidence

TASK-0037 browser pass on the isolated stack, 2026-10-08. The Approve request returned 400 VALIDATION_FAILED with the message "The immutable partner application submission was not found.".

## Root Cause

WP-04 correctly stopped the admin form from seeding status NEW_INQUIRY, which was a pretend inquiry. Nothing then gave console partners their own path forward. The review actions and the create-agreement visibility rules had both been written for the inquiry path only.

## Impact

Operators could not take any partner created in the console beyond DRAFT.

## Affected Areas

The partner record commands in apps/admin, and the partner lifecycle actions in the API.

## Proposed Resolution

Add `requiresInquiry` to the review actions in the shared table. Add a generic command `visibleWhen` setting to the admin runtime. Make Create agreement available from DRAFT. Return a domain error when an inquiry action is used without an inquiry.

## Acceptance Criteria

- A console DRAFT partner offers Create agreement and Delete, and no review actions.
- An inquiry partner keeps its review actions.
- An inquiry action on a partner without an inquiry returns 409 `PARTNER_INQUIRY_REQUIRED`.
- Approve or reject on a partner that does not exist returns 404.

## Resolution

- `requiresInquiry` is set on 4 actions in the lifecycle table.
- `PartnersService.get` now returns `hasInquiry`.
- A shared `visibility-condition.ts` matcher replaces two diverging copies; it now also reads nested fields.
- `command-visibility.ts` evaluates `states` together with `visibleWhen`.
- Create agreement is available from DRAFT and from the in-flight agreement states.
- `PARTNER_INQUIRY_REQUIRED` is returned with a 409.
- `docs/architecture/partners.md` now documents both entry paths.
