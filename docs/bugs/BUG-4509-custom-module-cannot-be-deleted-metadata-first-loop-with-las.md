# BUG-4509 — Custom module cannot be deleted: metadata-first loop with last default form

## Summary

Deleting a custom module (Settings > Customization > Modules) was refused while the module still had any field, form or view, and its last default form could not be deleted either, so a module with only its main form could never be removed.

## Expected Behavior

A custom module can be deleted directly. Its own fields, forms, views and records go with it after a confirmation that states the impact. Only a reference from another module blocks the delete.

## Actual Behavior

Deleting the module said to remove its metadata first. Deleting the main form said "Cannot delete the last active default/system form for this table."

## Reproduction

1. Create a custom module with only its default main form.
2. Delete the module: refused, metadata dependencies.
3. Delete the main form: refused, last default form.

## Evidence

`CustomizationService.deleteTable` failed when the dependency summary total was above zero, and `deleteForm` refused the last active default form (`services/api/src/modules/customization/customization.service.ts`). All five child tables of CustomizationTable are ON DELETE CASCADE in the database.

## Root Cause

The module delete treated the module's own forms, fields and views as external dependencies.

## Impact

Any tenant admin with a custom module; the module could never be removed.

## Affected Areas

customization API, `tables-list.tsx` delete dialog.

## Proposed Resolution

Cascade the module's own metadata; block only on lookups from other modules; show impact in the dialog.

## Acceptance Criteria

A module with forms deletes after the impact dialog; a module referenced by another module's lookup field is blocked and the referencing fields are listed.
