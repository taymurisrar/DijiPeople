# BUG-4427 — Safepay appends order_id to a success URL that already has a query string, so the onboarding id reaches the API malformed (uuid v4 is expected)

## Summary

The buyer's return from Safepay checkout lands on `/subscribe/success?onboarding=<uuid>?order_id=<ref>`. Safepay appends its own `?order_id=` to the success URL without checking for an existing query string, so the `onboarding` parameter's value is `<uuid>?order_id=<ref>`. The landing page forwarded it verbatim as a path segment and the API answered `400 Validation failed (uuid v4 is expected)`.

## Expected Behavior

The success page extracts the onboarding id and polls the status endpoint.

## Actual Behavior

The status poll 400s straight after payment; the buyer sees a failed poll instead of provisioning progress. 22 production occurrences, last 2026-11-03, row `/api/public/onboarding/<uuid>%3Forder_id`.

## Reproduction

1. Complete a Safepay checkout (or open `/subscribe/success?onboarding=<uuid>?order_id=X`).
2. The page polls `/api/public/onboarding/<uuid>%3Forder_id=X/status`.
3. API: 400 `uuid v4 is expected`.

## Evidence

Production `ErrorLog` (read-only aggregate, 2026-11-19): 1 row, 22 occurrences, module `public`, path `/api/public/onboarding/ed47cfb0-…%3Forder_id`. `safepay.gateway.ts:220-221` sets `redirect_url: input.successUrl`; `billing.service.ts:918` builds `/subscribe/success?onboarding=<id>`.

## Root Cause

Provider-side URL concatenation. The page trusted the query value instead of parsing the one id it needs.

## Impact

Growth-plan demo path and production monitoring signal quality.

## Affected Areas

[landing, billing]

## Proposed Resolution

`parseOnboardingId()` in `apps/landing/lib/provisioning-view.ts` takes the leading UUID; `subscribe/success/page.tsx` uses it. Spec `provisioning-view.spec.ts › parseOnboardingId`.
