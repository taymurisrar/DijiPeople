# BUG-3138 — Password reset unconditionally reactivates a disabled account

> **Architect triage, 2026-09-11 — `FIX_NOW`.** A password reset that reactivates a disabled account turns offboarding into a suggestion. Small, and the consequence is somebody who was removed getting back in.

## Summary

Password reset unconditionally reactivates a disabled account

Identified by the 2026-09-10 full technical audit as AUTH-02 (confidence: AUTH-02=CONFIRMED).

## Expected Behavior

Refuse the reset unless the user is currently `ACTIVE` (or `INVITED` for an activation flow) and the tenant is `ACTIVE`; never widen `status` as a side effect of a password write.

## Actual Behavior

A `password-reset` JWT is valid for 24 hours (`expiresIn: '1d'`, `auth.service.ts:851`). If the account is disabled during that window, redeeming the link sets a new password **and flips `status` back to `ACTIVE`**, and `mirrorPasswordToIdentity` propagates the credential to the shared identity. `AuthAccessService.loadAccessContext` then admits the session normally.

## Reproduction

This is a code-review finding from a static technical audit, not a QA-run runtime reproduction. To confirm: open the file(s) cited in Evidence and trace the call path described in Actual Behavior.

## Evidence

**AUTH-02** (services/api/src/modules/auth/auth.service.ts):

`services/api/src/modules/auth/auth.service.ts:925` — the handler verifies the JWT and then never loads the user before writing:
```ts
    if (
      payload.type !== 'password-reset' ||
      !payload.sub ||
      !payload.tenantId
    ) {
      throw new UnauthorizedException(...);
    }
```
`services/api/src/modules/auth/auth.service.ts:957` — the write:
```ts
      await tx.user.update({
        where: { id: payload.sub },
        data: {
          passwordHash,
          passwordChangedAt: new Date(),
          status: 'ACTIVE',
          updatedById: payload.sub,
        },
      });
```
There is no read of `user.status`, `user.tenant.status`, or `Identity.status` anywhere in the method.
Contrast `resetAdminPassword` at `auth.service.ts:504`, which does check: `if (!user || user.status !== 'ACTIVE' || currentVersion !== payload.passwordVersion)`.

## Root Cause

resetPassword wrote status ACTIVE unconditionally and never checked the account or tenant status.

## Impact

Standard offboarding — an employee is terminated and their user disabled. If they asked for a password reset in the preceding 24 hours (a completely ordinary thing to do on the day you are let go), the link in their personal mailbox restores their account and every role attached to it: payroll, employee PII, documents. The audit trail records a password reset, not a reinstatement.

## Affected Areas

services/api/src/modules/auth

## Proposed Resolution

In `AuthService.resetPassword`, load the user with its tenant inside the transaction, reject unless `user.status !== 'DISABLED'` and `tenant.status === 'ACTIVE'`, and replace `status: 'ACTIVE'` with a conditional promotion of `INVITED → ACTIVE` only.

(Difficulty: LOW; Regression risk: LOW; Fix now: YES)

## Resolution

resetPassword now refuses a DISABLED account or a non-active tenant with the same generic answer as an invalid link, and the compare-and-set write carries status not DISABLED so a disable landing between the read and the write also loses. INVITED users still activate by reset (existing behaviour, kept).
