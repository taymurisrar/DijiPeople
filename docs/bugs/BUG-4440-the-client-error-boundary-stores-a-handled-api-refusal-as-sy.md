# BUG-4440 — The client error boundary stores a handled API refusal as SYSTEM_UNEXPECTED_ERROR (500) in monitoring

## Summary

When a server page renders an API refusal through its error boundary, the client reports it with no status and `POST /error-logs/client` defaults it to 500 `SYSTEM_UNEXPECTED_ERROR`, severity ERROR. A handled 400 (password reset needs a linked user; unsupported setting key) therefore shows as a system fault.

## Expected Behavior

A handled refusal is stored with its real status and classified like the same event seen server-side.

## Actual Behavior

Two production rows (2026-08-28, 2026-09-11) are stored as 500 with a 400-class message.

## Reproduction

1. Trigger a handled API refusal on a server-rendered page. 2. Observe the monitoring row.

## Evidence

Production ErrorLog read 2026-11-19; `error-logs.controller.ts` defaults `statusCode` to 500.

## Root Cause

The boundary has no upstream status for server-component errors.

## Impact

Operators see ERROR-level rows for non-faults.

## Affected Areas

error-logs controller, web error boundary.

## Proposed Resolution

Carry the upstream status from the boundary, or classify by message for known refusals.
