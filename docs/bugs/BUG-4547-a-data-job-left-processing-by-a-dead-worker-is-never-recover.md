# BUG-4547 — A data job left PROCESSING by a dead worker is never recovered

## Summary

A data job claimed by a worker that then died (crash, deploy, OOM) stayed in PROCESSING forever: nothing recovered it, it blocked a re-run, and the submitter saw an import that never finished. The worker only claimed QUEUED jobs.

## Expected Behavior

A stranded job is detected, and then re-queued, resumed or finalised without applying any import row twice; where replay is not provably safe the uncertain row is parked and surfaced, never silently retried.

## Actual Behavior

The job stayed PROCESSING indefinitely.

## Reproduction

1. Start an import; kill the API process mid-run (or deploy). 2. Observe the DataJob stays PROCESSING with no owner and no heartbeat. 3. Nothing ever moves it. Reproduced against real PostgreSQL by `services/api/test/data-job-recovery.e2e-spec.ts`.

## Evidence

`services/api/src/modules/data-management/data-job-worker.service.ts` claim loop (QUEUED only) before this change; `DataJob` had no owner or lease columns. Found by SESSION-0135 while auditing the worker.

## Root Cause

Job ownership was implicit in the status column: PROCESSING meant "someone started this", with no way to tell whether that someone was alive.

## Impact

Any import or export interrupted by a restart or crash; reachable in production on every deploy that lands mid-job.

## Affected Areas

services/api/src/modules/data-management; DataJob and DataJobRow tables (additive migration).

## Proposed Resolution

Lease-based ownership, a recovery pass, and per-chunk checkpointing (see Resolution).

## Acceptance Criteria

A stranded job recovers once even with racing recoverers; no row is applied twice; the single unknown row is parked with an explicit message; retries are capped; live leases are never touched; audit log records the recovery.

## Resolution

Fixed on `agent/security-timesheet-datajob-followup`. `DataJob` gains `claimedBy` and `leaseExpiresAt` (renewed on a timer while the worker runs); `DataRowStatus` gains `IN_PROGRESS`, set per chunk before any row is applied. `DataJobRecoveryService` takes a single-winner conditional claim on a lapsed lease, then: re-queues an export (idempotent), and for an import parks the lowest-numbered IN_PROGRESS row (the only one whose outcome is unknown, because rows are applied strictly in order) as FAILED with an explicit message, returns the never-started rows to VALID, and resumes with counters carried forward. Retries are capped at 3. Every recovery writes an audit record. A worker that was only paused re-confirms ownership against the database before each row and stops if it was taken over. Verified with 8 PostgreSQL tests, mutation-checked.
