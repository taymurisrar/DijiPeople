# BUG-3888 — Safepay webhooks fail because SAFEPAY_WEBHOOK_SECRET is not configured in production

## Summary

Production received Safepay webhook calls on 2026-09-26 and could not process
them. The first failed because `SAFEPAY_WEBHOOK_SECRET` is not configured on
the API service, so the gateway refused it with `PAYMENT_PROVIDER_NOT_CONFIGURED`
(503). A later one failed signature verification (400). Until the secret is set,
no Safepay payment event can be trusted or applied, so PKR checkout through
Safepay cannot go live.

## Expected Behavior

Every environment that can receive Safepay webhooks has the webhook secret
configured, verifies each delivery's signature, and applies verified events.

## Actual Behavior

- 2026-09-26 18:11 — `PAYMENT_PROVIDER_NOT_CONFIGURED` 503, "SAFEPAY_WEBHOOK_SECRET
  is not configured."
- 2026-09-26 21:24 — `VALIDATION_FAILED` 400, "Safepay webhook signature could
  not be verified."
- 2026-09-26 22:28 and 23:19 — two `GET` requests on the webhook path, 404
  "Cannot GET". These look like reachability probes, not deliveries.

## Reproduction

1. On an environment without `SAFEPAY_WEBHOOK_SECRET`, `POST` any body to
   `/api/billing/safepay/webhook`.
2. The response is 503 `PAYMENT_PROVIDER_NOT_CONFIGURED`, and an `ErrorLog` row
   is written.

## Evidence

- Production `ErrorLog`, read-only query on 2026-10-07: 4 occurrences, all on
  2026-09-26 between 18:11 and 23:19, no tenant on any row.
- Stack of the 503: `SafepayGateway.require` in the compiled
  `billing/providers/safepay.gateway.js:328`.
- Whether the secret has been set since then was not checked. Reading the
  Render environment was refused during the triage.

## Root Cause

A deployment configuration gap. The code fails closed as intended. The secret
was never added to the production API service, and `render.yaml` is not
synchronised to the service on its own.

## Impact

- No Safepay payment can be confirmed by webhook in production. A customer who
  pays through Safepay would not be activated automatically.
- The severity is HIGH because Safepay is the planned PKR checkout path. If
  Safepay is not yet taking payments when this record is next read, MEDIUM is
  the honest severity.

## Affected Areas

- `services/api/src/modules/billing/providers/safepay.gateway.ts`
- The production API service environment on Render.
- PKR checkout on the landing site.

## Proposed Resolution

Set `SAFEPAY_WEBHOOK_SECRET` on the production API service from the Safepay
dashboard, redeploy, and send a test webhook from Safepay. Do this before
ITEM-0210 moves PKR checkout to Safepay. No code change is needed.

## Acceptance Criteria

- A Safepay test webhook to production returns 2xx and is applied.
- A delivery with a wrong signature is rejected with 400, and nothing is applied.
- No `PAYMENT_PROVIDER_NOT_CONFIGURED` row appears for Safepay after the change.
