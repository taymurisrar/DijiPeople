# BUG-3698 — Draft edits to custom fields take effect before they are published

## Summary

Editing a custom field (label, required flag, validation) writes straight to the live `CustomizationColumn` row, and the runtime reads live column rows for every column the last publish included. A draft edit therefore reaches users before anyone publishes it, while form and view edits correctly wait for publish.

## Expected Behavior

A field edit takes effect when it is published, like a form or view edit.

## Actual Behavior

The edit is visible immediately to anyone using the custom module.

## Reproduction

1. Publish a custom module with a field.
2. Edit the field's label or make it required; do not publish.
3. Open a record of that module: the new label or requirement applies.

## Evidence

- `services/api/src/modules/customization/customization.service.ts` `updateColumn` updates the base row in place.
- `services/api/src/modules/data/custom-module-runtime.service.ts` `resolvePublishedTable` takes column ids from the snapshot but reads the live rows.

## Root Cause

Columns have no draft layer; the snapshot stores which columns are published, not what they looked like.

## Impact

Administrators cannot stage a field change. A required flag added in draft blocks saves immediately. Reachable in production.

## Affected Areas

customization (columns), data (custom module runtime).

## Proposed Resolution

Serve column definitions from the publish snapshot as forms and views already are, or give columns a draft layer. Needs a plan: it changes when edits take effect.

## Acceptance Criteria

An unpublished field edit is invisible at runtime; publishing makes it visible.
