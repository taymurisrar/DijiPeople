# BUG-3579 — An attributed lead never shows its referral partner

## Summary

A lead attributed to a referral partner — whether automatically, through a
referral code, or manually via the attribution-correction endpoint — never
displayed that partner anywhere in the admin lead record, even though the
scalar `partnerId` was stored correctly. The lookup field and the new
partner-attribution panel both need the embedded partner record, not just its
id, and the API never sent it.

## Expected Behavior

A lead's record page should show its currently attributed partner (name, type,
status), both in the generic `partner` lookup field and in the
partner-attribution panel introduced alongside REG-557/REG-558/REG-559.

## Actual Behavior

`LeadsService.getLead()` returned only the scalar `partnerId` field. The
runtime form's lookup renders its label from an embedded `values.partner`
object; with none supplied, the field rendered with no label at all, and the
attribution panel had no "current partner" value to show, so an operator
correcting attribution could not see what the lead was already attributed to
before changing it.

## Reproduction

1. Attribute a lead to a partner (via referral code or the attribution-
   correction endpoint).
2. Open the lead's record page in `apps/admin`.
3. Observe the partner lookup field has no visible name, and the partner
   attribution panel shows no current partner.

**Live reproduction, throwaway stack, 2026-09-25** (TASK-0032 WP-09 QA,
partners Defects 2 and 3): confirmed `getLead` responses carried `partnerId`
with no embedded `partner` object.

## Evidence

- `services/api/src/modules/leads/leads.service.ts` — `getLead()`'s `select`/
  `include` shape omitted the `partner` relation entirely.
- `apps/admin` lead runtime form and the partner-attribution panel — both read
  `values.partner` for the display label; neither had a fallback fetch.

## Root Cause

A lookup field's label depends on an embedded relation the read path never
embedded — the API was a scalar-id-only contract for a field the frontend
already expected as an object.

## Impact

Every attributed lead — the primary object the WP-04 attribution-correction
work exists to manage — was indistinguishable from an unattributed one on its
own record page, undermining the very feature (REG-557/558/559) built to let
an operator review and correct attribution deliberately.

## Affected Areas

- `services/api/src/modules/leads/leads.service.ts` (`getLead`)
- `apps/admin` lead record page — the partner lookup field and the
  attribution panel

## Proposed Resolution

Embed a minimal `partner { id, displayName, type, status }` on `getLead()`'s
response and have the attribution panel and lookup field read it. No ExecPlan
needed — read-path addition only, no schema change.

## Acceptance Criteria

- `getLead` returns `partner { id, displayName, type, status }` for an
  attributed lead, and nothing else about the partner.
- The lead record page's lookup field and attribution panel both show
  "Current partner" for an attributed lead.
