# BUG-3786 — Adding a custom field ignores the table's isCustomizable flag

## Summary

Each system table in the customization registry has an `isCustomizable` flag. Permission and Country set it to false. Nothing reads the flag when a custom field is added, so an administrator can add fields to tables that were declared closed.

## Expected Behavior

Adding a custom field to a system table whose `isCustomizable` is false is refused, with an error naming the table. The same holds for a field arriving through a package import.

## Actual Behavior

`createColumn` creates the field. Package import creates it too.

## Reproduction

1. As a customizer, `POST /customization/tables/permissions/columns` with `{ "columnKey": "ad_note", "displayName": "Note", "dataType": "text" }`.
2. The response is 201, and the field exists on Permissions.

## Evidence

- `services/api/src/modules/customization/customization.service.ts`, `createColumn`: the only guard refuses reusing a system column key.
- `customization.registry.ts`: `isCustomizable: false` on Permission and Country, and the flag is read nowhere in the column path. The route-mapping explorer found this on 2026-09-27; `grep` confirms it.

## Root Cause

The flag was added to the registry and synced into each tenant's `CustomizationTable` row, but no write path checks it.

## Impact

It is reachable in production by any user with `customization.publish`. The result is fields that can never hold a value: Permission and Country have no edit route. Under ADR-0024, thirteen more tables are closed for the same reason. No data is at risk, but the product offers something that silently does nothing.

## Affected Areas

The customization column editor (Settings → Customization), `POST /customization/tables/:tableKey/columns`, and package import.

## Proposed Resolution

Enforce the flag in `createColumn`, and in the package comparison as a blocking INCOMPATIBLE item. Part of EXECPLAN-0054.

## Acceptance Criteria

- `createColumn` on a non-customizable system table answers 400 `CUSTOMIZATION_TABLE_NOT_CUSTOMIZABLE`.
- A package carrying a new column on such a table shows it as INCOMPATIBLE and blocks the import.
- Customizable tables are unaffected.

## Regression Coverage

`services/api/src/modules/customization/package-comparison.spec.ts`: the INCOMPATIBLE case, plus the customizable control case. `createColumn` is covered by the e2e with the fix.

## Dependencies

None.

## Resolution

Fixed in TASK-0035 (branch `agent/custom-fields-followup`, commits 0a9e643c and 4e32ea28).

- `createColumn` refuses a new custom field on a system table whose `isCustomizable` is false, with 400 `CUSTOMIZATION_TABLE_NOT_CUSTOMIZABLE`.
- Package import marks such a column INCOMPATIBLE and blocks the import.
- Fifteen tables that no route can carry values for are no longer customizable (`UNSTORABLE_TABLE_KEYS` in the registry, each with its reason).
- Every table that remains customizable stores values through a bound route. `custom-fields.bindings.spec.ts` keeps that true.

## QA Retest

Retested 2026-09-27 in the e2e, whose closed-table case passes, and in `package-comparison.spec.ts`. The bindings spec found two more tables that could not store values (attendancePolicies and onboardingTasks); both are now closed.
