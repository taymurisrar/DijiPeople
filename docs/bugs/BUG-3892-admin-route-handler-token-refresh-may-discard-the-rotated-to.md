# BUG-3892 — Admin route-handler token refresh may discard the rotated tokens, leaving a revoked refresh token in the cookie

## Summary

**This is an unverified hypothesis from reading the code, not a confirmed
defect.** Admin route handlers call the API through `apiRequest` in
`apps/admin/lib/server-api.ts`. On a 401, that function refreshes with the
refresh token from the cookie. It appears to keep only the new access token, and
it writes neither rotated token back to the cookies. Refresh-token rotation is on
by default, so that refresh revokes the token the cookie still holds. The next
refresh, from `proxy.ts`, would then present a revoked predecessor. Inside the
grace window from [[BUG-3359]] that refresh succeeds. Outside it, the admin is
signed out.

## Expected Behavior

Whichever layer refreshes a session persists the rotated access and refresh
tokens, so the cookie never holds a revoked refresh token.

## Actual Behavior

Unconfirmed. The code reading suggests the rotated refresh token is discarded.
The end-to-end effect was not observed, because `apps/admin/proxy.ts` could not
be read during the triage.

## Reproduction

Not yet reproduced. A test that would prove or disprove it:

1. Sign in to Platform admin. Delete the `accessToken` cookie and keep the
   refresh cookie.
2. Trigger a route handler that calls `apiRequest`. It sends no bearer, gets
   401, and refreshes.
3. Record the refresh cookie before and after. Check whether the API revoked the
   old refresh token.
4. Wait past the rotation grace window, then trigger a navigation that refreshes
   through `proxy.ts`.
5. If the session ends with `SESSION_REVOKED` or "Refresh token is invalid or
   expired", the hypothesis holds.

## Evidence

- `apps/admin/lib/server-api.ts:53-69`: with no access cookie, the request is
  sent without a bearer. These are the `AUTH_TOKEN_MISSING` rows.
- `apps/admin/lib/server-api.ts:296-316`: `refreshAccessToken` returns only
  `accessToken`.
- `services/api/src/common/config/auth.config.ts:281-286`: rotation defaults to
  on.
- Production `ErrorLog`, read-only query on 2026-10-07: `SESSION_REVOKED` has
  3,360 occurrences overall, and "Refresh token is invalid or expired" has 11
  occurrences on 2026-10-07. This hypothesis could explain part of that volume.
  Polling after sign-out ([[BUG-3895]]) and the agent update check
  ([[BUG-3891]]) explain other parts of it.
- Whether `AUTH_REFRESH_ROTATION_ENABLED` is overridden in production was not
  checked.

## Root Cause

Not established. The candidate is two refresh paths, the route handler and the
proxy, where only one of them persists rotated tokens.

## Impact

If confirmed, platform admins are signed out unexpectedly, and some of the
monitoring 401 volume comes from this. No privilege is gained: the defect would
cause a sign-out, never access.

## Affected Areas

- `apps/admin/lib/server-api.ts`
- `apps/admin/proxy.ts`
- `services/api/src/modules/auth` (refresh rotation)

## Proposed Resolution

Run the test in Reproduction first. If it is confirmed, refresh in a single
place. Either persist the rotated tokens to cookies from route handlers, or move
all refreshing into `proxy.ts` and have route handlers return 401. This needs a
short plan because it changes session handling.

## Acceptance Criteria

- The reproduction test is written and its result recorded in this record.
- If confirmed: after a route-handler refresh, the refresh cookie holds the
  rotated token, and a refresh outside the grace window succeeds.
- If disproved: the record is closed as NOT_A_BUG, with the test as evidence.
