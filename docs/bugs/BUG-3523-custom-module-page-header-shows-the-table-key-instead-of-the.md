# BUG-3523 — Custom module page header shows the table key instead of the module name

## Summary

Every screen of a published custom module shows the module's table key, title
cased, in the tenant app's top bar — `QaLocalAsset` — instead of the name the
tenant gave it, `QA Local Assets`. The page body and the main menu are
unaffected; the shell header and the browser tab title both read the URL.

## Expected Behavior

The top bar names the module the way the tenant named it: the plural display
name on the list, the singular display name on a record.

## Actual Behavior

The top bar shows the last meaningful URL segment, title cased. For
`/custom-modules/qaLocalAsset` that is `QaLocalAsset`; the same text appears on
the create and record screens because `new`, `edit` and ids are skipped.

## Reproduction

1. In Settings → Customization, create a table with display name "QA Local Asset", add a field, publish.
2. Open the module from the main menu (`/custom-modules/qaLocalAsset`).
3. Read the top bar title: `QaLocalAsset`. The page body reads "Active QA Local Assets".
4. Click New: the top bar still reads `QaLocalAsset`.

## Evidence

- Local browser QA on a throwaway database, TASK-0031 WP-07: screenshots of the list and the create screen show the top bar `QaLocalAsset` above "Active QA Local Assets" and "New QA Local Asset".
- `apps/web/lib/tenant-branding-client.ts` `resolveRouteTitle`: with no explicit route title, it title-cases the last URL segment that is not `new`, `edit`, `designer` or a UUID.
- `apps/web/app/(authenticated)/_components/dashboard-topbar.tsx`: `pageTitle?.trim() || resolveRouteTitle(pathname)`; the custom module pages pass their title to `StandardModuleListPage`, not to the top bar.

## Root Cause

The shell derives a page title from the URL when a route has no explicit title.
System modules have readable path segments; a custom module's segment is its
table key, which is an identifier, not a name.

## Impact

Cosmetic. Every tenant user who opens a published custom module sees an
identifier in the header. No data or access impact. Reachable in production
once custom modules render there (ADR-0016).

## Affected Areas

- The top bar of `/custom-modules/<key>`, `/custom-modules/<key>/new`, `/custom-modules/<key>/<id>` and `/edit`.
- The document title from `app/(authenticated)/layout.tsx`, which uses the same resolver.

## Proposed Resolution

Let the custom module routes supply the top bar title from the published
definition, through whatever the shell already accepts as an explicit
`pageTitle`, rather than teaching the URL resolver about custom modules. No
ExecPlan needed.

## Acceptance Criteria

- The list screen of a published custom module shows its plural display name in the top bar.
- Its create and record screens show its singular display name.
- System module titles are unchanged.

## Regression Coverage

A unit test on the title the custom module routes hand the shell, failing while
the top bar falls back to the URL segment. No REG entry yet.
