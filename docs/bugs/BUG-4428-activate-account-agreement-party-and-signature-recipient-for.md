# BUG-4428 — Activate-account, agreement party and signature-recipient forms submit input the API will refuse (unmet password policy, malformed email)

## Summary

Three forms submit input the API is certain to refuse, so each mistake round-trips as a 400 that monitoring records: activate-account sends a password that fails the published policy; the agreement party form and signature-recipient dialog send a malformed email (`email must be an email`, `recipients.0.email must be an email`).

## Expected Behavior

The form blocks the submission and says which rule is unmet, inline, where the value was typed.

## Actual Behavior

The activate form's checklist was advisory only; the party/recipient forms only checked non-empty.

## Reproduction

1. Open an activation link, type `abc`, submit -> request sent, 400.
2. Agreement party email `foo` -> Save enabled -> 400.

## Evidence

Production rows: `/api/auth/activate-account` 'Password must be at least 12 characters long, include…' (x5); `/api/contracts/<id>/parties/<id>` 'email must be an email'; `/api/contracts/<id>/signature-requests` 'recipients.0.email must be an email'.

## Root Cause

No client-side check mirrored the server rule at submit time.

## Impact

Growth-plan demo path and production monitoring signal quality.

## Affected Areas

[auth, contracts, apps/web, apps/admin]

## Proposed Resolution

web `activate-account-form.tsx` blocks on unmet policy rules; admin `lib/email-format.ts` + `DialogField` inline error + disabled Save/Send. Specs: `email-format.spec.ts`.
