# BUG-3901 — The generic exception filter maps any connection or timeout message to DATABASE_TIMEOUT

## Summary

The exception filter's generic fallback assigns `DATABASE_TIMEOUT` to any
non-HTTP error whose message mentions "pool", "connection", "connect" or
"database" together with "timeout". On 2026-08-11 an SMTP connection timeout was
labelled a database timeout this way. The email path has since been fixed at its
source, but the filter still mislabels any other integration timeout.

## Expected Behavior

`DATABASE_TIMEOUT` is assigned only to errors from the database driver or Prisma.

## Actual Behavior

The classification matches on message text, so any library's connection
timeout qualifies.

## Reproduction

1. Throw `new Error('connection timed out')` from any service code path.
2. The response and the error-log row carry `DATABASE_TIMEOUT`.

## Evidence

- `services/api/src/common/filters/http-exception.filter.ts:288-291`: the
  `/pool|connection|connect|database/i` test, then `/timeout|timed out/i`.
- Production `ErrorLog`, read-only query on 2026-10-07: 7 occurrences on
  2026-08-11, on one tenant. All were platform email test-connection SMTP
  timeouts. No recurrence since then.

## Root Cause

The classification uses a message regex instead of the error's type or origin.

## Impact

Integration timeouts are misattributed to the database, which misdirects
incident response. The volume is low.

## Affected Areas

- `services/api/src/common/filters/http-exception.filter.ts`

## Proposed Resolution

Restrict the fallback to Prisma or `pg` error classes and codes. Classify other
timeouts as `INTEGRATION_TIMEOUT` or `SYSTEM_UNEXPECTED_ERROR`.

## Acceptance Criteria

- A non-database error whose message contains "connection timed out" is not
  classified `DATABASE_TIMEOUT`.
- A Prisma pool timeout still is.
