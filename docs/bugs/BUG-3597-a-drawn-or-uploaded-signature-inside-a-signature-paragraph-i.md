# BUG-3597 — A drawn or uploaded signature inside a signature paragraph is dropped from the signed PDF and DOCX

## Summary

When a signer draws or uploads a signature, the executed agreement's official
signed copy (PDF and DOCX) printed the signer's name, method, hash and signing
time — but not the signature mark itself. The image never reached the document.

## Expected Behavior

The signed PDF and DOCX show a drawn or uploaded signature as an image on the
signer's signature line, next to the signer's name and signing time.

## Actual Behavior

No image object appears in the signed PDF (`/Subtype /Image` absent) and no
`word/media/` entry exists in the DOCX. Only the text metadata is printed.

## Reproduction

1. Create an agreement from any system template (every one uses
   `<p>For X: {{signature.counterparty.name}} — {{signature.counterparty.date}}</p>`).
2. Approve it, send it for signature, and sign with the **Draw** method.
3. Download the stored `SIGNED_COPY` PDF (or its DOCX): no signature image.

## Evidence

Re-verification run on the throwaway stack (`dijipeople_pah_test`), 2026-09-25:
signed copies `CON-20260925-874F1CFC-v2.pdf` (3,590 bytes) and
`CON-20260925-EA2DC7A1-v2.pdf` (5,379 bytes) contained zero image objects,
although their decompressed text carried "Counterparty Signer DRAWN signature ·
Verified · SHA-256 …". After the fix the same flow produced a signed copy with
the drawn stroke rendered beneath the counterparty's line (read visually).

## Root Cause

`extractAgreementDocumentStructure` in
`services/api/src/modules/contracts/contracts.service.ts` turns every `<p>` into
a single text block via `nodeText`, which discards element children. The
evidence renderer places the `<img>` for a drawn signature inline, in place of
the `{{signature.*.name}}` token — which sits inside a `<p>` in every system
template. The image existed only at the top level in the existing BUG-3554
test, so the paragraph case was never exercised.

## Impact

Every executed agreement signed with a drawn or uploaded signature. On
`develop` the customer-service and service-order templates already carried
inline signature tokens, so this is reachable in production; TASK-0032's new
signature blocks extended it to every system template.

## Affected Areas

Signed-copy generation (`generateDocument` immutable path), PDF and DOCX
renderers (`createPdf`, `createDocx`), all agreement types.

## Proposed Resolution

Split a paragraph that contains images into text-image-text blocks rather than
flattening it.

## Acceptance Criteria

- A paragraph holding an `<img>` renders the text before it, the image, and the
  text after it, in order.
- The signed PDF contains an image object and the DOCX a `word/media/` entry
  for a drawn signature.

## Regression Coverage

REG-627 — `services/api/src/modules/contracts/contracts.domain.spec.ts`
("keeps a signature image that sits inside a paragraph …"), which fails against
the pre-fix service.

## Dependencies

None.

## Related Items

[[BUG-3554]], [[TASK-0032]], [[BUG-3598]]

## Resolution

Fixed on `agent/partner-agreements-admin-hardening` (TASK-0032): a new
`splitParagraphAroundImages` helper in `contracts.service.ts`, used by
`extractAgreementDocumentStructure` for any paragraph containing an image. Both
renderers consume that structure, so PDF and DOCX are fixed together.

## QA Retest

Re-verification script against the throwaway stack: 38/38 checks passed,
including "signed copy draws the drawn signature image" for a partner agreement
(drawn only) and a customer agreement (typed platform + drawn customer).
Scenario QA-CONTRACT-012.
