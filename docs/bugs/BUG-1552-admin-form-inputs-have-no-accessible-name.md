# BUG-1552 — Admin form inputs have no accessible name

> **Architect triage, 2026-08-27 — `DUPLICATE`.** Duplicate of [[BUG-1423]]. Same defect: runtime form controls carry no accessible name. BUG-1423 was filed first, rates it axe-core critical and covers four screens. Same missed retrieval as BUG-1542.


## Summary

Form controls across the admin console have no accessible name. Labels are
rendered as `div` elements rather than `<label>`, so nothing associates the text
with the input. On the New Lead form, five of five inputs were unnamed. The
console is not usable with a screen reader, and it is only partly drivable by
accessibility-based automation.

## Expected Behavior

Every form control has an accessible name, provided by an associated `<label>`
or an explicit `aria-label`, so assistive technology and role-and-name based
automation can both identify it.

## Actual Behavior

Label text is rendered in `div` elements with no association to the control.
Controls expose no accessible name.

## Reproduction

1. Sign in to `admin.dijipeople.com` as a platform owner.
2. Open Leads and start a new lead.
3. Take an accessibility snapshot of the form, or inspect the label markup.
4. Observe that the inputs carry no accessible name.

Reproduces on Leads, Customers and Onboarding.

## Evidence

Observed on production, 2026-08-26. On the New Lead form, five of five inputs
had no accessible name. The same pattern was present on the Customers and
Onboarding forms.

Related context: `apps/admin` contains zero `data-testid` attributes, so roles
and accessible names are the only semantic handle available on these screens.
With no accessible names either, parts of the console cannot be addressed
semantically at all.

## Root Cause

Not established. The pattern is consistent enough across screens to suggest a
shared form component renders labels as `div`, rather than each screen doing so
independently — but the specific component has not been identified.

## Impact

Screen reader users cannot fill these forms: an unnamed input is an input whose
purpose is unannounced. This is an accessibility defect in the operator console
rather than in a customer-facing surface, which limits who is affected but does
not make it acceptable.

It also degrades agent-driven and automated testing of admin, since the same
missing name that fails a screen reader fails a role-and-name locator. That is
the direct connection recorded in `docs/development/browser-control.md`.

## Affected Areas

- `apps/admin` — the shared runtime form and its label rendering
- The Leads, Customers and Onboarding forms specifically
- `services/api/src/modules/customization` — form metadata, as the label source

## Proposed Resolution

Fix the shared form component so a field's label renders as a `<label>`
associated with its control, rather than as a `div`. Doing it at the shared
component fixes every metadata-driven form at once, which is the whole reason
the runtime exists.

Audit for controls that are not metadata-driven separately; they will not be
covered by the same change.

## Acceptance Criteria

- Every input on the Leads, Customers and Onboarding forms exposes an accessible
  name matching its visible label.
- An accessibility snapshot of each form shows named controls throughout.
- Clicking a label focuses its control.

## Regression Coverage

None yet. Needs a test asserting that every control rendered by the shared
runtime form has an accessible name. Requires a `REG-nnn` entry once written.
