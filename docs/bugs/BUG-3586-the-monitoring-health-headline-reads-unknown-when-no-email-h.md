# BUG-3586 — The monitoring health headline reads Unknown when no email has been sent

## Summary

On a fresh or quiet environment where no email has ever been sent, the
platform health overview's email component read "Unknown" — the same word the
service correctly uses for a genuinely inconclusive probe (a timeout) — which
reads to an operator as "something is wrong with monitoring" rather than "no
email has been sent yet", an entirely normal and expected state on a new
tenant or a throwaway environment.

## Expected Behavior

The email health tile should distinguish "no email has ever been sent, which
is a normal and expected state" from "we tried to check and the probe was
inconclusive". Only the latter should read "Unknown".

## Actual Behavior

`PlatformHealthService`'s email component reported `'UNKNOWN'` whenever there
was no delivery-log history to compute a success rate from, collapsing "never
tried" into the same status as "tried and could not tell" — both of which the
service otherwise takes care to keep distinct for every other component (see
ITEM-0198 / REG-580's "never fabricate OK" rule).

## Reproduction

1. Load the platform health overview on an environment (or a fresh tenant)
   with no delivery-log rows.
2. Observe the email component / headline reads "Unknown".

**Live reproduction, throwaway stack, 2026-09-25** (TASK-0032 WP-09 live QA):
the health headline read "Unknown" purely because the throwaway tenant had
never sent an email, not because of any actual monitoring failure.

## Evidence

- `services/api/src/modules/platform-monitoring/platform-health.service.ts` —
  the email component's status derivation had no distinct branch for "zero
  delivery-log rows exist" versus "the probe could not resolve within its time
  budget".

## Root Cause

The email component's health derivation treated an empty result set (nothing
to sample) identically to a genuinely inconclusive probe, reusing the same
status label for two different meanings.

## Impact

Cosmetic but actively misleading on the environment where it is most visible —
a fresh tenant or a throwaway stack — reading as a monitoring fault when
nothing has actually gone wrong.

## Affected Areas

- `services/api/src/modules/platform-monitoring/platform-health.service.ts`
- `apps/admin` monitoring overview (renders the headline)

## Proposed Resolution

Add an explicit "nothing has ever been sent" branch to the email component
that reports a distinct, honest status rather than reusing `'UNKNOWN'`. No
ExecPlan needed — a service-level status derivation fix, no schema change.

## Acceptance Criteria

- An environment with zero delivery-log rows reports the email component's
  dedicated "nothing sent yet" status, not `'UNKNOWN'`.
- A component that genuinely could not be probed (timeout) still reports
  `'UNKNOWN'`.
