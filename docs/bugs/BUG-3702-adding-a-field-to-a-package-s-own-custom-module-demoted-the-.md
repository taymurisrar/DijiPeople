# BUG-3702 — Adding a field to a package's own custom module demoted the module to a reference

## Summary

Adding the first field to a custom module rewrote the owning package's module row from `create` to `reference`. The package stopped recording that it owns the module, so an export shipped the field without the module it lives in, and the import refused it as a missing dependency.

## Expected Behavior

Adding a field never changes how the package holds its module.

## Actual Behavior

Before the fix: the module row became `reference`.

## Reproduction

1. In a package, create a module.
2. Add a field to it.
3. The package's `table` component row now has layerAction `reference`.

## Evidence

Found by the TASK-0033 DB-backed round trip: the UAT import reported "module misAsset is referenced but does not exist here".

## Root Cause

`ensurePackageModuleMembership` upserted the module row with `layerAction: 'reference'`, overwriting the existing `create`.

## Impact

Every package whose own module received a field could not be exported and imported. Existing workspaces carry demoted rows.

## Affected Areas

customization: createColumn and every path through ensurePackageModuleMembership; package export.

## Proposed Resolution

Done: membership leaves an existing row alone; the portable reader recovers already-demoted modules (the oldest row wins when no package holds `create`).

## Acceptance Criteria

After adding a field, the module row is still `create`; an existing demoted module exports as created by its original package.
