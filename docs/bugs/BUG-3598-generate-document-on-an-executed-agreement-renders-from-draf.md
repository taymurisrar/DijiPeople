# BUG-3598 — Generate document on an executed agreement renders from draft values, not the signature evidence

## Summary

The admin "Generate document" action is offered on agreements in every status.
On an executed agreement it produced a copy rendered from the agreement's
placeholder values rather than from its signature evidence, so the copy an
operator downloaded disagreed with the signed original.

## Expected Behavior

Any copy of a signed version is rendered from the frozen version and its
signature evidence — signer names, signature images, real signing times and
the signature appendix — exactly as the stored signed copy is.

## Actual Behavior

A typed signer's name printed, a drawn signer's line was blank ("For X: — 25
September 2026, 14:13 UTC"), no signature image appeared and there was no
signature appendix or audit certificate.

## Reproduction

1. Execute an agreement with one drawn signature.
2. In admin, open the agreement and choose **Generate document**
   (`POST /api/contracts/:id/generate/pdf`).
3. The downloaded PDF's signature line has a date but no name and no image.

## Evidence

Re-verification on the throwaway stack, 2026-09-25: the DOCX generated for
executed agreement `CON-20260925-874F1CFC` read "For ZZZ Active B …: — 25
September 2026, 14:13 UTC", while the stored signed copy of the same version
named "Counterparty Signer DRAWN signature".

## Root Cause

`generateDocument` rendered from evidence only when called with
`immutable = true`, which only the completion hook passes. The admin route
always passes `false`, so it took the draft-preview path, which resolves
`signature.*` from stored placeholder values (a typed name, or a data URL that
the display render discards).

## Impact

Operators downloading an executed agreement from admin received a copy that
misrepresents who signed and how. The stored official copy was unaffected.

## Affected Areas

`POST /contracts/:id/generate/:format`; admin record action
`generate-document` (`apps/admin/lib/runtime/runtime-record-action-handler.ts`).

## Proposed Resolution

Render from the evidence whenever the latest version has a completed signature
request; keep only the completion copy immutable.

## Acceptance Criteria

- Generating a document for a signed version prints the signers from the
  evidence, the signature appendix, and no "Pending".
- That copy is stored as an ordinary `GENERATED_PDF`, not as `SIGNED_COPY`.

## Regression Coverage

REG-628 — `services/api/src/modules/contracts/contracts.agreement-rendering.spec.ts`
("an operator-generated copy of a signed version also renders from the
evidence"), which fails against the pre-fix service.

## Dependencies

None.

## Resolution

Fixed on `agent/partner-agreements-admin-hardening` (TASK-0032):
`generateDocument` computes whether the latest version has a COMPLETED
signature request and, if so, renders from the evidence; `kind` and
`isImmutable` still follow the `immutable` flag.

## QA Retest

Live: generating a PDF for both executed re-verification agreements after the
fix returned the evidence-rendered copy with the signature image and the
appendix. Scenario QA-CONTRACT-012.
