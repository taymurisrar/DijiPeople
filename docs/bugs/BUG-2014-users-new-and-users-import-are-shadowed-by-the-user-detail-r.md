# BUG-2014 — Users new and Users import fall through to the user detail route and report a permissions refusal

## Summary

`apps/web/app/(authenticated)/users/` has no `new/page.tsx` and no
`import/page.tsx`. Both URLs are matched by the sibling `users/[userId]` detail
route with the literal segment as the id, so the page fetches a user whose id is
`"new"` or `"import"`. The detail route handles the resulting 404 without
crashing — this is a dead-end, not a crash — but the state it renders leads with
**"ACCESS DENIED — You cannot view this user record"**, telling an administrator
they lack a permission they hold, for a record that never existed. Both links are
generated by the users command bar and the `/users` empty state, so they are
product-authored dead ends, and both are reachable by direct URL today.

## Expected Behavior

**New** on the users command bar creates a user. **Data > Import** imports users.
If neither capability exists, neither control is rendered — and a hand-typed
`/users/new` produces a not-found state that says the record was not found, not
that access was denied.

## Actual Behavior

Both routes render the detail page's error state:

```
ACCESS DENIED
You cannot view this user record.
404: User was not found for this tenant.
```

`/users/new` carries the page title "Users | DijiPeople"; `/users/import` carries
the page title "Import | DijiPeople" while rendering the same access-denied body,
so even the tab title disagrees with the content.

## Reproduction

Target: `https://dijipeople-demo.ws.dijipeople.com`, tenant `DijiPeople Demo`,
production API commit `949f461c`, observed 2026-08-29, signed in as the tenant
owner.

1. Sign in to the tenant workspace.
2. Navigate directly to `/users/new`. The page renders the ACCESS DENIED block
   quoted above, titled "Users | DijiPeople".
3. Navigate directly to `/users/import`. The same ACCESS DENIED block renders,
   titled "Import | DijiPeople".

Direct URLs are used because the two controls that link to these routes are on
`/users`, which does not render at all (BUG-2003). They are unreachable by
clicking, not unreachable by request — and they become reachable by clicking the
moment BUG-2003 is fixed.

## Evidence

Observed live, as quoted above, on production as the tenant owner.

Code, at `eb457d9d`:

- `apps/web/app/(authenticated)/users/` contains `page.tsx`, `types.ts`,
  `_components/`, and `[userId]/page.tsx`. There is no `new/` and no `import/`
  directory, so both paths are matched by `users/[userId]`.
- The two links are generated:
  - `users-command-bar.tsx:~46` — the **New** action.
  - `users-command-bar.tsx:~118` — **Data > Import**.
  - `users/page.tsx:~170` — the empty state also links to `/users/new`.
- The route sweep that found them enumerated every `page.tsx` under
  `(authenticated)`, built the static/dynamic route table, extracted every
  literal internal path string in `apps/web/app` and `apps/web/lib`, and kept
  only paths with no static page sitting under a directory that has both a page
  and a `[param]` child. After discarding backend API paths passed to
  `apiRequestJson` and the `/settings/*` paths that `next.config.ts` redirects,
  three survivors remained: `/approvals/new` (BUG-2004), `/users/new` and
  `/users/import`.

**The message names the wrong cause.** A 404 — "User was not found for this
tenant", printed in the same block — is presented under the heading ACCESS
DENIED. That is the misclassification described in BUG-2013 seen from the other
side: where BUG-2013 shows the boundary cannot classify a server-component throw
at all, this shows it classifying a genuine 404 as a permissions refusal.

**Not fixed in `develop`.** No commit in `949f461c..origin/develop` touches
`apps/web/app/(authenticated)/users`.

## Root Cause

**Established.** Two links are emitted to routes that have no page, so Next
matches them against the sibling `users/[userId]` dynamic route with the literal
path segment as the record id. The separate question of why the resulting 404
renders as "ACCESS DENIED" belongs to BUG-2013.

## Impact

An administrator is offered **New** and **Import** on the users screen, takes
either, and is told they do not have permission to do something they are fully
entitled to do. That is worse than a plain dead link: it sends the customer to
support with a permissions question that has no permissions answer, and it will
send whoever investigates into the RBAC configuration.

Nothing is created, changed or exposed, and the pages recover with the back
button. Reachable in production today by URL, and reachable by clicking as soon
as BUG-2003 is fixed.

Rated MEDIUM: missing UI state plus a misleading error, on a screen that is not
currently reachable by clicking. It would be HIGH if it blocked a journey — it
does not, because there is no working user-create journey here to block.

## Affected Areas

`apps/web/app/(authenticated)/users/_components/users-command-bar.tsx` (the New
and Data > Import actions); `apps/web/app/(authenticated)/users/page.tsx` (the
empty-state link); `apps/web/app/(authenticated)/users/[userId]/page.tsx` (the
error state it renders for a nonexistent id).

## Proposed Resolution

Decide with ITEM-0107 first: if `/users` is redirected to
`/settings/security-access/identities/users` and the bespoke tree deleted, both
links disappear with it and this record closes for free. That is the recommended
path.

If the tree survives, then either build `new/page.tsx` and `import/page.tsx`, or
remove the two command-bar actions and the empty-state link. In both cases, make
`users/[userId]` render a not-found state for a nonexistent id rather than an
access-denied one.

## Acceptance Criteria

- No control in the users screen links to a route that has no page.
- `/users/new` and `/users/import` either work or render a not-found state whose
  heading says the record was not found.
- No screen in the tenant app presents a 404 under an "ACCESS DENIED" heading.
- The route-integrity test described in BUG-2004 — no literal `href` or
  `router.push` string in `apps/web` resolves to a path matched only by a sibling
  `[param]` route — covers these two paths.

## Resolution

Fixed, without pre-empting ITEM-0107 and without building a second user-create
screen.

**The premise was verified before anything was changed.** All three links were
still there at this branch's base: `users-command-bar.tsx:52` (New),
`:125` (Data > Import) and `page.tsx:172` (the empty state), none of which
resolves to a page, and `users/[userId]/page.tsx:117-129` still answered both a
403 and a 404 with the same `AccessDeniedState`.

**The two links now point somewhere real, or nowhere at all.**

There is exactly one user-create screen in this product and it belongs to the
settings runtime: `settings/[category]/[settingGroup]/[item]/new/page.tsx`
resolves `/settings/security-access/identities/users/new`, and `next.config.ts`
redirects the older `/settings/security-access/users/*` spelling onto it. So
`New` points there, through a single named constant at
`users/_lib/user-routes.ts` so the two call sites cannot drift
(`users-command-bar.tsx:52`, `users/page.tsx:170`). Nothing about permissions
changed: the API decides who may create a user, as it did before.

`Data > Import` was **removed**, along with the `canImport` prop that gated it
and the now-unused `users.import` permission read at `page.tsx:53`. There is no
users import screen anywhere in this app, so there was nowhere honest to point
it. Pointing it at another route that does not exist would have moved the defect
rather than fixed it.

Building `new/page.tsx` and `import/page.tsx` under `/users` was the other
option the record offered and was deliberately not taken: ITEM-0107 may redirect
this whole tree to the settings screen, and two more bespoke pages is the wrong
thing to leave behind if it does.

**A 404 is no longer reported as a permissions refusal.**
`users/[userId]/page.tsx:124-146` splits the two cases that used to share a
panel: a 404 renders the new `RecordNotFoundState` ("This user record was not
found"), and a 403 keeps `AccessDeniedState`. The new component
(`_components/record-not-found-state.tsx`) is built on the shared `EmptyState`
and `Button` rather than a hand-rolled panel.

**The empty state is no longer hand-rolled.** `users/page.tsx:163-174` was a
bespoke `<section>` with its own border, heading and link. It is the shared
`EmptyState` now, with the create action pointing at the real route.

Against the acceptance criteria:

- **1, no control links to a route that has no page** - met. One link
  retargeted, one removed, both verified by the test below.
- **2, `/users/new` and `/users/import` work or say the record was not found** -
  met. Neither is linked any more, and typing either still lands on
  `users/[userId]`, which now answers "This user record was not found" rather
  than ACCESS DENIED.
- **3, no screen presents a 404 under an ACCESS DENIED heading** - met on this
  screen, and met in the shared boundary by BUG-2013, which now reads an
  explicit HTTP status before any message heuristic.
- **4, the route-integrity test covers these paths** - met, in the same suite
  BUG-2004 asked for: the second block of
  `apps/web/lib/routing/route-integrity.spec.ts` extracts every literal internal
  link in `apps/web/app` - `href`-ish properties, `router.push`/`redirect`
  calls, and named route constants - and asserts each resolves to a page without
  a `[param]` eating its last segment. 50 links are checked.

Mutation-tested rather than assumed: pointing `USER_CREATE_ROUTE` back at
`/users/new` fails the suite with
`"reason": "matched by (authenticated)/users/[userId]"`. Restored afterwards.

One honest limit of that test: it only sees **literal** strings. A link built
from a template literal is not checked, deliberately - a path built around a
record id is not the mistake this looks for - so it catches this defect and
every copy of its shape, not every possible dead link.

## QA Retest

Retested by the new unit suite, not in a browser: 26 assertions in
`apps/web/lib/routing/route-integrity.spec.ts` pass, and the link assertion
fails against the defect.

**Not retested live**, and two things are therefore open:

- Production runs `main` at `949f461c` and this work is on a task branch, so
  `/users/new` and `/users/import` still show ACCESS DENIED on the demo tenant.
- **The settings user-create screen has not been walked end to end here.** The
  route resolves and the settings runtime owns a `users` adapter
  (`settings-adapter-registry.ts:5940-6010`), so New now leads to a real page -
  but that a user can actually be created through it was not observed in this
  task, and it should be on the next release walkthrough. If it turns out that
  screen cannot create a user, this record's link is still better than a dead
  one, but ITEM-0107 gains a harder question.
