# BUG-3500 — Every seeded email template is active with placeholder body text

## Summary

The system email templates a tenant sees are all ACTIVE. Most of them have a
body that literally reads "This is a system placeholder email template.
Configure tenant-specific content before production sending." That is what
employees would receive for events such as leave approval the moment real
delivery is switched on.

Templates are also ACTIVE for events nothing emits (`AUTH_OTP`,
`PAYROLL_PROCESSED`). The placeholders are regenerated by the configuration seed
on every run.

## Expected Behavior

Every system email template that ships ACTIVE carries real, professional default
copy for its event: a meaningful subject, HTML and text bodies, and the
variables the event actually supplies. Owner decision 2026-09-13: the Architect
drafts that copy per event, and it ships ACTIVE together with the retirement of
sink providers (ADR-0015, [[BUG-3501]]).

## Actual Behavior

- `/settings/notifications/templates` lists 11 email templates, all ACTIVE.
- Opening "Leave approved email" shows the placeholder text in both the HTML and Text bodies:
  - Body: "This is a system placeholder email template. Configure tenant-specific content before production sending."
  - Description: "System placeholder template for Leave approved."
- ACTIVE templates also exist for `AUTH_OTP` and `PAYROLL_PROCESSED`, events with no emitter.

## Reproduction

1. Sign in to `https://dijipeople-demo.ws.dijipeople.com` (demo tenant) as the workspace owner.
2. Open Settings → Notifications → Email Templates (`/settings/notifications/templates`).
3. Observe that all 11 templates are ACTIVE.
4. Open "Leave approved email" and read the HTML Template, Text Template and Description.
5. Observe the `AUTH_OTP` and `PAYROLL_PROCESSED` templates in the list, both ACTIVE.

## Evidence

Browser QA on the live demo tenant at `df0f84f1`. Code references are at the
worktree HEAD.

**The placeholder is generated in the notification catalog.**
`services/api/src/modules/notifications/notification-events.catalog.ts:554-557`
builds `SYSTEM_EMAIL_TEMPLATE_PLACEHOLDERS` from every catalog event that has a
`systemTemplateKey`. `createSystemTemplateSeed` writes real copy for only three
events: `AUTH_ACCOUNT_ACTIVATION`, `AUTH_PASSWORD_RESET` and
`SUPPORT_CASE_UPDATE` (lines 559-738). Every other event falls through to the
generic return at lines 740-759, which sets:
- `description` "System placeholder template for …" (line 745)
- the placeholder HTML and text bodies (lines 747-750)
- `status: EmailTemplateStatus.ACTIVE` (line 756)

**The seed overwrites existing rows on every run.**
`services/api/prisma/seed-config.ts:876-912` upserts each of those seeds. Its
`update` branch (lines 900-911) rewrites `htmlTemplate`, `textTemplate`,
`description` and `status` on existing rows. Re-running the seed therefore
restores the placeholder and ACTIVE status on every system template.

**The seed is part of the release script.**
`services/api/package.json:34` defines `release` as migrate → `seed:config` →
…, and `render.yaml:38` declares `preDeployCommand: npm --workspace api run release`.
The live Render service configuration has previously been found to diverge from
`render.yaml`, so this record does not assert that every production deploy ran
the seed. The declared intent is that it does.

## Root Cause

The generic fallback in `createSystemTemplateSeed`
(`notification-events.catalog.ts:740-759`) seeds placeholder copy with
`status: ACTIVE` for every event that has a `systemTemplateKey` but no
hand-written template. `seed-config.ts:876-912` applies that catalog with an
upsert whose `update` branch re-imposes the placeholder bodies and ACTIVE status
on every run. The catalog is the source of truth, so real copy has to be written
there. Editing the rows would be reverted by the next seed.

## Impact

- **Go-live blocker.** When tenant email is delivered for real, employees of every tenant receive placeholder text for leave, approval and similar events.
- **Current state:** the demo tenant's only provider is CONSOLE ([[BUG-3501]]), so these emails are not reaching inboxes today. That is exactly why the defect has been invisible.
- **Why it cannot wait:** the owner's decision to retire CONSOLE providers makes real delivery imminent, so the two must ship together.
- ACTIVE templates for events that are never emitted mislead administrators about what the product sends.

## Affected Areas

- API `notifications` module: the event catalog's system template seeds.
- `services/api/prisma/seed-config.ts` (system email template seeding).
- Tenant settings: Notifications → Email Templates list and editor.
- Every tenant's outbound notification email.

## Proposed Resolution

- Write real default copy in `notification-events.catalog.ts` for every event with a `systemTemplateKey`, using only the variables each event's emitter actually supplies. Take `SUPPORT_CASE_UPDATE` (lines 700-738) as the pattern.
- Remove the placeholder fallback, so an event without authored copy cannot silently seed a placeholder.
- Decide per event whether one with no emitter keeps a template at all. Align with the catalog hygiene work rather than seeding ACTIVE templates for dead events.
- Ship together with [[BUG-3501]]'s provider change, per ADR-0015.

This is copy authoring plus a catalog change, with no schema change; no ExecPlan
needed.

## Acceptance Criteria

- No system email template, in the catalog or on a freshly seeded database, contains the text "system placeholder".
- Every ACTIVE system template has a subject, HTML body and text body specific to its event.
- Every `{{variable}}` used in a template is supplied by that event's emitter.
- Running `seed:config` twice leaves the authored copy in place.
- No ACTIVE system template exists for an event the catalog marks unavailable or that has no emitter.
- On the demo tenant, "Leave approved email" shows the authored copy after deploy.

## Regression Coverage

An API unit test over `SYSTEM_EMAIL_TEMPLATE_PLACEHOLDERS` must assert that:
- no seed body or description contains "placeholder";
- every ACTIVE seed's template variables are a subset of its declared `availableVariables`.

The test fails today. REG entry to be added when the test exists.
