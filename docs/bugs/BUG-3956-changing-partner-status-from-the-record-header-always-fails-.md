# BUG-3956 — Changing Partner status from the record header always fails and would bypass the partner state machine

## Summary

Partner status was shown as writable in the record header and the process bar, but every change failed with "Review the highlighted fields and submit again.". Had it succeeded, it would have bypassed `partnerTransition()`.

The lifecycle also had other gaps:
- Create accepted any status.
- Update allowed jumps between non-ACTIVE statuses.
- Inquiry qualification, inquiry rejection and contract signing could demote a live partner.
- The Activate button was hidden in INFORMATION_APPROVED, which is exactly where activation succeeds.

## Expected Behavior

Status changes only through lifecycle actions, and the server enforces them. The record shows a status phase with the exact status as sub-status, and explains why status is read-only.

## Actual Behavior

`platform-runtime.service.ts:1097-1110` spread the whole GET record into `UpdatePartnerDto`, which rejects unknown properties (`forbidNonWhitelisted`), so the request returned 400. The admin registry marked partners as header-status writable.

## Reproduction

1. On a partner record, change Status in the header.
2. The request returns 400 with the generic message.

## Evidence

- Registry `:288-292` and `:4271-4288`.
- `partners.service.ts:463`: create spread `dto.status`.
- `contracts.service.ts:4306-4316`: contract signing set AGREEMENT_EXECUTED unconditionally.

## Root Cause

No single lifecycle definition existed. The admin, the generic runtime status path and four services each decided transitions on their own.

## Impact

Operators could not change status and had no explanation. Data could reach invalid states: a partner could be created as ACTIVE, or a live partner demoted.

## Affected Areas

The partner record header and process bar, partner create and update, inquiry qualify and reject, and contract signing.

## Proposed Resolution

ADR-0026: add one shared lifecycle module in `packages/config` with phases, labels and the from-states for each action, and enforce it on the server.

## Acceptance Criteria

- Header status changes for partners are refused with `PARTNER_STATUS_ACTION_REQUIRED`.
- Create starts at DRAFT.
- Update refuses status changes.
- Qualify and reject refuse live partners with `PARTNER_ALREADY_LIVE`.
- Contract signing never demotes a live partner.
- Activate is visible exactly where the server accepts it.
- The phase mapping covers all 24 statuses, and a test reads the Prisma enum.

## Resolution

- Shared `partner-lifecycle.js` covers phases, account-status explanations and action from-states.
- The server uses the shared table and has 3 new catalog codes.
- The account status gaps are fixed: reactivate and portal acceptance now respect the current state.
- Every status change now records its actor on the timeline and in the audit log.
- In the admin, status is read-only, the process bar shows phases, `deactivate-partner` is declared, and Reject, Suspend and Deactivate ask for a reason.
