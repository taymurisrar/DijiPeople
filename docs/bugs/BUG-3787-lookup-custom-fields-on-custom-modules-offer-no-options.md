# BUG-3787 — Lookup custom fields on custom modules offer no options

## Summary

A custom module can have a lookup field that points at another table, for example a "Primary contact" on a custom Assets module that points at Employees. On the record form, that field's dropdown never offers any record to choose.

## Expected Behavior

A lookup field lists records of its target table that the user may read, searchable by name. The target can be a custom module or a system table.

## Actual Behavior

The dropdown is empty and cannot be searched.

## Reproduction

1. Create a custom module with a lookup field whose target is `employees`, then publish.
2. Open New on that module.
3. The lookup field has no options.

## Evidence

- `apps/web/lib/runtime/custom-modules/custom-module-runtime.ts` sets `lookupTargetEntityLogicalName` from `lookupTargetTableKey` for lookup fields, but never sets `spec.lookupApiPaths`.
- `apps/web/lib/runtime/modules/standard-module-data.adapter.ts` only adds `getLookupOptions` when `spec.lookupApiPaths` is set.
- `runtime-metadata-form-renderer.tsx` guards every lookup on `dataAdapter?.getLookupOptions`, and does nothing when it is absent.

## Root Cause

Nothing on the web resolves a lookup's options from its target table key; only hard-coded per-module paths exist.

## Impact

Every custom-module lookup field is unusable, in production, for every tenant that uses one.

## Affected Areas

Custom module record forms, and custom lookup fields on system modules (EXECPLAN-0054).

## Proposed Resolution

A generic lookup-options resolver keyed by target table key. Custom modules use `/api/data/<key>`; system tables use their own list endpoint. Part of EXECPLAN-0054 WP-06.

## Acceptance Criteria

- A custom-module lookup field lists target records and searches them.
- The same resolver serves custom lookup fields on system modules.
