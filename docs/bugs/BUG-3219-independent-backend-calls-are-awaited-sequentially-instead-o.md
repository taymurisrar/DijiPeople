# BUG-3219 — Independent backend calls are awaited sequentially instead of in parallel in at least two shared code paths

## Summary

Independent backend calls are awaited sequentially instead of in parallel in at least two shared code paths

Identified by the 2026-09-10 full technical audit as FE-04 (confidence: FE-04=CONFIRMED).

## Expected Behavior

Independent requests should always be issued together via `Promise.all`, as is already done correctly elsewhere in the same files (e.g. `apps/web/app/(authenticated)/reports/page.tsx:35-37`, `apps/web/app/(authenticated)/employees/page.tsx:35-39`).

## Actual Behavior

Both examples pay one full extra network round trip (each also paying the ~26-DB-round-trip auth tax per ORCH-04) that a `Promise.all` would eliminate.

## Reproduction

This is a code-review finding from a static technical audit, not a QA-run runtime reproduction. To confirm: open the file(s) cited in Evidence and trace the call path described in Actual Behavior.

## Evidence

**FE-04** (`apps/web/app/(authenticated)/attendance/page.tsx`, `apps/admin/app/_components/runtime/runtime-module-page.tsx`):

`apps/web/app/(authenticated)/attendance/page.tsx:30-44`:
  ```
  const [sessionUser, resolvedSettings, attendanceContext] = await Promise.all([
    getSessionUser(),
    apiRequestJson<TenantResolvedSettingsResponse>("/tenant-settings/resolved").catch(() => null),
    apiRequestJson<AttendanceRuntimeContext>("/attendance/runtime-context").catch(() => null),
  ]);
  ...
  const businessUnitAccess = await getBusinessUnitAccessSummary();
  ```
  `businessUnitAccess` depends on none of the three values already resolved, yet is awaited only after they complete — a fully avoidable extra sequential hop.
  `apps/admin/app/_components/runtime/runtime-module-page.tsx:16-20`:
  ```
  const user = await requireSystemAdminUser(definition.routeBase);
  const preference = await apiRequestJson<PreferenceResponse>(
    `/platform-users/me/module-preferences?moduleKey=${encodeURIComponent(moduleKey)}`,
  ).catch(...);
  ```
  The preference fetch only needs `moduleKey` (a prop), not `user`; it is nonetheless awaited strictly after the auth call rather than run alongside it.

Not established — the audit's analysis (see Evidence) identifies the mechanism but a full root-cause investigation has not been performed. See Actual Behavior for the closest available explanation.

## Impact

Adds one avoidable round trip (and its ~26-round-trip auth cost) to every load of the Attendance list and every admin platform-runtime module page (Tenants, Customers, Subscriptions, etc. — all routed through `RuntimeModulePage`).

## Affected Areas

apps/web

## Proposed Resolution

Move `getBusinessUnitAccessSummary()` into the existing `Promise.all` at `attendance/page.tsx:30`. Move the preference fetch into a `Promise.all` alongside `requireSystemAdminUser` in `runtime-module-page.tsx:17-20` (the preference fetch doesn't need `user`; only the render below it does).
