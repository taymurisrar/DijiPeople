# BUG-4429 — Monitoring queues user-correctable 4xx outcomes (blank agreement field, weak password, used signature link, duplicate agreement, stale public price) as incidents

## Summary

Production monitoring held 209 open rows (37 error, 172 warning) out of 3,774. The newest open rows are 4xx outcomes where the system correctly told a person what to fix: blank required agreement fields at submit-approval, a used signature link, an existing active agreement, a weak password, a malformed typed email, a stale public price id. They are not defects and buried the genuine 5xx rows.

## Expected Behavior

Expected, user-correctable outcomes are recorded but start as NOT_AN_INCIDENT; genuine faults still queue.

## Actual Behavior

They arrived as NEW and waited for triage.

## Reproduction

1. POST /api/contracts/<id>/submit-approval with an empty required field -> 400 -> ErrorLog row supportStatus NEW.

## Evidence

Aggregated read of production ErrorLog 2026-11-19; see `expected-protocol-outcome.spec.ts`.

## Root Cause

`isExpectedProtocolOutcome` knew only 401/404/two named 400 families, and BUG-1742 rightly forbids a blanket 400 rule.

## Impact

Growth-plan demo path and production monitoring signal quality.

## Affected Areas

[error-logs, platform-monitoring, contracts]

## Proposed Resolution

Named, path-anchored rules in `expected-protocol-outcome.ts`: used/expired signature link, password-policy text on auth routes, required-field text on submit-approval/signature-requests, CONTRACT_DUPLICATE_AGREEMENT (409), public stale price, and typed-text-only validation (email/length/not-empty) on named user-facing routes. UUID/enum/`should not exist`, 5xx and the same wording on other routes still queue (tested).
