# BUG-4056 — Create Agreement from a customer always fails for templates that need a primary signer

## Summary

Create Agreement started from a customer failed every time for contract templates that require a primary signer. Production reference admin_c54e1577-82c7-4ca9-9e90-ee6b726cd55c at 2026-10-11T06:47:10Z.

## Expected Behavior

Create Agreement from a customer fills the template from the customer record, including the primary signer when the customer has one, and only reports ineligibility when it genuinely cannot be filled.

## Actual Behavior

The request always failed for templates that need a primary signer because the source never supplied one.

## Reproduction

1. Open a customer in platform admin.
2. Choose Create Agreement with a template that requires a primary signer.
3. Observe the error (trace admin_c54e1577-82c7-4ca9-9e90-ee6b726cd55c).

## Evidence

Diagnosed from code during SESSION-0121 (DP platform remediation) against 4489a3c6, matching the production refusal `POST /api/contracts/from-source` → 400 naming `customer.primarySigner.name`, `.title` and `.email`.

## Root Cause

The contract placeholder catalog in `services/api/src/modules/contracts/contracts.service.ts` declares `customer.primarySigner.name/title/email` as required. The customer source never emitted those keys, and `CustomerAccount` had no signer fields at all. Only the lead source carried a signer, and the onboarding source carried name and email but no title. Every customer source therefore failed `assertSourceCanFillTemplate` for any template naming the signer, and the operator had no way to supply one. The admin launcher listed every template whatever the source, so the refusal only appeared on submit. The exception filter also rendered the specific refusal code as `VALIDATION_FAILED` and queued it as a NEW incident.

## Resolution

Commit 51c80beb:

- `CustomerAccount.authorizedSignerName/Title/Email` (additive migration) fill `customer.primarySigner.*`. They are never inferred from the primary contact.
- Lead conversion copies the lead's signer onto the customer.
- `GET /contracts/template-eligibility` reports each template as ELIGIBLE, NEEDS_SIGNER (the missing fields are collectable) or INELIGIBLE (the source can never supply them), using the same pure check as creation.
- `createFromSource` accepts an optional signer. It saves only the provided fields to the customer, with an audit row, then re-checks and creates the agreement. This is owner decision D3.
- The admin launcher disables ineligible templates and collects the signer inline.
- The refusal code survives to the client and is classified as an expected outcome, not an incident.

Known edge: if agreement creation fails after the signer is saved, the signer stays on the customer. It is real, audited, operator-entered data.
