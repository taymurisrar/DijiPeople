# BUG-1822 — Landing CSP permits the API over http, so its own connect-src does not match

> **Architect triage, 2026-08-28 — `BLOCKED_EXTERNAL`.** The code half is done: `securityHeadersForApp` now refuses a non-loopback `http://` API origin, so no future build can emit this policy. The remaining half is one environment variable on the landing deployment, which lives outside this repository and belongs to the owner — the same boundary as [[BUG-0905]]. Not urgent: the policy is report-only, so nothing is blocked today. It becomes blocking the moment anyone enforces the CSP, which is the direction [[BUG-1424]] points, so it should be cleared before that work starts rather than discovered by it.

## Summary

`www.dijipeople.com` serves a Content-Security-Policy whose `connect-src`
permits **`http://api.dijipeople.com/api`**. The admin and tenant apps serve the
same header with **`https://`**.

The site itself is served over HTTPS, so a request to an `http:` origin is
blocked as mixed content before CSP is consulted at all. The effect is that the
landing site's CSP does not actually permit the API origin it talks to — the
entry is there and matches nothing.

Currently harmless, because the header is `Content-Security-Policy-Report-Only`.
It stops being harmless the moment anyone enforces it, which is the direction
[[BUG-1424]] points.

## Expected Behavior

All three apps declare the same API origin in their CSP, over `https`.

## Actual Behavior

Landing declares `http://api.dijipeople.com/api`; admin and the tenant app
declare `https://api.dijipeople.com/api`.

## Reproduction

```
curl -sI https://www.dijipeople.com/   | grep -i content-security-policy
curl -sI https://admin.dijipeople.com/ | grep -i content-security-policy
curl -sI https://app.dijipeople.com/   | grep -i content-security-policy
```

The `connect-src` clause differs in scheme between the first and the other two.

## Evidence

Measured against production on 2026-08-28, deployed API commit `e0aeabcd`.

Landing:

```
connect-src 'self' http://api.dijipeople.com/api;
```

Admin and tenant app:

```
connect-src 'self' https://api.dijipeople.com/api;
```

Every other header is identical across the three — HSTS,
`X-Content-Type-Options`, `X-Frame-Options: DENY` — so this is one value, not a
missing configuration.

## Root Cause

The CSP is generated by `contentSecurityPolicy({ apiOrigin })` in
`packages/config/security-headers.js`, and `apiOrigin` comes from
`getApiBaseUrl()` — which reads the deployment's own environment. The landing
deployment's API base URL is therefore configured with an `http://` scheme where
the other two use `https://`.

That makes this a deployment-configuration difference rather than a code defect:
the same code produces the correct header for two of the three apps. The
`NEXT_PUBLIC_*` variables are inlined at build time, so the value in the served
bundle is whatever the last landing build was given.

## Impact

None today: the header is report-only, so a `connect-src` that matches nothing
blocks nothing. It generates violation reports for every API call the landing
site makes, which is noise in exactly the signal somebody would read before
deciding to enforce.

Under enforcement it would break the landing site's API calls outright —
checkout, plan browsing, lead capture and partner enquiry all talk to the API.
So it is a latent break placed directly in the path of the work
[[BUG-1424]] describes.

## Affected Areas

Modules, endpoints, screens and consumers.

## Proposed Resolution

Set the landing deployment's API base URL to `https://api.dijipeople.com/api`
and rebuild. It is one environment variable on one Vercel project.

Worth checking at the same time whether anything else in the landing build reads
that variable to *make requests* rather than to declare a CSP — a plain-http API
base would be a live mixed-content failure rather than a latent one, and the
measurement above cannot distinguish the two.

Nothing in this repository can assert the value, for the same reason recorded in
[[BUG-0905]]: it lives on the deployment. What the repository can do is compare
the three apps' headers, which is what found this.

## Acceptance Criteria

- `curl -sI https://www.dijipeople.com/` reports `connect-src` with `https`.
- All three apps declare the same API origin, scheme included.
- No mixed-content error appears in the landing site's console during a checkout.

## Resolution

Fixed 2026-08-28 by the repository owner, on the landing deployment. Verified by
measurement the same day:

```
curl -sI https://www.dijipeople.com/   -> connect-src 'self' https://api.dijipeople.com/api
curl -sI https://admin.dijipeople.com/ -> connect-src 'self' https://api.dijipeople.com/api
curl -sI https://app.dijipeople.com/   -> connect-src 'self' https://api.dijipeople.com/api
```

All three now declare the same API origin over `https`. The landing site's
`connect-src` previously named `http://api.dijipeople.com/api`, which a browser
on an HTTPS page blocks as mixed content before CSP is consulted — so the entry
matched nothing it was meant to permit.

The code half landed with this record: `securityHeadersForApp` refuses a
non-loopback `http://` API origin at build time rather than emitting a policy
that cannot work, so no future build can reintroduce it. Loopback origins stay
allowed, because `http://localhost:4000` is the correct local answer.

Guarded by REG-295.
