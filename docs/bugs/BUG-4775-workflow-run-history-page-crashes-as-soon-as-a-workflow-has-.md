# BUG-4775 — Workflow run history page crashes as soon as a workflow has one run

## Summary

The detail page of a workflow in tenant settings shows a Run History table. The table component is a server component and called a date formatter that lives in a client module, which React Server Components forbid. With zero runs the table is not rendered, so the page worked; with one run it threw and the whole page was replaced by the error screen. Every tenant that used a workflow would have hit it on first use.

## Expected Behavior

The Run History table lists each run with its time, result, emails sent and detail.

## Actual Behavior

The error screen "We hit an unexpected problem while loading this page" with the server error "Attempted to call formatDateTime() from the server but formatDateTime is on the client".

## Reproduction

1. Create a workflow with one action in a tenant. 2. Cause one run (or insert a run row). 3. Open the workflow's detail page.

## Evidence

Found in the DP-MASTER WP-26.S3 browser pass against an isolated stack. Console: the error names `WorkflowRunHistory`. `workflow-run-history.tsx` had no "use client" and imported `formatDateTime` from `settings/notifications/_components/notification-ui.tsx`, which starts with "use client". No unit or API test renders across that boundary, so 7,500+ tests passed.

## Root Cause

A server component imported a function from a client module and called it during render.

## Impact

Any tenant administrator opening a workflow that had run at least once. Reachable in production; the Run History is also where a half-delivered rule is meant to be seen.

## Affected Areas

`apps/web/app/(authenticated)/settings/approvals/_components/workflow-run-history.tsx`.

## Proposed Resolution

Take `formatDateTime` from the boundary-free `lib/formatting-context`.

## Acceptance Criteria

The page renders with runs present and shows the PARTIALLY FAILED badge for a half-delivered run.

## Regression Coverage
