# BUG-4518 — JwtAuthGuard rewrites a timesheet-restriction 403 into a 401 INVALID_TOKEN

## Summary

`JwtAuthGuard.canActivate` calls `assertTimesheetRestrictionAllowsRequest` inside its `try`. That method throws `ForbiddenException` (`TIMESHEET_ACCESS_RESTRICTED`, with `allowedRoutes`), but the guard's `catch` only re-throws `UnauthorizedException`; anything else that is not a JWT/expiry/database error falls through to a final `throw new UnauthorizedException({ code: 'INVALID_TOKEN', message: 'Access token could not be verified.' })`. A restricted employee therefore receives a 401 INVALID_TOKEN, not the designed 403 with a reason.

## Expected Behavior

A request refused by an active timesheet restriction returns 403 with `code: TIMESHEET_ACCESS_RESTRICTED`, the restriction reason and `allowedRoutes`, and the client keeps the session.

## Actual Behavior

The response is 401 `INVALID_TOKEN` "Access token could not be verified." A client that treats 401 as an expired session will try to refresh or sign the employee out.

## Reproduction

1. Give an employee an active `TimesheetAccessRestriction` with `restrictionMode: TIMESHEET_ONLY` and no expiry.
2. Call any authenticated route outside the allow-list with that employee's token.
3. Observe 401 `INVALID_TOKEN`; the 403 body is never produced. Reproduced against real PostgreSQL by `services/api/test/auth-query-budget.e2e-spec.ts` (observed status 401 where 403 is designed).

## Evidence

`services/api/src/common/guards/jwt-auth.guard.ts` — the `try` containing the restriction check, and the `catch` that re-throws only `UnauthorizedException` before the generic fallback. Found 2026-11-21 while measuring per-request queries (SESSION-0135). Related but distinct: BUG-3164 (the allow-list omits the `/api` prefix); fixing only one leaves the other.

## Root Cause

`JwtAuthGuard.canActivate` runs the restriction check inside its `try`, and its `catch` re-threw only `UnauthorizedException`; the restriction's `ForbiddenException` fell through to the generic branch, which throws 401 `INVALID_TOKEN`. The exception filter also only honours codes in the error catalog, and `TIMESHEET_ACCESS_RESTRICTED` was not in it, so even a 403 would have rendered as `ACCESS_DENIED`.

## Impact

Any employee under a non-WARNING_ONLY restriction. Severity depends on how the web app handles 401; unverified in this record. Reachable in production wherever restrictions are created.

## Affected Areas

Modules, endpoints, screens and consumers.

## Proposed Resolution

Re-throw `HttpException` (or specifically `ForbiddenException`) from the guard's `catch` before the generic fallback; fix together with BUG-3164 so the allow-list actually admits `/api/timesheets` and friends. Confirm the web client's handling of the 403 body first.

## Acceptance Criteria

A restricted employee gets 403 `TIMESHEET_ACCESS_RESTRICTED` on a blocked route and 200 on an allowed one; unrestricted employees are unaffected; the e2e assertion in `auth-query-budget.e2e-spec.ts` that currently accepts 401 or 403 is tightened to 403.

## Resolution

Fixed together with BUG-3164 on `agent/security-timesheet-datajob-followup`. The guard now re-throws deliberate `HttpException`s. `TIMESHEET_ACCESS_RESTRICTED` is in the API error catalog and mirrored in the web client catalog. The restriction data (mode, id, allow-list) travels in `details`, the only field the filter passes through. Verified against real PostgreSQL with the global `/api` prefix and the real exception filter: 403 with the reason, no 401, session not revoked, and the web client makes one request and never calls `/auth/refresh`.
