# BUG-4034 — Runtime lists rendered the definition's default columns, then swapped to the saved view's columns (column flash on load)

## Summary

Runtime list pages initialised their visible columns from the module definition, rendered the table, then fetched the operator's saved table preferences and replaced the columns. Anyone with a saved view saw the default columns flash before their own appeared.

## Expected Behavior

Resolve the effective column configuration first, then render the table; show a neutral skeleton until it is known.

## Actual Behavior

The default columns rendered for the length of the preferences request, then swapped.

## Reproduction

1. Hide or reorder columns on Tenants.
2. Reload.
3. The default column set appears briefly before the saved one.

## Evidence

`runtime-module-list.tsx`: `useState` seeded from `definition.columns`, preferences applied in a later effect; `ProDataTable` rendered meanwhile.

## Root Cause

Asynchronous preference resolution with the table rendered against a provisional column state.

## Impact

Every runtime list for operators with saved table state.

## Affected Areas

`apps/admin/app/_components/runtime/runtime-module-list.tsx`, `apps/admin/app/_components/crm/data-table.tsx`.

## Proposed Resolution

One pure resolver for the effective columns; `ProDataTable` gains `columnsPending` to draw a header-less skeleton until they are known.

## Acceptance Criteria

With a non-default saved view, a MutationObserver records exactly one distinct header set during load.

## Regression Coverage

`apps/admin/lib/runtime/effective-columns.spec.ts` (REG-665).

## Dependencies

None.

## Related Items

[[BUG-4033]].

## Resolution

`resolveTableColumnState` applies saved selection, order and widths in one step; the list passes `columnsPending` until preferences resolve. Branch `agent/admin-ux-cleanup`.

## QA Retest

Browser-verified with a saved four-column view: one header set, `Tenant | Status | Customer | Created`. Scenario QA-ADMINUX-003.
