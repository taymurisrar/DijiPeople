# BUG-2625 — Reports headcount counts soft-deleted employees and disagrees with the Employees screen

## Summary

`ReportsService` never filters `isDeleted`. `Employee` is one of only two models in
the schema that carries a soft-delete flag, and every other read path filters
`{ isDeleted: false, deletedAt: null }`. The Reports page therefore counts deleted
employees and reports a headcount higher than the Employees screen for the same
tenant.

## Expected Behavior

A deleted employee is not part of headcount. Two screens describing the same
population should agree.

## Actual Behavior

`/reports` counts every `Employee` row including soft-deleted ones; `/employees`
excludes them. The two disagree by the number of deletions the tenant has ever made.

## Reproduction

1. Note the tenant's headcount on `/reports` and the row count on `/employees`.
2. Delete an employee through the product (a soft delete: `isDeleted` becomes true).
3. Reload both screens.
4. `/employees` drops by one. `/reports` does not.

## Evidence

`grep -c isDeleted services/api/src/modules/reports/reports.service.ts` → `0`.

`services/api/src/modules/employees/employees.service.ts:650` —
`where: { tenantId, isDeleted: false, deletedAt: null }`, and the same pair appears
in `employees.repository.ts` at lines 243, 260, 284, 300, 316 and 330.

`services/api/prisma/schema.prisma`, model `Employee`: `deletedAt DateTime?`,
`deletedById String?`, `isDeleted Boolean @default(false)`.

## Root Cause

There is no shared definition of "an employee that counts". Each module re-states the
predicate, and the reporting module was written without it. The schema offers no
help: `isDeleted` exists on `Employee` and `CustomDataRecord` and nowhere else, so
there is no uniform rule to follow either.

## Impact

Correctness and trust rather than security. Headcount, department distribution and
every derived rate are overstated for any tenant that has deleted an employee. It is
the kind of defect that surfaces as "the system's numbers do not agree with each
other", which undermines a reporting product more than a visibly missing feature.

## Affected Areas

`GET /reports/headcount-summary` and anything derived from it.

## Proposed Resolution

Express the predicate once, as the workforce data source's `baseWhere` in the new
reporting semantic layer, so every workforce metric inherits it rather than
re-stating it. Re-point the legacy endpoint at that engine.

## Acceptance Criteria

- Headcount on `/reports` equals the row count on `/employees` for the same caller.
- Soft-deleting an employee decrements both.
- A unit test asserts the workforce data source's `baseWhere` contains both
  `isDeleted: false` and `deletedAt: null`.

## Regression Coverage

A metric spec asserting headcount against the analytics fixture, which seeds
soft-deleted employees precisely so this cannot regress silently.
