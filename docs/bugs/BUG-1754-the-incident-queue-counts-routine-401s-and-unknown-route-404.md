# BUG-1754 — The incident queue counts routine 401s and unknown-route 404s as incidents needing triage

## Summary

The monitoring queue holds **1,588 incidents waiting for triage**, and the
newest pages of it are almost entirely non-incidents: `401` responses from
ordinary session expiry, `404` responses for routes that do not exist, and
client validation rejections. None of these is something a human should pick up.
The genuine signal — including 11 critical items nobody has touched — is buried
under them.

## Expected Behavior

The triage queue contains failures a person should act on. Expected protocol
responses are either not recorded as incidents or are auto-resolved.

## Actual Behavior

Every 4xx is recorded as a `WARNING` incident with `supportStatus: NEW`, so the
untriaged count grows with normal usage and never falls.

## Reproduction

1. Platform Admin, **Monitoring**. "Waiting for triage" reads 1,588.
2. Read "Incidents to pick up". Recent entries include:
   - `Session is no longer active.` — `401` on `/api/auth/activity`,
     `/api/workspaces/mine`, `/api/employees/me/context` and others
   - `Cannot GET /api/plans` — `404` on a route that does not exist
   - `pageSize must not be less than 10` — `400`, a client sending a bad page size
3. Let a session expire and use the console again; new `401` incidents appear.

## Evidence

Observed directly in the queue during this pass. A single expired admin session
produced eight `Session is no longer active.` incidents in one burst, one per
in-flight request, each `New` and `Unassigned`.

The queue's own counters at the time of the pass:

```
CRITICAL, UNTRIAGED   11
WAITING FOR TRIAGE  1588
UNDER INVESTIGATION    0
RESOLVED               0
```

Nothing has ever been resolved, which is consistent with a queue nobody can work
because most of it is noise.

Roughly ten of the newest incidents were generated by this QA pass itself —
including one reading
`Cannot GET /apiC:/Program%20Files/Git/super-admin/payments`, which is a shell
path-expansion mistake of the tester's, faithfully recorded as a production
incident awaiting triage. That is a neat demonstration of the problem: a typo in
a terminal became a platform incident.

## Root Cause

Not established. The ingest path appears to record every non-2xx response
without distinguishing expected protocol outcomes from failures. A `401` on an
expired session and a `404` on an unrouted path are both normal HTTP, not
defects.

## Impact

The queue cannot be worked. 1,588 open items with 11 critical among them means
the critical ones are effectively invisible, which is the same outcome as having
no monitoring. It also makes the "Waiting for triage" figure useless as a health
signal, since it rises with ordinary traffic.

This compounds [[BUG-1750]], where the critical count is wrong as well as buried.

## Affected Areas

Error-log ingest, `platform-monitoring` queue and metrics, the Monitoring
overview.

## Proposed Resolution

Classify at ingest. Exclude — or record without queueing — the expected
outcomes: `401` from an expired or absent session, `404` for an unmatched route,
and `400` client validation rejections that carry no server fault. Keep them
searchable if they are useful for support, but out of the triage queue.

Then decide what to do with the existing 1,588: a one-off bulk resolve of the
classes above would make the queue usable again.

## Acceptance Criteria

- An expired session does not create incidents needing triage.
- A request to an unrouted path does not create an incident needing triage.
- The untriaged count reflects failures a person should act on.
- The existing backlog is triaged or bulk-resolved by class.

## Resolution

Fixed 2026-08-28 on `agent/open-bug-sweep`. The root cause this record left open
is that the ingest path recorded every non-2xx response as work waiting for a
human, with no notion that some non-2xx responses are the protocol working.

Classified at ingest. `401` from an expired or absent session and `404` for a
route that does not exist now arrive as `NOT_AN_INCIDENT` rather than `NEW`.
They are still recorded and still searchable — support needs to answer "why was
I signed out" — they are simply not queued. The "waiting for triage" metric
counted `not: 'RESOLVED'`, which counted them as open work, and now excludes
them too.

**`400` is deliberately excluded from the rule, against this record's
suggestion.** Client validation rejections are the tempting case and the
dangerous one: [[BUG-1742]] — no lead could be created from Platform Admin, for
anyone, in production — presented as exactly that, a `400` saying `partnerId
must be a UUID`. A rule that filed it as routine client error would have hidden
a defect blocking the entry point of the commercial funnel. The distinction that
matters is not "did the client send something invalid" but "could the client
have sent something valid".

The `404` rule is narrow for the same reason: only an *unmatched route*, which
Nest answers with `Cannot GET /path`. A `404` naming a record may be a broken
link and keeps its place.

For the existing 1,588 rows, `npm run repair:routine-incidents` moves the same
classes out of the queue. It touches only rows still `NEW` — anything a human
has already assigned, investigated or resolved is left alone rather than
overwritten by a heuristic — and `--dry-run` reports what it would do first.
**It has not been run against production.**

### What this record said before the sweep

Not retested against production, and the repair has not been run there.

`expected-protocol-outcome.spec.ts` covers the classification, and its
interesting assertions are the negative ones: a `400` validation rejection, a
`404` naming a record rather than a route, a `401` that is not about the
session, and anything unrecognised all keep their place in the queue.

The retest is: run `npm run repair:routine-incidents -- --dry-run` against
production, read the breakdown it prints, and only then run it for real. Then
confirm the queue depth drops and that the eleven critical items this record
mentions are now visible rather than buried.
