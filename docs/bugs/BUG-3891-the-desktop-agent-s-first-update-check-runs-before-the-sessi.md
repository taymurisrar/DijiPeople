# BUG-3891 — The desktop agent's first update check runs before the session is restored, so it 401s on every launch

## Summary

When the desktop attendance agent starts, it checks for updates before it has
restored the signed-in session. The update feed requires authentication, so the
first check goes out without a token and gets 401 `AUTH_TOKEN_MISSING` on every
launch. The next check runs about six hours later, so an agent restarted daily
checks for updates only intermittently.

## Expected Behavior

The first update check runs with a valid token, or is skipped until a session is
available.

## Actual Behavior

The first check runs while the access token is still null, and is rejected.

## Reproduction

1. Sign in to the desktop agent, then quit it.
2. Start it again and watch the API request log.
3. `GET /api/app-releases/feed/agent-desktop/latest.yml` arrives without an
   Authorization header and returns 401 `AUTH_TOKEN_MISSING`.

## Evidence

- `apps/agent-desktop/src/main/main.ts:573-580` calls
  `updateManager.start(..., () => apiClient.getAccessToken())`, and `start()`
  calls `check()` straight away.
- `sessionManager.restore()` runs only afterwards, at `main.ts:584`.
- Production `ErrorLog`, read-only query on 2026-10-07: 56 incidents from
  2026-09-24 to 2026-10-07, 13 of them in the last 14 days, with no tenant.
  They are classified `NOT_AN_INCIDENT` by `expected-protocol-outcome.ts`
  (401 plus a session code), so the queue never showed them.

## Root Cause

A startup ordering error. The update manager starts before the session is
restored.

## Impact

- Agents may run outdated builds for hours after a release.
- The failures add steady 401 noise to monitoring.
- No security impact: the feed fails closed.

## Affected Areas

- `apps/agent-desktop/src/main/main.ts`
- `apps/agent-desktop/src/main/update-manager.ts`

## Proposed Resolution

Start `updateManager` after `sessionManager.restore()` resolves, or have
`check()` return early while no token is available and retry once a session
exists.

## Acceptance Criteria

- On a cold start with a stored session, the first update check carries a
  bearer token.
- With no session, no unauthenticated update request is sent.
- A unit test on the startup order fails if `start()` runs before restore.
