# BUG-4009 — Failed onboarding resend overwrites a newer invitation during compensation

## Summary

A failed onboarding resend restored the previous invitation by application id alone. If a concurrent resend had already issued a newer token, the older request's compensation could overwrite it and invalidate the newly delivered link.

## Expected Behavior

Failure compensation changes an invitation only when the row still contains the exact token hash issued by that request.

## Actual Behavior

The compensation update/delete matched only the application id and could clobber a later request.

## Reproduction

1. Start resend A and pause its provider result.
2. After the cooldown, issue resend B and deliver it.
3. Let resend A fail and compensate.
4. Before the fix, A restored its old token over B's token.

## Evidence

`partner-experience.service.ts`, `revokeUndeliveredInvitation`; guarded by the onboarding invitation stateful test harness.

## Root Cause

Compensation lacked an optimistic concurrency predicate for the issued credential.

## Impact

Operators resending during a delayed provider failure can deliver a link that is invalid by the time it is opened.

## Affected Areas

Partner onboarding invitation and platform communications retry scheduling.

## Proposed Resolution

Include the issued token hash in compensation `updateMany`/`deleteMany` predicates. Covered by EXECPLAN-0055.

## Acceptance Criteria

- Compensation restores or deletes only the token issued by its own request.
- A newer token survives stale compensation.
- Failed outbound rows carrying dead links are removed from retry scheduling.

## Regression Coverage

`partner-onboarding-invitation.spec.ts` stateful failed-resend coverage plus conditional token predicates.

## Dependencies

None.
