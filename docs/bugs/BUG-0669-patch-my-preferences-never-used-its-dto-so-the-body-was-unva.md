# BUG-0669 — PATCH my-preferences never used its DTO, so the body was unvalidated

## Summary

`UpdateMyPreferencesDto` existed in `settings-context.controller.ts` with
`@IsString`, `@MaxLength` and `@Matches` rules on all four fields — and was
never referenced. The handler took `@Body() dto: Record<string, unknown>`, which
gives the global `ValidationPipe` no metadata to validate against, so
`PATCH /settings/my-preferences` accepted any body at all.

## Expected Behavior

The body is validated against the DTO: bounded strings, an enumerated time
format, and a 400 for an unknown field, as the global pipe's
`forbidNonWhitelisted: true` implies everywhere else.

## Actual Behavior

Everything reached the service. `normalizePreferences` there is an allow-list of
four keys, so nothing unexpected was written — but the **values** were taken as
sent.

## Reproduction

1. `PATCH /api/settings/my-preferences` with `{ "timezone": "x".repeat(500) }`.
2. It is accepted and persisted rather than refused with a 400.
3. `PATCH` with `{ "timezone": "Not/A/Zone" }` — `new Intl.DateTimeFormat`
   throws `RangeError`, which surfaces as a **500** where 400 is the answer.

## Evidence

- `settings-context.controller.ts` — `updateMyPreferences` took
  `Record<string, unknown>`; the DTO sat unreferenced below the class.
- `settings-context.service.ts` — `normalizePreferences` reads four keys and
  drops the rest; the timezone reaches `new Intl.DateTimeFormat` unguarded.
- ESLint reported the class as `no-unused-vars`.

## Root Cause

`declared-but-unwired-step`, the pattern this repository already has a name for:
the declaration reads as cover and the behaviour is absent. Anybody auditing the
controller would see a DTO with correct rules and move on.

## Impact

Low. Authenticated, self-scoped, and the allow-list prevents mass assignment —
the exposure is unbounded strings on the caller's own row, and a 500 instead of a
400 on an invalid timezone. It is worth fixing mostly because a validation gap
that *looks* closed is the kind that stays open.

## Affected Areas

`PATCH /api/settings/my-preferences`.

## Proposed Resolution

Use the DTO as the parameter type.

## Acceptance Criteria

- The handler's `@Body()` parameter type is `UpdateMyPreferencesDto`.
- Over-long values, wrong types and unknown fields are refused.
- An empty body is still accepted — updating one preference must not require
  restating the others.

## Regression Coverage

REG-224 — `my-preferences-validation.spec.ts`, seven tests.

The load-bearing one asserts the **parameter type** through
`design:paramtypes`, because that is the fact that was wrong. A DTO's rules can
be perfect and never run; without that assertion every rule test could pass while
the endpoint stayed open.

## Dependencies

None.

## Resolution

The handler now takes `@Body() dto: UpdateMyPreferencesDto`, and the class moved
above the controller and is exported.

The move is not cosmetic: `design:paramtypes` metadata is evaluated when the
controller class is defined, so a DTO declared after it is in a temporal dead
zone. `wiring-invariants.spec.ts` caught that immediately — *"Cannot access
'UpdateMyPreferencesDto' before initialization"* — which is the second time this
session that the runtime invariant was right where reading was not.

Fixed on branch `agent/qa-verify-and-burndown`.
