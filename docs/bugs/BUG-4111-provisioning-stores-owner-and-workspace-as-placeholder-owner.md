# BUG-4111 — Provisioning stores Owner and Workspace as placeholder owner names, and owner and other lookups do not link to their record

## Summary

Customer → Summary → Tenant primary owner showed "Anou Owner". The display
was faithful: provisioning had stored the word "Owner" as the user's surname
because none was entered. Separately, several lookups rendered as plain text
instead of linking to the record they name, and the tenant record header said
"Primary tenant owner: Unassigned" while its Access tab named the owner.

## Expected Behavior

An owner's stored name is exactly what was entered; a missing surname is
empty. Every lookup naming a record links to where that record is read or
managed. Owner names can be corrected from Platform Admin.

## Actual Behavior

- `provisioning-requested.handler.ts`, `tenant-identities-provisioning.service.ts`
  and `tenant-access.service.ts` wrote "Owner" (and "Workspace" as a first
  name) when the source had none.
- Lookups with no record-page mapping (platform users, teams, payment tenant
  and invoice, subscription price, the tenant primary owner) did not link.
- The tenant header's owner slot read `ownerUser`; the tenant payload carries
  `owner`, so it always said "Unassigned".
- The Access & Security panel offered no way to edit an owner's name although
  `PATCH /tenants/:id/access/:userId` accepted one.

## Reproduction

1. Provision a tenant from an onboarding or checkout whose owner has no last
   name.
2. Open the customer → Summary → Tenant primary owner: "<first> Owner".
3. The value is not a link; the tenant's header reads "Unassigned".

## Evidence

The three placeholder fallbacks above; the form joins first and last name, so
the placeholder surfaces verbatim.

## Root Cause

Placeholder values were used to satisfy a required column instead of storing
the empty surname the schema already allows, and link resolution covered only
collections with a `/:id` record page.

## Impact

Every Platform Admin and tenant-app screen naming an affected owner. Reachable
in production.

## Affected Areas

Tenant provisioning (onboarding, checkout, Access tab create); admin customer,
tenant, payment, subscription, contract, support-case and lead records.

## Proposed Resolution

Store entered names only; repair existing provable placeholders; link every
lookup; allow editing owner details.

## Acceptance Criteria

- New owners with no surname are stored with an empty surname.
- The repair changes only owners whose every source has the name part empty,
  is idempotent and audited; a real surname "Owner" is kept.
- Tenant primary owner links to the tenant's Access & Security tab with the
  owner row outlined; platform users and teams link to their lists outlined.
- Every non-catalog lookup links (enforced by `lookup-links.spec.ts`).
- The tenant header names the primary owner.

## Resolution

Branch `agent/owner-names-and-lookup-links`: `storedPersonName` in
`common/utils/person-name.ts` used by all three provisioning paths;
`repair:owner-names` (dry run by default, `--apply` to write, audited as
USER_PLACEHOLDER_NAME_REPAIRED); `ProDataTable.highlightedRowId`;
managed-list links for platform users and teams; explicit links for payment
tenant/invoice and subscription price; owner link to the tenant Access tab;
"Edit details" on Tenant Owners with name changes audited; header owner slot
falls back to the record's own relation.
