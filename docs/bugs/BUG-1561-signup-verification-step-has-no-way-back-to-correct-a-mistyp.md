# BUG-1561 — Signup verification step has no way back to correct a mistyped email

> **Architect triage, 2026-08-27 — `DEFER`.** On the paid funnel, which argues for urgency, but signup completes correctly when the address is right.


## Summary

The signup verification step has no Back button. A prospective customer who
mistypes their admin email address cannot correct it — the verification code goes
to the wrong address and the only route forward is to restart all five wizard
steps.

## Expected Behavior

The verification step offers a way back to correct the email address, or a way
to change the address in place and reissue the code.

## Actual Behavior

The step offers no Back control. Correcting a mistyped address requires
restarting the signup from the beginning.

## Reproduction

1. Begin a signup on `www.dijipeople.com`.
2. Reach the verification step and enter an email address with a typo.
3. Look for a way back to the previous step.

## Evidence

Observed on production, 2026-08-26, during the signup funnel walkthrough.

## Root Cause

Not established. The step appears to omit the back control the other wizard
steps carry, but whether that is deliberate — to protect the issued code — has
not been confirmed.

## Impact

This is on the paid acquisition path, at the step immediately before payment. A
typo is a common and entirely expected user error, and the cost of it here is
re-entering four steps of company details. Some proportion of prospects will
simply leave.

Recorded as low severity because signup completes correctly when the address is
right, but the position of this defect in the funnel is worse than its severity
suggests.

## Affected Areas

- `apps/landing` — the signup wizard, verification step
- `services/api/src/modules/leads` — signup intake and verification codes

## Proposed Resolution

Add a way to change the email address from the verification step, reissuing the
code against the corrected address and invalidating the previous one. Preserve
the entered wizard state so nothing else has to be retyped.

If the step deliberately omits Back to protect the issued code, invalidating the
old code on change satisfies that concern without stranding the user.

## Acceptance Criteria

- A user on the verification step can correct the email address.
- A new code is issued to the corrected address and the previous code no longer
  works.
- Wizard state entered in earlier steps survives the correction.

## Regression Coverage

None yet. Needs a signup test that corrects the address at the verification step
and completes. Requires a `REG-nnn` entry once written.

## Dependencies

None.

## Resolution

Fixed 2026-08-28 on `agent/open-bug-sweep`.

The verification step now offers **Change email address**, which returns to the
wizard. Every answer the buyer gave is still in the component's state, so
nothing is retyped — they land back on the review step with the form intact,
correct the address and resubmit.

This record asks that a corrected address reissue the code and invalidate the
previous one, and notes that if Back was omitted deliberately to protect the
issued code, invalidating it satisfies that concern. **The API already does
this**, so no change was needed there: `issueCode` overwrites
`emailVerificationCodeHash` and resets `emailVerificationAttempts`, so the
moment a new code is sent the previous one stops working.

Guarded by REG-296.

## QA Retest

Not retested in a browser. The check is short: reach the verification step, press
Change email address, confirm the wizard reappears with every field still
populated, correct the email, resubmit, and confirm the new code works and the
old one does not.

The last part is the one worth actually doing rather than assuming — it depends
on the API overwriting the hash, which is read from the source here rather than
observed.
