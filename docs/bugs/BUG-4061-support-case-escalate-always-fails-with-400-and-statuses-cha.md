# BUG-4061 — Support case Escalate always fails with 400 and statuses change without validation

## Summary

Escalate on a support case always failed with 400, and the status field could be changed from any status to any other without validation.

## Expected Behavior

Escalate raises the numeric escalation level and succeeds; status changes follow the allowed lifecycle transitions and are rejected otherwise.

## Actual Behavior

The UI sent escalationLevel ESCALATED to an integer field (400). PATCH accepted any status from any status, and concurrent merges were unsafe.

## Reproduction

1. Open a support case and press Escalate; observe 400.
2. PATCH a CLOSED case to NEW; observe it accepted.

## Evidence

Reproduced and diagnosed during SESSION-0121 (DP platform remediation) against 4489a3c6. The regression tests named in REG coverage pass with the fix; they were not mutation-tested against the pre-fix code.

## Root Cause

apps/admin sent a string where support-cases expects an Int, and the service had no transition table; merge ran without a guard against terminal or already-merged cases.

## Impact

Reachable in production through the normal user flow described above.

## Affected Areas

support-cases, apps/admin

## Proposed Resolution

Implemented; see Resolution.

## Acceptance Criteria

The expected behaviour above holds and the regression test passes.
