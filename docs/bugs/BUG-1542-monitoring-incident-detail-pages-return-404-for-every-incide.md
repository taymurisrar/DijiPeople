# BUG-1542 — Monitoring incident detail pages return 404 for every incident

## Summary

The platform monitoring queue lists 1,495 incidents, but every attempt to open
one returns HTTP 404. The queue can be counted and sorted and never worked. One
incident is marked critical and none has ever been resolved, which is the
expected consequence of a detail page nobody can reach.

## Expected Behavior

Selecting an incident from the monitoring queue opens its detail page, showing
the recorded error, its context and whatever actions resolve or dismiss it.

## Actual Behavior

`/settings/monitoring/error-logs/<id>` returns HTTP 404 for every incident id.
The list renders correctly; only the detail route fails.

## Reproduction

1. Sign in to `admin.dijipeople.com` as a platform owner.
2. Open Settings → Monitoring.
3. Select any incident from the queue, or navigate directly to
   `/settings/monitoring/error-logs/<id>` with an id taken from the list.
4. Observe the 404 page.

## Evidence

Observed on production, 2026-08-26:

- Six distinct incident ids, taken from the rendered list, produced a 404 on
  navigation. Several failed during Next.js link prefetch, before any click.
- The queue itself reported 1,495 incidents, 1 critical, 0 resolved.

## Root Cause

Not established. Both a missing route segment under the admin monitoring path
and a detail endpoint that does not accept the id shape the list emits would
produce this symptom, and they have not been told apart.

## Impact

Platform monitoring is effectively write-only. Operators can see that incidents
exist and cannot triage, diagnose or resolve any of them. The "0 resolved"
figure across 1,495 incidents is not a backlog — it is the absence of a working
tool, and it means no production error recorded by this system has ever been
looked at through the product.

Reachable in production today.

## Affected Areas

- `apps/admin` — `/settings/monitoring/error-logs/<id>` route
- `services/api/src/modules/platform-monitoring`
- `services/api/src/modules/error-logs`

## Proposed Resolution

Determine whether the failure is the admin route or the API endpoint by calling
the detail endpoint directly with an id from the list. Fix whichever is absent,
and add the missing half if both are.

The list should not link to a route that cannot resolve; whichever fix lands,
the link and the target must be verified together.

## Acceptance Criteria

- Selecting any incident in the monitoring queue opens its detail page.
- The detail page renders the recorded error, its timestamp, and its context.
- An operator can move an incident out of the unresolved state.
- No id present in the list produces a 404.

## Regression Coverage

None yet. Needs a test that takes an id from the list endpoint and asserts the
detail endpoint returns it, so a list and a detail that disagree about id shape
cannot ship again. Requires a `REG-nnn` entry once written.
