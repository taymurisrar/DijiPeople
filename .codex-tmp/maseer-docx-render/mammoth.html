This plan covers the first DijiPeople customer rollout for Maseer Group or Maseer Tech. The final legal/customer name is intentionally left as a confirmation item. The commercial relationship is understood as a partnership in which Sir Saud owns Maseer Group and Taimur Israr owns DijiPeople. DijiPeople currently operates in association with Maseer Group but is expected to become a separate product/business over time.

Recommendation Run a controlled Phase 1 rather than exposing every available module. Start with employee records, leave, attendance, tenant settings and dashboards; stabilise real usage; then release recruitment and onboarding as Phase 2.

Target outcome

  • Maseer has a configured tenant with accurate employee and organisation data.
  • Employees can access their profile, submit leave and use the agreed attendance method.
  • Managers can review attendance and approve or reject leave requests.
  • HR administrators can maintain employees, leave policies, attendance settings, holidays and user access.
  • Leadership can view trusted Phase 1 dashboard metrics.
  • DijiPeople has documented support, issue triage and change-control processes for its first production customer.

3. Implementation approach and governance

Guiding principles

  • Configure the standard product first. Avoid customer-specific code unless a confirmed business requirement cannot be met through tenant settings or reusable rules.
  • Use a train-the-trainer model: DijiPeople trains Maseer HR/admin champions, who then help reinforce employee adoption.
  • Use real Maseer processes and approved data in UAT, not generic demonstrations.
  • Maintain one controlled issue list with severity, owner, target date and release decision.
  • Freeze Phase 1 scope after the kickoff. New ideas go into the Phase 2 backlog unless they block legal, security or operational use.

Data migration method

1. DijiPeople issues controlled Excel/CSV templates with required fields, examples and allowed values.

2. Maseer completes the files and performs an internal first review before submission.

3. DijiPeople validates duplicates, missing relationships, invalid dates, unsupported values and leave-balance totals.

4. A first import is performed in staging and a reconciliation report is returned.

5. Maseer corrects the source file rather than making uncontrolled staging edits where possible.

6. The approved final file is frozen for production cutover and retained as migration evidence.

7. Post-import checks confirm employee count, active/inactive count, manager relationships, balances, shifts and role access.

Defect severity and release treatment

Severity

Definition

Go-live rule

Critical

Outage, data loss/corruption, cross-tenant exposure, login failure for broad user groups or unusable attendance/leave process.

Must be fixed and retested before go-live.

High

Major process is blocked for a role or produces materially incorrect business results without a practical workaround.

Fix before go-live or obtain explicit sponsor risk acceptance with a dated fix.

Medium

Limited impact with a safe workaround; does not compromise data or core operation.

May enter post-go-live backlog with owner and target date.

Low

Cosmetic, wording or minor convenience issue.

Does not block go-live.

Cutover checklist

1. Freeze approved employee, leave-balance and attendance configuration files.

2. Create a production recovery point and verify monitoring and support contacts.

3. Apply production configuration and import final data/delta.

4. Run employee-count, hierarchy, leave-balance and shift reconciliations.

5. Smoke-test administrator, manager and employee accounts.

6. Send invitations in controlled batches, starting with HR, managers and pilot employees.

7. Deploy the desktop agent to approved devices and confirm the first attendance event.

8. Open the support channel, daily checkpoint and issue register.
